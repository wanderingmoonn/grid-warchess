# 2026-11-13 高境界修士强度分析（只分析，未改代码）

## 背景

修真包的升级难度是按"整体水温不超过第 6 时代"定的（`HIGH_RANK_EXP_FROM=6`、
`HIGH_RANK_EXP_MUL=1.65`）。main 分支已经有第 7 代「装甲时代」和第 8 代「聚变时代」，
需要重新评估 rank 6+ 够不够。

## 关键测量（用真实 stats.ts 公式跑，未改代码）

各境界炼气士（150 金）：

| 境界 | 攻(次数) | 甲 | 血 | 射 | 溅 |
|---|---|---|---|---|---|
| 4 | 33×2 | 21 | 98 | 3 | 1 |
| 5 | 44×3 | 32 | 222 | 3 | 1 |
| 6 | 61×3 | 47 | 571 | 4 | 1 |
| 7 | 93×4 | 66 | 1514 | 4 | 1 |
| 8 | 153×4 | 89 | 3948 | 5 | 2 |

## 第一次结论错在哪（重要）

第一版只用了单件主武器（96/144 伤害）代表 7/8 代，**漏了模块化配装**，于是得出
"6 期能单挑 8 代"的错误结论。实际 8 代「塔」：

- 裸素体 44 → 常规配 135 → **满配 330 伤害/回合**（轨道炮 273 破甲 reload + 等离子 135
  + 微型导弹巢 39×3；甲 31→43，血 429→546，电力 draw 124 / 聚变堆 280）
- 多武器**同一回合各开一次火**（`attacksLeft` 在 `shotsLeftThisTurn>0` 时重置）
- 7/8 代起**破甲是标配**（反装甲炮、磁力锤、轨道炮、等离子刃），把修士 47/89 甲砍半

## 按"以一敌多"标准重算（炼气士先手、敌人贴身、敌人挤一圈 = 对修士最有利的假设）

能同时打赢几个：

| 境界 | 3代中位 | 5代中位 | 6代 中型坦克 | 7代 砧常规 | 8代 塔常规 | 8代 塔满配 |
|---|---|---|---|---|---|---|
| 2 | 1 | 0 | 0 | 0 | 0 | 0 |
| 3 | 3 | 1 | 0 | 0 | 0 | 0 |
| 4 | 12+ | 3 | 2 | 0 | 0 | 0 |
| 5 | 12+ | 12+ | 8 | 1 | 0 | 0 |
| 6 | 12+ | 12+ | 12+ | 4 | 1 | 0 |
| 7 | 12+ | 12+ | 12+ | 12+ | 11 | 3 |
| 8 | 12+ | 12+ | 12+ | 12+ | 12+ | 12+ |

结论：按"同代对标 + 要一挑三"的标准，现在**差 1.5~2 个境界**。6 期打 8 代只能 1 换 1，
打满配直接 0；要到 7 期才真正"以一敌多"跨代。

## 结构性原因（不是加数值能修的）

1. **单体多段**：3~4 下攻击都是单体，溅射只有 1~2 格 ×50%，人一多输出不乘；
   对面 N 台一起打却是 N 倍。
2. **破甲**：7/8 代破甲武器把甲砍半，堆甲这条路被硬克。
3. **射程**：修士 4~5 格，7/8 代武器 7~11 格，会被放风筝；贴身要先吃 1~2 轮。

→ 想做到"以一敌多"，杠杆是**面积（溅射/反击）**，不是继续堆攻血甲。

## 设计意图（用户 2026-11-13 明确）

- **不调曲线**，用经验墙拦；适当时候把墙往后挪。
- 高境界修士难修成、早被消耗、难量产，所以 2 级以上就该有"以一敌多"的水准。
- 7/8 代的强度主要在模块化配装，比较时必须按配装档位分层（裸素体 / 常规配 / 满配）。

## 提醒（未验证，待确认）

经验"收入"是线性（打坐 = 境界+2），"需求"是三次+指数（6→7 要 2292，打坐 9/回合 =
254 回合，寿元只有 73）。所以**只挪墙不挪收入，门还是关的**；两者要一起动。

临时探针在 `.tmp/highrank.mjs`、`.tmp/highrank2.mjs`、`.tmp/onevsmany.mjs`、
`.tmp/onevsmany2.mjs`（未提交，可删）。

# 第二件事：法术池从 1 门扩到 3 门（已落地）

用户方向：**不动境界曲线**（那是普攻的唯一真相，改起来牵一发动全身），
**用法术一点一点补强度**。100 份草案还没进来，先做两门验证。

## 新增

- `skills/spirit-breath.ts`「吐纳术」：抽脚下 50% 灵气，2 点换 1 点修为，
  单次上限 `4 × 境界`（保底 4），耗 20 灵力，`targeting: 'none'`。
- `skills/gang-wind.ts`「罡风」：射程 8、半径 2、范围内**所有**敌人各吃
  `30 + 9×境界`（无视护甲），耗 80 灵力，研发 90 灵石，`minRank 4`。
- `qi-field.ts` 新增 `drainQiAt(s, x, y, ratio)`：`writeQi` 仍是唯一写入口。
- `spells.ts` 的 `SpellDef` 新增 `minRank`（"够不够格学"），
  与「法术位 = ⌊境界÷2⌋」（"背得下几门"）是两件事。检查放在藏经阁之前。

## 几个刻意的选择（改之前先读）

- **吐纳用 floor 不用 ceil**：先算修为再倒推抽多少灵气，保证
  「抽掉的灵气 = 修为 × 2」，账面是平的。
- **吐纳开 `multiCast: true`**：`skillTurn` 是整个单位共用的，
  写成 false 会连带锁住其它非连发法术。次数限制交给"抽一半自带衰减"。
- **罡风逐个 `api.hurt` 而不是走 splash**：要的是"一片人同时掉血"，
  不是 50% 的边际伤害；代价是不吃任何溅射加成/减免（有意的）。
- 罡风圈人用 `distToUnit`（点到矩形），2×2 建筑一角在圈里就算中。
- 罡风**空放不扣灵力**：先圈人再扣。

## 待办 / 已知缺口

- 法术没有视野门槛（`doHeroSkill` 不查迷雾），可以对看不见的格子放——
  和掌心雷同一个老问题，罡风因为是 AOE 更容易滥用。
- AI 不会放任何法术（`ai.ts` 的 `heroSkillCandidate` 只遍历 `def.skills`，
  不读 `extraSkills`，也没有修真技能的 case）。用户说有人在重构 AI，先不管。
- 灵力池仍是 `(4+境界)×10` / 回 30：6 期 100 点，罡风一发 80，一回合只能一发。

## 验证

`npm run manual` 9 册（新法术已入册）。

# 第三件事：修「无来源伤害无视护甲」（2026-11-13）

## 病根

`hurtUnit` 收的是"该掉多少血"，**自己不减甲**——因为普攻那条路已经在
`computeDamage` 里减过一次，再减就是扣两遍。代价是：所有绕过
`computeDamage` 的伤害都自动获得"无视护甲"特权。地雷、水雷、哥布林陷阱、
自爆冲击波全中。表现是"重甲兵踩雷和民兵踩雷掉一样多"。

`marks.ts` 里原本还写着"雷炸出来的伤害不走进攻公式（无护甲）"，
那是把 bug 当设计写进了注释——已改。

## 修法

不能直接让 `hurtUnit` 减甲（普攻会扣两遍）。做法是把"物理直伤"单列：

- 新增 `hurtPhysical(s, target, amount, opts)`（`rules.ts`，导出），
  以及 `AbilityApi.hurtPhysical` 和 `MarkApi.hurtPhysical` 两个入口。
- 口径：**数值是"攻击力"走 hurtPhysical；数值是"算好的伤害"走 hurt。**
- 甲取 `ownArmorOf`（兵种基础 + 圣剑/石化），**不含地形、不含临时护甲**。
  地雷不给摆阵/吃药的时间。
- `opts.pierce` = 破甲（甲减半），给反装甲雷用。
- 打不穿（dealt 0）时写一条**私有战报**"扛住了这一下"，避免看起来像没触发。
- `logText` 支持函数形式：减完甲才知道掉了多少，写死数字会变成假账。

## 改动点

地雷（era-mine 16）、反装甲雷（era-at-mine 30 → **pierce**，不再"无视护甲"）、
水雷（naval 14）、哥布林陷阱（fantasy 10）、自爆冲击波（abilities 自爆）。
玩家可见的 summary 全部改成"按护甲结算"/"破甲"，规则书同步重生成。

## 测试

老断言改了 8 条（它们原本钉的正是旧行为，改法是写成
`max(0, 威力 − 目标护甲)`，跟着兵种表走，改甲不会红）。
新增 1 条口径用例「物理直伤：hurtPhysical 先减甲、hurt 不减」。

## 遗留

- **main 分支的 `armor-expansion.ts` 里那颗「反装甲地雷」（52）还在走 `hurt`**，
  merge 时不会自动跟着改，要手动换 `hurtPhysical(..., { pierce: true })`。
- 高甲单位现在对地雷**免疫**（伤害 0）：8 代塔 43 甲、rank8 修士 89 甲。
  这是"甲厚"的直接后果，要不要给个保底（比如至少 1 点 / 25%）需要拍板。
- 仍走 `hurt` 的：掌心雷、罡风（明示无视护甲）、剑气/血祭（先 computeDamage）、
  陨卵（魔法伤害，按设计不吃甲）。

# 第四件事：收编两条"野路子" + 扣血出口守卫（2026-11-13 下午）

## 背景

上一批修完地雷之后，全仓库还有 8 条扣血路径。梳理出来 9 处裸 `hp -=`：
hurtUnit 自己、中毒、灼烧、decays 自损、onTurnEnd.hurt、焦土、
城市 ×2、守御阵吸血。已提交在 `9686563`。

## 这一批做了什么

1. **扣血出口守卫**（`test-rules.ts`「代码纪律：扣血只有一个出口」）：
   扫 `src/core/**/*.ts` 的所有 `.hp -=`，除 hurtUnit 内部外必须带
   `hp-exempt: 理由`。新加一条直伤会当场红，报错里直接指向 hurtPhysical。
   在 `npm run test:rules` 里，CI 会跑。这是防"再长一条路"的唯一有效手段。
2. **焦土（死亡枕藉）→ `hurtPhysical`**：`KillCtx` 新增 `hurtPhysical` 入口
   （由 rules 的 `fireKilled` 注入）。副作用是守御阵现在能接尸体砸人，
   战报统一，护甲生效。summary 同步改成"（按护甲结算）"。
3. **`onTurnEnd.hurt` → `hurtUnit({ internal: true })`**：
   天气维护费/雷暴这类"内生损耗"仍然**不吃护甲**（这是设计），
   但不再绕过统一出口。`internal` 只跳过两件事：伤害转移、受伤钩子。

## 关键区分（写进注释了，别再混）

**"绕过护甲"和"绕过统一出口"是两件事。**
- 走不走护甲：由选哪个函数决定（`hurt` = 数已算好 / `hurtPhysical` = 先减甲）
- 转不转移、触不触发受伤钩子：由 `internal` 决定

所以"维护费不足扣血"= `hurt(..., { internal: true })`：
不吃甲 + 没攻方 + 不被阵挡 + 不触发挨打钩子，但仍然只有一条出口。

另注：`seasons.ts` 的天气伤害本来就在扩展内部自己算了甲
（风暴 5×10 点普通伤害吃甲、雷暴 50 点真伤不吃），
所以它传给 `hurt` 的确实已经是"算好的数"，语义正确，没改。

## 测试

`test:rules` 709、`test:cultivation` 138（+1 守御阵接焦土）、`test:ui` 206、
`tsc` 干净。老断言改了 3 条（焦土 ×1、死亡枕藉 ×2），改法同前：
写成 `max(0, 威力 − 目标护甲)`。

## 还没做

- 中毒/灼烧/decays 仍在裸扣（标注着 hp-exempt）。要收编的话得先解决
  "状态的 onTurnStart 返回文案、由调用方统一 log"这条链，不然会写两条战报。
- 致死仍未统一：`killUnit` / `sweepDead` / 自己 filter 三套并存，
  差别在击杀归属（毒死/烧死算不到任何人头上）。

# 第五件事：中毒/灼烧/自损收编到统一出口（2026-11-13）

## 做了什么

- `StatusDef.onTurnStart` 的签名从 `(s, u, val)` 改成 `(c: StatusTickCtx)`，
  ctx 里有 `{ state, unit, val, hurt(amount) }`。**这是机制，不是特例**：
  任何扩展注册状态都能用，核心里没有 `if (id === 'poison')`。
- `poison` / `burn` 改成 `c.hurt(dmg)`；`decayUnits`（自损）改成
  `hurtUnit(s, u, d, { internal: true })`。
- `c.hurt` **刻意不写战报**——`onTurnStart` 返回的那行字符串才是战报。
  两处都写会双份。这条写进了 StatusTickCtx 的注释。
- 守卫测试的豁免从 7 处降到 4 处：hurtUnit 自己、城市 ×2、守御阵吸血。

## 关于"这些状态来自扩展包"的核查结论

**poison / burn 其实是核心自己的**：`SKILL_EFFECTS.cycle`（属性切换）和
`applyOnHitStatus` 里的 `heroBuff.elementHit === 'nature' / 'fire'` 都是核心代码，
它们直接贴毒/贴火。所以状态定义留在 `STATUS_REGISTRY` 是对的，
搬出去会让核心这条路变成"贴一个未注册的状态"当场抛错。

`decays` 是 `UnitTypeDef` 上的通用字段（只有 fantasy 的一个兵在用），
`decayUnits` 是通用机制，不是特例，也没搬。

**真正的残留是文案**：`burn-hit`（燃焰）的 summary 写着
"点燃 3 回合，每回合掉 8% 生命上限"，而实际规则是"每层每回合 4 点、最多 3 层"
（`BURN_PER_LAYER = 4`，且 burn 的数值同时充当层数和剩余回合）。
已改成与规则一致。

## 顺手记下的问题（没改）

burn 的数值**同时是层数和剩余回合**（`addBurnLayer` 直接 +1，tick 每回合 −1），
所以"3 层"和"还能烧 3 回合"绑死。这是既有设计，改它要动状态模型，不在这一批。

## 测试

`test:rules` 709、`test:cultivation` 138、`test:ui` 206、`tsc` 干净、manual 重生成。
守御阵那条用例改成走真实路径（END_TURN → 状态结算），不再手工调 onTurnStart。

# 第六件事：状态注册表下沉 + 中毒/灼烧搬进奇想包（2026-11-13）

## 为什么要动

`STATUS_REGISTRY` 和 `registerStatus` 原先长在 `rules.ts` 里，而扩展不能 import rules
（rules → expansions → 扩展 → rules 是运行时环）。于是"扩展可以注册状态"只是注释里的
一句话：中毒/灼烧/诅咒这些**奇想包的内容**被迫写死在核心，关掉奇想也还在。

## 做了什么

1. 新建 `src/core/statuses.ts`：`StatusDef` / `StatusTickCtx` / `STATUS_REGISTRY` /
   `registerStatus` 全部下沉。依赖只有 `types.ts`，扩展可以直接 import，不成环。
2. `ability-hooks.ts` 里那两个接口改成 `export type { ... } from './statuses.ts'`（兼容旧导入）。
3. `rules.ts`：状态表从 `export const STATUS_REGISTRY = {...}` 改成
   `const CORE_STATUS_DEFS = { slow, chill, sunder, curse, curse-deep }` + 循环注册，
   并 re-export `STATUS_REGISTRY`/`registerStatus` 给测试。
4. `fantasy-packs.ts`：`registerStatus(poison)` / `registerStatus(burn)` + `BURN_PER_LAYER`
   搬过来（原来是 rules 的导出，`scripts/dump-fantasy.ts` 的 import 跟着改）。
5. `StatusTickCtx` 补了 `maxHpOf` / `utypeOf`：状态在扩展里拿不到 `rules` 的这两个函数，
   由核心注入。

## `internal` 改名 `attrition`

用户质疑"internal 是不是专门给守御阵开后门的"。结论：概念是对的（它描述伤害的性质，
不是某条能力的开关），但名字在说"不是什么"。改成 `attrition`（损耗），
注释里写清两个消费者（转移、受伤钩子），以及"以后要按物理/法术分挡，应该把伤害种类
传进 redirectDamage 让防御方自己判，而不是加第二个布尔"。

## 还没搬（下一步的清单）

- `SKILL_EFFECTS` 12 条全在 rules，而**只有 fantasy-packs 有带技能的兵**
  （核心与其他包 `skills:` 计数为 0）。这一搬迁是纯机械的：
  `registerSkillEffect` 已经是现成插件口。
- 元素/魔法：`weak`/`resist` 只有奇想兵有（核心 0 处实际使用），
  但 `applyElementMul` / `magicSegment` 在 computeDamage 里，需要一个**护甲之后**的
  伤害阶段钩子才能真正搬走（`modifyDamage` 跑在减甲之前，顶不上）。
- `heroBuff`（elementHit / burnLayers / hidden / freeShot / rangeMul）被核心战斗与
  迷雾读取，搬它得先把这些降级成通用修正。
- `BURN_MAX_LAYERS` 与 `addBurnLayer` 仍留核心：命中即贴那条路（`applyOnHitStatus`）
  还在核心，等元素系统搬完再一起走。

# 第七件事：死亡合一（2026-11-13）

## 之前的状态

"一个单位死了"有五套实现：
1. `abilityApi.killUnit`（完整：移除+战报+沉船+fireKilled）
2. `doAttack` 里内联三块（主目标 / 溅射 / 反击阵亡）
3. 攻城溅射又一块
4. `sweepDead`（战报写给自己、fireKilled(undefined)）
5. 焦土、自爆善后直接 `filter`（**不跑亡语**）

## 现在

- `function killUnit(s, victim, killer, logText)` 是**唯一实现**，abilityApi 只是转发。
- `sweepDead` 只做一件事：把 hp≤0 的逐个交给 killUnit（第二入口，不是第二套实现）。
- `fireKilled` / `drownCargo` 现在**各只有 1 个调用点**，都在 killUnit 里。
- `KillCtx` 新增 `sweepDead()`，给扩展用（焦土已经改用；扩展不能 import rules）。
- 战报收件人统一成 `killer?.owner ?? victim.owner`（原来是 `other(victim.owner)`，
  和 sweepDead/反击阵亡的实际行为不一致）。

## 修掉的真实 bug

焦土砸死的单位**不跑自己的亡语**：炸死一个自爆兵，自爆兵不炸，连锁到第二代就断。
自爆波及善后（`dctx.result.blasts > 0 → filter`）同理。
现在两处都走 sweepDead，已加用例「死亡合一：焦土砸死的兵也会跑自己的亡语」。

## 边界（写进 killUnit 注释了）

- 走 killUnit = **死亡**：打死、毒死、烧死、自损、坐化 → 战报/沉船/onUnitKilled/亡语。
- 不走 = **移除**：遣散、投降、分裂合体、桥塌落水、飞机上舰 → 没有凶手，不触发亡语。
- 血归零 ≠ 立刻消失：「油尽灯枯」要靠"待清场"这一拍让玩家救人或补刀。
