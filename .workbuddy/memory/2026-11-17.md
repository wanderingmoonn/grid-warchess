# 2026-11-17

## 「黑暗动乱」扩展包：单兵 AI 方案讨论（未开工，只到方案层）

背景：修真包作者要做一个服务关卡/剧情模式的扩展包（boss + 仆从），
需要一个"按特定流程行动"的 boss。先问引擎支不支持兵种自带 AI。

### 查代码得到的硬事实（以后别再重查）

- **不支持兵种级 AI。** `ai.ts` 只有一套按**席位**算分的通用算法；兵种差异
  只来自属性 + 几条写死特例（英雄不吃战线、攻城器、慢甲近战守点、经济兵）。
- **AI 完全不认识修真包**：`ai.ts` 里没有任何 cultivation 字样，修士在电脑手里
  只会走过去平砍，不会施法。
- **AI 用技能是逐个写死的**：`heroSkillCandidate` 里 `switch (k.effect)` 只认
  throw-axe / regenerate / dive / cycle / descend / vanish / raise-dead 等，
  清单外一律不用。给 boss 配法术，AI 一门都不会放。
- **施法的门是通的**：走 `HERO_SKILL` 动作，`doHeroSkill` **不要求 def.hero**，
  冷却/充能/skillTurn/bornTurn/canCastSkill 全现成，扩展能 `registerSkillEffect`。
  缺的只是"谁来提这个动作"。
- **选招四道闸**（改单兵 AI 必须全部考虑）：
  1. 候选表全局扁平：所有兵 + 招募/建造/升级混在一张表排序；
  2. `best.v <= 0` → 返回 null（等于这一手什么都不做），局部分的零点必须对齐；
  3. 前 6 名（LOOKAHEAD_K）会被 applyAction 试走，按 `0.35 × 对手最狠一刀` 扣分
     —— boss 的"以伤换伤"会被这条削掉，需要豁免；
  4. 分差 1.5% 内按 aiNoise 随机挑 —— "必须做"必须给足分差；
  5. 深推 `PLAN_ON = false`（现在是关的），将来打开要重测。
- **约束**：AI 只看 `playerView`（雾图），单兵 AI 不能看全图；不能用 Math.random
  （回放重跑，只能 aiNoise）；`AI_MAX_STEPS = 50`，每步重建整张候选表 → 必须按
  「自主分>0 才跑」分流。
- 关卡事件**不能移动单位**（只有 spawn/say/doctrine/terrain/reveal/gold），
  所以"boss 走过来"必须写进扩展，不能只写关卡配置。

### 已倾向的结论（待作者最终确认）

- 核心加一层通用机制：兵种数据 `aiAutonomy`(0~1) + `aiProfile`（扩展注册的行为），
  扩展返回三样：**新候选**（法术/召唤，自带换算分）、**乘法加权**、**一条"必须做"**。
- **不要用分数相加**（全局分没有统一单位），用 `全局分 × (1 + 自主分 × 局部偏好)`。
- 默认值必须全 0，否则 208 场跑批基线作废、主线对局行为漂移。
- 只给 `level.units` 的关卡 boss 填值，普通兵种不动。
- 收敛方向：profile 内部写成**优先级列表/阶段机**，比加权平均可预测得多。

### 没解决的

- 单兵 AI 管不到席位级决策（造什么、打到哪、复活、换血）—— 这部分仍是空的。
- 高自主兵之间会互相拆台（各打各的），全局协同是这套 AI 的强项，别让普通兵开自主。
- 机制本体要写"改动清单"还没写；三步推进（一个兵+必须做 → 接真法术 → 跑批/回放断言）没开始。

### 追加（22:5x——已落成文档）

**决定：核心可以改，开始打地基。boss 数值/演出暂不做。**

查实的新事实：

- `CONFIG.maxUnits = 24`（config.ts:45）＋ 一个兵一回合「走一步+打一下」= 48，
  再加 2 招募 + 1 升级 + 建造/装配 → **后期满编局必然超过 `AI_MAX_STEPS = 50`**。
  这就是"50 步是历史遗留"的实证。跑批里早有 `capHits` 统计（evaluate-ai.ts:110），
  但历史结果没留逐局数据 → 动它之前要先量一遍。
- 深推 `PLAN_ON = false`（ai.ts:5735），现在是关的，不会翻案；将来打开要重测。
- 施法：`doHeroSkill`（rules.ts:7700）**不要求 def.hero**，冷却/充能/skillTurn/bornTurn/
  canCastSkill 全现成，扩展能 `registerSkillEffect`。缺的只是"谁来提这个动作"。

**接口最终形态（和口头讨论的差别要记住）**：不是「自主分×全局分」，而是
`add`（局部分，已换算成全局量级）＋ `must`（固定 1000）。乘法的方向是"自主分×局部分"，
因为跨量纲不能乘。理由写在 DESIGN 第 4.4 节。

### 阶段 0b：卡死检测（2026-11-18 01:2x 完成）

**为什么要有它**：`aiStepCap` 只保证"不会烧到天上去"，兜不住"这一回合剩下的人全都不动"。
病根是"成功但没进展"的动作（形态切换、开关姿态、塞船又拿出来）——每步都合法，
`rejected` 记不住（那张表只记被拒的），于是 AI 一直选、一直成功，把名额烧光。

**判据（故意窄）**：同一个动作 key 连续成功 且 局面指纹没变 → 计数 +1；到 2（第 3 次执行）→ 交棒。
- 不用"连续三步都没变化"：会误伤"三个兵依次进架势"（每人做的事不同，但指纹相同）。
- **指纹不含 `unit.custom`**：形态/姿态/层数都在那儿，算进去就永远抓不到形态切换。
  指纹只认站位/血量/moved·acted/单位数/金币/城/留痕/胜者。
- 只喂**成功**的动作；被拒的归 `rejected` 管。

**落地**：`ai-meta.ts` 加 `aiProgressFingerprint` + `aiStallGuard(limit=2)`；`ai.ts` 转出；
`main.ts` 每回合建 guard，成功动作后 note，判死则 `break` + `console.warn`（**不 return**，
这一回合还要交割）；`probe-ai-steps` 同步使用（测量口径必须等于实机）+ 汇总加"卡死"列。
`test-ai-optimization.ts` 加 4 条用例。

**验证**：AI 测试 53 项全过；2 局 120 回合卡死 0 次、步数与此前完全一致（527/511）→ 无误判。

**已知临时不一致**：跑批脚本仍用 `AI_MAX_STEPS`、没装 guard，靠 50 兜底。阶段 4 统一迁移时一起加。
