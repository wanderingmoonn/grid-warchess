## 桥的更正 + 编制注释清理 + 废墟安全闸（aiRuinSafe）

**更正**：桥是 `category:'building'`、`move:0` 的**建筑**（木 45 / 石 85 / 钢 140 金），
占一格水面、改地形；**被拆掉时**才还原，它不会自己走开。"人一走桥就塌"是我说错了。
5 格河 = 5 座桥建筑（+ 工人动作），不是吃 5 个兵。19 座桥 ≈ 1600 金建材。

**编制注释**：v3 已无编制上限，`ai-v3.ts` 里所有"编制上限 / 帽子 / 编制快满"的说法删掉；
"编制"在这个文件里现在只指**阵容档位**（tank/melee/ranged/siege）。

**废墟安全闸（`aiRuinSafe`，默认关）**：
- 三处都要求"抢下来守得住"，判据 `enemyThreatAt(废墟格).n === 0`
  （敌人移动力+射程，和"城下有人"同一把尺子，不新拍数字）；
- 接管分和坡度乘 `1/(1+接管次数)`；次数用 **`capturedTurn`** 数——
  不能用归属：废墟被打空不改归属，同一方能反复接管自己那座城（22 次里大多数是这种）。

**实测**：Q4|32|A 22 次 / 5924 金 → **4 次 / 1096 金**，261 平 → 87 胜（=基线）。
四组：基线 10-2-0/11-1-0；只开废墟闸 **0↑0↓（对基线 no-op）**；
三件套 11-1-0/4-3-5；三件套+废墟闸 11-1-0/**4-1-7**（叠在三件套上 **2↑0↓**，两局负→平）。

**教训**："修了一个 bug"要分清是"所有局受益"还是"给某个开关配套"——
废墟闸对基线逐局不变，只是等三件套把兵推到城下才显形。别拿它解释基线胜率。

## 方法论：防过拟合靠"影响面"（09:45）

用户担心 "照着 v3 那种'发现一个问题修一个问题'做，v4 也会过拟合"，并且想先做一批"基础操作题"
（该出经济还是军事 / 军事要地 / 别一个个送 / 经济兵先近后远）。

**我的结论**：
1. **分类错了**。v3 过拟合的根因不是"在实战里发现问题"，是**每次都用加一项分数来修**。
   换考题只换了"问题从哪来"，没换"怎么修"。**改机制会泛化，改数字只会拟合那道题。**
2. **"人类基础 ≠ AI 基础"这点用户是对的，但正确的分类不是"简不简单"**，而是
   **这条知识能不能写成机制**：
   - 能写成几何/规则（要地 = 删掉它路程变长；该撤 = 身价比 + 距离）→ 做成机制；
   - 只能写成偏好（先占近的再往外）→ 打分层的一条尺子。
3. **用户列的四个里三个已经有题**：S-009（经济 vs 军事）、S-005（要地，用行为考而非识图）、
   S-004（别一个个送）、S-006（站位）。**缺的不是题，是打分层那把尺子**。
   批量造"基础题"只会得到一堆重复的 S-006。

## 跨回合记忆（aiFocus.v4）+ 决定迟滞 + 编队 want/eta（10:30）

用户质疑我"记忆会污染存档/回放"的说法。查证后**我错了**：回放是 `stateAt(i)` 重放录好的动作
（`main.ts:1859`），不重跑 AI；`aiFocus` 只是随 state 一起存的数据。
真正的代价只有：存档变大 + 旧记忆被新代码用新语义读（v3 靠"只在 ai-v3.ts 读写"这个约定）。

但**记忆确实该有**（用户对）：v1 的短视就是"每手重算"。v3 的注释里有实测——"判决 4 局翻 128 次"。

**落地方案（与 v3 的区别在"存什么"）**：
- `GameState.aiFocus[p].v4`：只存**承诺**（decision: kind/cityId/since/untilTurn）与**事实**（squad: formedAt/want）；
- **单一写入点** `writeMemory`（对应 v3 的 `setFocus`），存的是决定与事实，不是中间缓存（v3 的 plan/squads/keep 那种）；
- 读写走**真状态**：`currentView` 里的 view 是 playerView 副本，写副本等于没写（下一步 applyAction 就换对象）；
- 迟滞：press 持续到 untilTurn，兵力比跌破 1.0 提前收手；defend 到 foeStr<myStr*0.6；expand 到 ratio≥1.25；
- 编队 `want` = 目标城守军身价 ÷ 我方平均身价 × 1.5（夹 4~12），成立时定下、12 手内不因伤亡而缩；
- 出发条件 = 人数 ≥ want 或 eta80 ≤ 1（纯几何，不需要记"我等了几回合"）。

**试错**：先写成"两回合内到城下的人 ≥ want"→ 循环条件（到不了城就永远不出发），
S-000 从绿变红、S-005 过河 4→3。撤回。

**成绩：0 道题变化**（exams:all --diff 说"一道题都没动"）。按判据这是"没生效"——
因为它是**基础设施**（给后面的长期行为打地基），不是修复。

**顺手定位了 S-002 的真问题**：不是队形。v4 的兵距城**卡在 4~5 格不再前进**，
每回合只打 0~2 次，而 v3 能打到 32~34 城伤。所以 S-002 卡的是"突不破 12 个 4 代步枪兵阵"，
不是集结。下一步该做**集中火力**（打同一目标），不是继续调队形。

## 集火（约束层）+ 两个硬 bug：S-001 变绿（10:40）

用户问"集火该放打分层还是约束层"。**决定放约束层**，三条理由：
1. "全体打 X"的真含义是"不许各打各的"——是约束不是排序；
2. 放打分层会逼出坏结构：每个单位各算"打谁划算"，加总必然分散；要收敛就得让单位互相知道
   别人在打谁，打分层就变成有状态的协调器，废掉"一个单位一步、只看自己"；
3. 用户"从上面发下来"的直觉，在架构里就是"每回合只决策一次"= 约束层。
落地：`Squad.focusId`（约束层选，一把尺子：这一手能不能打死它，能打死的挑血最少），
打分层只执行（排在攻城之后、乱打之前）。

**集火本身没让 S-002 动（0 城伤），但顺着它挖出两个硬 bug：**

1. **让位计划的落点是拿缓存局面算的**：轮到第 8 个单位时，前面的人已经占了那格，
   于是每回合被引擎拒 **20 次**（"目标格不可达"），动作预算全烧在这上面。
   → 改成"计划落点只当方向，用当前局面重挑可达格"。拒绝数降到 0~3。
2. **走过路的单位被禁止再攻击**（`live.moved` 也跳了）。引擎只要求"这回合没攻击过"，
   走过照样能开火。等于每个兵每回合只能走或打二选一，**火力砍半**。
   → 只跳 `acted`。**S-001 因此从红变绿**（v4 第一次过"该赢必赢"）。

**矩阵**：v4 过 4 道（S-000 / S-001 / S-005 / S-009），超过 v3 的 3 道。
`--diff` 只报 1 处变化并提示"先假设是补丁"——但这次是两处正确性修复（其中一处还降了拒绝数），
不是调参。

**S-002 仍未过**。诊断：30 个兵**卡在距城 4 格**，12 个 4 代步枪兵（射程 4）把城围成一圈，
进不到攻城距离（3 格）也吃不掉他们。不是队形问题，也不是集火问题——需要真正的突破战术，
或者这道题的线对"没有协同概念"的 AI 本来就不可达。
