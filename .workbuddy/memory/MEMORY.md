## 太空战争：战斗口径（2026-11-12 P2f）

- **材料研究室**改回普通 `modifyArmor`：它的加成本来是给**地球**部队的，
  站内被「恶劣外空环境」÷5 吃掉是对的。`postHazardArmor` 钩子已删，
  别再"为了不被除"把它挪到环境之后。
- **敌方空间站只公开外形**（甲板/破口），舱段靠 `hideUnit` 钩子整块不下发，
  只有核心舱例外。`fog.playerView` 里活单位、ghosts、`memory.known` 三处都要过。
- 轨道轰击是**跨图盲打**：选一格，空甲板 → `wreck`，有舱段 → `computeDamage`。
  核心舱那一格连可点格都不给。
- **核心舱死 ≠ 站消失**：`StarStation.ruin`（3 个原主回合）→ 站上任意单位付
  `200+60×规模` 接管；到期 `removeStationBoard` 连人带舱段一起删。自拆走同一条。
- 废墟不逐处判：`stationPower` 对废墟直接 `brownout`，全站停摆一次到位。

## 架构与坑

- **移动是瞬移结算**：`doMove` 直接改坐标，没有路径记录。要按"路过"判定必须
  给 `reachableTiles` 补父指针再回溯。目前相关规则（反应射击）一律按**落点**算。
- **`s.cities = []` 会让引擎把该席位判为出局**，`END_TURN` 转一圈回到同一个人，
  守方永远轮不到回合。做脚本对局时城市要留着，只把战场挪到无城横带。
- **`placeUnit` 是纯函数**：新单位在返回的 state 里，不改入参。
- **跑批**：单次 60 局会被系统杀；20 局一批、串行连跑多批稳定（约 7 分钟/批）。
  两个进程并发约 24s/局，四个并发反而拖到 2 分钟/局。
- **`node_modules` 是符号链接**，`.gitignore` 里必须写 `node_modules`（不能带斜杠，
  带斜杠只匹配目录，符号链接漏网，合并时会把它提交进库）。
- 仓库会自动 push：提交后 `origin/<branch>` 可能已经更新，不用手动推。

## 关卡模式（2026-11-15 告一段落）

**接手先读 `docs/STATUS-LEVEL-MODE-2026-11-15.md`**——能力清单、三张关的当前配置、
七条坑、没做的、怎么验。写关卡看 `GUIDE-LEVEL-AUTHORING.md`，历史决策看
`PLAN-LEVEL-MODE-2026-11-14.md`（顶部有导航，标明它是历史）。

**最重要的三条结论**（都花了好几轮才认下来）：
1. **AI 不会自己渡河进攻**——投送是硬伤（过河的兵堵桥头、大部队卡在窄桥），
   调 `riskAversion`/`cohesion` 只能让它多过去一两个。要压力就用事件把兵送到对方那侧，
   且**必须从地图边缘进场**（直接刷在身边＝玩家觉得 AI 耍赖）。
2. **`spawn` 落点被占会静默不刷**（现在改成半径 1~2 就近找位）。
   作者的坐标是"大概位置"，波次重叠就会大量失败而没人知道。
3. **难度不来自数值**，来自"有没有安全位""有没有必须回应的威胁""玩家能不能看见发生了什么"。

**存档**：`config.level` 是整包快照，改关卡不影响旧存档（自洽）。想看新版开新局或 `?fresh=1`。
**别做"关卡变了就丢存档"**——那会连「继续上一局」和配置记忆一起干掉。

**测试**：`npm run probe:level`（26 段）比整套 test 快得多，第 1 段逐条列关卡校验错因。
探针断言不许钉死具体数值（时间/地形/阵容），要么读事件数据，要么退回结构性要求。

## 单兵 AI / 自主分（2026-11-17 立地基，未开工）

**先读 `docs/DESIGN-UNIT-AI-2026-11-17.md`（清单/接口/12 条红线）+ `PLAN-UNIT-AI-2026-11-17.md`（四阶段）。**

方向：核心加一层通用机制，`UnitTypeDef.aiAutonomy`(0~1) + `aiProfile`（扩展在 `Expansion.unitAi` 注册），
扩展只返回两样：`add`（自己想的动作，分数已换算成全局量级，生效分＝自主分×分）和 `must`（一回合一条，固定 1000）。
**不要用"自主分×全局分"**——全局分没有统一量纲；乘法只能发生在"已换算的局部分"上。

四条不许忘：默认全 0（否则 208 场基线作废）；只给 `level.units` 的 boss 填值；
handler 只拿 `playerView`（不能看真局）；不许 `Math.random`、不许副作用。

**50 步上限已拆（2026-11-17 阶段 0 完成）**：主流程改用 `aiStepCap(s) = 8 + 6×本单位数 + 6×本城数`
（每兵 6＝走一步+最多 4 段 burst+技能）。**实测 18 局：平均 8 步/回合、最大 23、撞上限 0 次**
——"24 兵×2=48 必然爆"是推错的，AI 在 `best.v<=0` 时就收手。所以这次改动是行为空操作，
拆它的理由在将来（单兵 AI 会推高步数）。**`AI_MAX_STEPS` 没删**（`scripts/baselines/*` 与四十多个脚本 import 它）。
测量工具：`npm run probe:ai-steps`（同种子跑两档并排对比）。

**卡死检测（阶段 0b 已落）**：`aiStallGuard` + `aiProgressFingerprint`（`ai-meta.ts`）。
判据是"同一个动作 key 连续成功 + 局面指纹没变，第 3 次交棒"——**不是**"连续三步都没变化"
（会误伤三个兵依次进架势）。指纹**不含 `unit.custom`**，否则形态切换这类空转永远抓不到。
只喂成功的动作。跑批脚本还没装（靠 50 兜底），阶段 4 一起迁移。

**阶段 1 骨架已落（2026-11-18）**：`UnitTypeDef.aiAutonomy` / `aiProfile` +
`Expansion.unitAi` + `core/unit-ai.ts`（注册表、白名单、`UNIT_AI_MUST_SCORE=1000`）。
转化在 `ai.ts` 的 `unitAiCandidates()`；`Candidate` 多了 `ignoreRisk`（`must` 恒为 true）。
探针 `npm run probe:unit-ai` 已接进 `npm test`，5 段：零变化 / 未注册 / 白名单 / 清单。
**验收硬指标是"自主分 0 或 profile 返回空时，动作序列逐条相同"**，现在两档都验过。

**阶段 2 三道门已过（2026-11-18）**：`probe:unit-ai` 第 5 段用手工小局面（不建 dev 关卡）

## 「黑暗动乱」扩展（2026-11-18 最小可跑版）

**核心设计**：尸骸仙帝超越九级修士但**会老**（修真包最高 9 级）。平时在沉眠地延缓衰老
（平时 +2 岁/回合、沉眠地 +1），寿元将尽出山屠杀换寿元，缺食物时吞自己人（从低级往上）。
单位分仆从/诡异，全部只能关卡生成。

**三个不许改错的决策**：
1. **不走修真境界系统**——`MAX_RANK=9` 且 9 级寿元 Infinity，塞第 10 级会牵动
   属性公式/经验墙/规则书/平衡。boss 不是修士兵种，直接给固定值。
2. **年龄用核心的 `u.age`**（核心每回合 +1），本包只在"不在沉眠地"时再 +1。
   不要改核心年龄规则，也不要倒扣。
3. **寿元存 `custom.lifespan`**：修真包 `isDoomed` 只对修士生效，所以判死得自己做。

**入口**：`dark-turmoil-packs.ts`（兵种/技能/钩子）、`docs/DESIGN-DARK-TURMOIL-2026-11-18.md`、
`npm run probe:dark-turmoil`（26 条）、关卡 `level:dark-turmoil`。

**实测**：关体 40 动作内仙帝吃 1 次（200→210 寿元），但把玩家清场——占位数值必然如此，
这关现在只是"循环跑得通"的证据，不是难度关。

**暗影领域已实现（2026-11-18）**：`UnitTypeDef.shadowRadius` + `GameState.overlays.shadow`。
每回合末整份重铺（不跟随移动），站在里面视野/射程减半向上取整；严格超过一半才触发。
**`modifyVision` 里绝不能再调 `visionOf`/`playerView`（死循环）**，只能用 `base`。
探针 `npm run probe:shadow`（8 段）。

**影系三兵已跑通（2026-11-18）**：蚀影（贴暗影边）/ 暗影（同类散开、击杀原地生蚀影）/
影主（不贴身、计时器召唤暗影，攻击过更快）。真伤叫**暗蚀**，走 `DAMAGE_STAGE.trueDamage`。
**坑**：包内不能 import `unit-ai.ts`（它顶层读 EXPANSIONS → 循环），
必须走 `Expansion.unitAi`。`UnitAiCtx` 现在带 `foes`/`allies`。探针 `npm run probe:shade`（50 条）。

**影系第二轮（2026-11-18）**：目标偏好（蚀影扑落单 / 暗影补刀 / 影主打威胁最大）；

## 协作约定

- 判断类结论要有实测支撑（真跑 `applyAction`，别只看配置表）。
- 报告要写清"没做什么/样本多小"，别把方向性结论写成定论。
- **跑批对照必须用 `--old ./baselines/ai-9efb961.ts`**（与 `results/bench/bridge-clear.json` 同对手）。
  用"自己前一版"当 old 等于新 vs 自己，胜率必然 ~50%，会得出反向结论——
  2026-11-21 因此连续四轮误判"扫描有害"。跑批前先验证基线版能逐局复现。

- **评价 AI 改动不能只看胜率/平局率**（2026-11-22）：胜、负、平三个出口要一起看，
  主指标是配对方向。平局↑ 但败率↓、胜率不变 = 改善（少输）；平局↑ 且败率不变才是变保守。
  阶段 1b 就是例子：平局 8%→17%，但配对 2↑0↓、两处「负→平」，属改善。

## v3 的硬前提（**先读 `docs/V3-INVARIANTS.md`**）

- **v3 没有单位编制上限**：`CONFIG.maxUnits=24` 是 v1 的帽子，不是规则。2026-11-22 已删
  `unitCapOf` / `swapOutCandidate`（换血整套）/ 采购"编制已满" / `SWAP_GAIN`。
