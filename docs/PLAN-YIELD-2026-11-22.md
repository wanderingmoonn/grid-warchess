# 让位：统一占位重排（2026-11-22 立项）

> 一句话：**三类让位是同一个问题——把「洞」搬到关键格上**。
> 现在有四套互不相干的机制，都只在"防"、不在"治"，而且 C（经济外迁）完全没做。

相关：`docs/V3-INVARIANTS.md`（硬前提）、`docs/V3-BACKLOG.md` P0-5、`docs/AUDIT-SOLVERS-2026-11-22.md`（`econUntil` 无消费者）。

## 一、现状：四套机制，各管一段

| 场景 | 机制 | 触发条件 | 手段 | 实测效果 |
|---|---|---|---|---|
| A 军队堵桥位 | `bridgeClear`（`ai-v3.ts:4286`） | `needBridge`（陆路真不通） | 桥点 5×5 内"走进"−32 分，**已在里面不罚** | Q3/seed30 261 平 → 87 胜，桥 9→16 |
| A' 渡口整体拥堵 | `bridgeJam`（`:3354`）+ `crossingAlt`（`:3400`） | 连续 3 回合半径 3 内 ≥10 兵或 ≥2 编队 | 一支编队改走第二渡口（≥6 格），锁 10 回合 | Q3 一局平→胜 |
| B 城格被占（军队侧） | `chokedCities`（`:9602`）→ 战斗单位出城 +150（`:6514`） | **产兵格 = 0** | 奖"从城格走出去"一步 | 修掉 seed32 死锁（t81 起两城产兵 0、140 回合零兵） |
| B' 城格被占（经济侧） | `buildYieldChain`（`:2548`）+ 回合级 `yieldChain`（`:9540`） | 产兵格 **< size²** | 从城格 BFS 半径 8 找**最远空地**，回溯成链，逆序执行 | `probe:yield` 4/4（0→4）；`probe:yield5` 25 全移；Q1/Q2 无副作用 |
| C 经济外迁优质地 | **无** | — | — | — |

### 四个缺口

1. **A 只防不治**：`bridgeClear` 注释写明"已经在里面不罚"。大军已经堆在桥头时它不起作用——
   那正是当初 261 回合平局的样子。
2. **B 两套方向相反**：`chokedCities` 让**军队出城**（军队给产兵让位），而实际需求是
   **经济给军队让位**（城周被经济占满，军队出不去）。且 `chokedCities` 只认"产兵格 = 0"，
   军队出了第一格、城外又被占时它不解决。
3. **C 完全没有**：代码里没有任何"经济单位往哪站"的评分（`economicYield` 只用于识别敌人/骚扰）。
   先出生的永远占着城格和近郊，后出生的只能往外挤 → "优良地形被占满"是必然。
4. **三套都是反应式**：`power-solver` 的 `econUntil` 能算"未来该投多少经济"，消费者 **0 个**。

### 为什么"打分"走不通

候选系统的架构是「每单位独立生成候选 → 全局 argmax」。**分数只能排序，不能排除**。
让位要表达的是"这几格必须空出来 / 必须由某角色占"，那是**约束**。
`chokedCities` 给 150、`buildGuide` 给 20/格 硬压，都是在打分值战争，而分值的上限由当回合最高分决定。
核心其实有表达"必须"的口子（`Candidate.must` = 1000），但语义是**一回合一条**——让位天然需要一次多条。

## 二、统一抽象：两层

```
关键格 K + 应占角色 R(k) + 当前占位者 O(k) + 洞 H（可站空地）
约束：一格一人、移动串行、每步目标格必须空
```

三类场景只是 K 不同：

| 场景 | 关键格 K | 应占 R | 占位者 O |
|---|---|---|---|
| A | 桥位 / 桥点 5×5 | 工程队 | 战斗单位 |
| B | 城格 / 产兵格 | 新兵 | 经济 · 建造 |
| C | 城格（要留空） | 新兵 | 经济（**目标是优质槽位**） |

**层 1 可行性（硬）：洞搬迁**
```
minimize  Σ w(k) · cost(k, h)        k∈K 按紧急度加权
s.t.      每个 k 至少一个洞；洞不够按 w(k) 排队，绝不静默死锁
          cost = 地形代价下的路径长（用 distanceFields，不用曼哈顿）
输出      一组 (unitId → 下一格)，沿路径逆序执行
```
没有洞 = **无解**，唯一出路是"制造洞"（单位走到半径外空地）——**这正是 C**。
所以 C 不是第四件事，是 B 无解时的唯一出口。

**层 2 最优性（软）：位置指派**
```
maximize  Σ [ yield(tile) − λ · travelCost(unit, tile) ]
s.t.      关键格不许占；一格一人
```
这一层顺带回答"**谁**该让位"：不是"任何经济单位"，而是搬运最便宜的那个。

**两层必须联立**：层 2 的指派决定洞在哪里分布。分开做 = 清完又堵，就是 HANDOFF 待办 1
那个"T4 占 4 → T12 降到 2 → T28 回到 3 → T36 回到 4"。

**实现上的关键手段**：从**所有洞**出发做**一次多源 BFS**，得到"每格到最近洞的距离场"，
所有关键格查表 O(1)。"整排外推"与"洞内滑"是同一件事的两个视角。

## 三、分步计划

### 第 0 步：量现状（两个探针）· 本次做

- **做什么**：`probe:bridge-block`（军队堵桥点）、`probe:combat-trap`（军队被经济围死）。
- **解决什么**：把"只防不治"和"军队被围无解"从推测变成实测数字，作为后续所有改动的对照。
- **怎么验收**：
  - 两个探针各自能独立跑通，输出「关键格状态 / 动作序列 / 判定」；
  - 判定必须来自**动作序列**（谁动了、动了几次），不是靠读配置猜；
  - 结果记回本文档第四节。
- **红线**：探针不断言"必须解不开"（修好之后会红），只打印结论。

### 第 1 步：关键格表（纯重构，零行为变化）

- **做什么**：定义 `SlotPlan`（关键格清单 + 紧急度 + 应占角色），把四套机制的"关键格来源"
  收敛到一处计算，`bridgeClear` / `chokedCities` / `yieldChain` 改成读这份表。
- **解决什么**：A/B/C 各算一套的问题，以及"多城只处理第一座城"（现在是 `find` 第一个）。
- **怎么验收**：**`probe:ai-goal` 四种子指纹逐字不变**（本项目对纯重构的硬口径），
  外加 `probe:yield` / `probe:yield5` 输出一致。
- **风险**：这一步最容易"顺手改行为"。任何指纹变化都当错误处理。

### 第 1 步：关键格表（纯重构）· ✅ 已完成（2026-11-22）

**做了什么**

- `SlotPlan` / `CriticalCell` 两个类型 + `buildSlotPlan(view, me, bridgeSite)`：
  产兵格全占的城、产兵格没满的城、桥点 5×5、以及"被占住的产兵格"清单，
  **一次算完**，成为三类让位关键格的唯一出处。
  位置：`ai-v3.ts` 里原 `spawnCellCountOf` 那一块。
- `Fields.slots` 新增；`fields.chokedCities` / `spawnStarved` / `bridgeClear`
  改成从 `slots` 取，取值逐字不变。
- `bestBridgeSite` 从"算两遍"（fields 一次、`bridgeClear` 立即函数一次）变成一遍。
  纯函数、同一个 view/wade，结果必然相同；省一遍全图扫描。
- `buildYieldChain(view, me, slots)` 用 `slots.starvedCities` 找"城格上有经济/建造单位的城"，
  顺序与 `citiesOf` 一致（`buildSlotPlan` 顺着它 push），所以仍是同一座城。
- 删掉 `spawnCellCountOf`：被 `buildSlotPlan` 完全覆盖，留着就是两份口径迟早漂。

**没做的（明确留给后面）**

- `critical` 只有数据、**没有消费者**——第 2 步的洞搬迁才读它；
- "多城只处理第一座城"仍在：`yieldChain` 还是只建一条链（第 3 步）；
- 桥位仍是"软区域"（`bridgeArea`），没进 `critical` 硬格——桥点本身是水格不能站人，
  真正要空的是施工位，第 2 步再定它的约束形式。

**验收：四个种子指纹逐字不变**（外加四个让位探针输出一致），详见第六节。

### 第 2 步：洞搬迁求解器（层 1）

- **做什么**：多源 BFS 距离场 + 关键格按紧急度匹配洞 + 输出有序移动链；支持多城、多关键格。
- **解决什么**：A 从"只防"变"能清"；B 从"只认产兵格=0"变成"没满就排"；
  `buildYieldChain` 的"只挑一座城、一条链、找最远空地不看地形"一起换掉。
- **怎么验收**：
  - 第 0 步的两个探针从"0 动作"变成"N 回合内解开"（N 记进文档）；
  - `probe:yield` 4/4、`probe:yield5` 25 全移**不退化**；
  - 跑批 Q1~Q4 配对不出现净负（单批 12 局，两批 24 局）。
- **风险**：桥点 5×5 是**软区域**，城格是**硬格**——层 1 里必须区分"必须空"和"最好空"，
  否则兵会在桥头来回挪（44.6 那次 58%→38% 就是这么来的）。

### 第 3 步：多链调度与同回合重算

- **做什么**：链空即重算（去掉 `yieldTurn` 的挡板），多条链并行且互不抢目标格。
- **解决什么**：HANDOFF 待办 1 的"让位与经济出生拉锯"（一回合只清一列）。
- **怎么验收**：构造局面（4 条链清 4 格）能**同回合**完成；
  实战回放里城格占用单调不回升（T4/T12/T28/T36 那四个采样点）。

### 第 4 步：位置指派（层 2，C 场景）

- **做什么**：经济单位 × 空地的最小代价指派，收益 = 地形产出 − λ·迁移代价；
  带"值得搬"阈值与迁移罚分（防抖）。
- **解决什么**：C 完全缺失；同时让"谁让位"由代价决定，而不是写死"经济/建造都行"。
- **怎么验收**：新增 C 探针（城周一圈被占、外圈有高产出空地）里，经济单位主动外迁到产出更高格；
  跑批 Q1/Q2 不掉。
- **风险**：AI 只看 `playerView`，半径外的地块没探明 → 收益估计带噪声 → 目标会抖。
  必须靠迁移罚分压住，不能指望机制自己稳。

### 第 5 步：前瞻（采购 × 占位）

- **做什么**：把 `econUntil` / 采购计划接进关键格表——未来 N 回合要出生多少单位、占哪座城的格。
- **解决什么**：反应式 → 预防式（提前外迁，而不是堵了再清）。
- **怎么验收**：城格占用率（`spawnCellCountOf` 的平均）下降，且跑批不掉。

### 第 6 步：候选系统支持"一组有序动作"（按需）

- **做什么**：让 `must` 能一回合多条（按链顺序逐条生效），或引入显式的"计划组"。
- **解决什么**：现在的绕法（把链头伪装成普通候选）在链变多、变长之后撑不住。
- **怎么验收**：链长 > 5 时同回合走完；`probe:unit-ai` 的 `must` 契约不变。

## 四、第 0 步实测记录（2026-11-22）

两个探针都已落地：`npm run probe:bridge-block`、`npm run probe:combat-trap`。
断言口径按红线第 2 条：只打印结论，不钉死"必须失败"——第 2 步修完之后它们应该变绿。

### 探针 1：军队堵桥点（`probe:bridge-block`）

局面：12×12，河在 x=5（y 3~8 是水，上下用山封死，陆路真不通）；桥点 **5,5**；
工人退到 **(0,5)**，距桥点 **5 格**（造桥半径 `buildRange(2)+2 = 4`，差这一步就够不到）；
我方岸上距桥点 ≤4 格的格子**全部塞满战斗单位（35 个）**。

| 回合 | 工人距桥点 | 身边空格 | 5×5 内战斗单位 | 我方桥 |
|---|---|---|---|---|
| 起始 | 5 | 2 | 10 | 0 |
| 1~10 | **5（一步没动）** | 2 | **10 → 10（一个没让）** | **0** |

**判定：堵死。** 工人 10 回合里一格都没挪，一格桥面都没铺，军队也一个没让。
注意"身边空格 = 2"：它不是物理上寸步难行，而是**能走两步又被挡住**——正是"需要别人让开"的形状，
而 `bridgeClear` 不驱赶已站在 5×5 里的兵。

### 探针 2：经济围死城（`probe:combat-trap`）

局面：12×12，城在 (4,4)；**城格 2×2 四格全站战斗单位**（产兵格 = 0）；
城周围两圈塞 32 个经济单位（城格不放）。这样 `buildYieldChain` 的前提（城格上有经济/建造单位）不成立，
`chokedCities`（产兵格 = 0）成立但出城邻格全被占。

| 回合 | 我方动作 | MOVE（战斗/经济） | 最远战斗单位离城 |
|---|---|---|---|
| 1~8 | **0** | 0 / 0 | 0 |

**判定：完全死锁。** 8 个回合我方一个动作都提不出来：城格四格被自己人站满、
出城邻格又被经济单位占满，`chokedCities` 给的 +150 找不到落点，
`buildYieldChain` 又因为"城格上没有经济/建造单位"不触发。

### 两个数字放在一起看

| 场景 | 现状 | 问题性质 |
|---|---|---|
| A 军队堵桥点 | **永远解不开**（10 回合 0 进展，军队 0 让步） | 缺"驱赶已在场者"，`bridgeClear` 只管新进入 |
| B 经济围死城 | **永远出不来**（8 回合 0 动作） | 两条机制都不覆盖这个局面，没有任何一方会主动腾位 |

### 一个差点被当成"让位生效"的假象

探针第一版（没围住对手的兵）跑出来是"停摆 4 回合、第 7 回合出城"，看起来像机制在慢慢起效。
查下去发现：**那是对手的兵走过来，把农民"吓跑"了**。`tacticalMoveScore` 里经济单位有一条
躲威胁（`(currentThreat.damage − futureThreat.damage) × 2`），农民一被吓就往反方向跑，
正好让出一条路——和"让位机制"毫无关系。

验证方法：给 `ai-v3.ts` 临时加一行打印候选最高分（`AI_DBG=1`），看到第 9 回合
（A 的第 5 回合）跳出 `22.5` 分的 `farmer:MOVE`——那是逃跑，不是让位。
把对手那只兵用山围死之后，8 回合 0 动作，真相就出来了。

> 口径备注：两个探针都把我方的钱也每回合清空。不清的话我方会在城内攒钱造兵
> （实测 B 场景多出 2 个兵），产兵格跟着变，就分不清"让位"和"新兵占位"了。

### 构造探针时踩的三个坑（别再踩）

1. **把钱清零会让对手出局**：`checkWinner` 判"没兵 + 造不起"即出局，对局第 1 回合就结束、
   后面什么也测不到。必须给对手留一个兵。
2. **多留敌城，对手会自己架桥过河**（实测第 7 回合真在 5,4 铺了一格桥面），
   把"我方工人被堵"的观察搅浑。双方各留一座城。
3. **`s.unitTypes[type].bridges` 查不到桥**——桥是建筑，不在"这一局启用的兵种表"里。
   判"有没有桥"要用 `type.startsWith('bridge')`，否则会把造出来的桥漏成"没造"。
4. **对手的兵不能让它乱走**：它一靠近，经济单位就会"逃跑"（躲威胁项），
   看起来像让位。要么围死，要么每回合清空它的钱+资源（见上面那个假象）。
5. **统计动作要按 owner 过滤**：第一版没筛，把对手在右下角调度自己的农民
   也记成"我方经济单位开始让位"了。
6. **给钱要挑时机**：预热阶段给钱，工人第 1 回合就把桥造好、计划 `done` 退场，
   探针拿不到桥点（`probe:bridge-block` 踩过）。

## 五、红线（每次改动都要过一遍）
1. **一次只改一处**（44.6 的教训：三处一起改 → 38%，四轮二分才定位）。
2. **探针断言不许钉死具体数值**（时间/地形/阵容），只做结构性要求。
3. **不改核心规则层**：让位是 AI 层的计划，`rules.ts` 不动。
4. **跑批对照只用 `--old ./baselines/ai-9efb961.ts`**，不用自己前一版。
5. **别用 `s.cities = []`** 造局面（引擎会把席位判出局，守方拿不到回合）。
6. **探针不许 `Math.random`**，随机性从种子派生。

## 六、纯重构的护栏：指纹基线

任何声称"零行为变化"的改动，都用这一套对照。**基线是"当前代码 + 当前数值"**，
所以每次合并 main、或改了平衡数值之后都要重跑一遍——旧指纹会整体漂，别拿去比。

基线（2026-11-22，合并 main `0bc27a2` 之后）：

| 种子 | 步数 | 指纹 |
|---|---|---|
| 11 | 721 | `a2795f65a6e2` |
| 22 | 933 | `ab20edd69085` |
| 33 | 700 | `c1ea93b65154` |
| 44 | 703 | `b6ecaf01bbf0` |

外加四个让位探针的输出（第 1 步验收时逐条对过）：

| 探针 | 基线输出 |
|---|---|
| `probe:yield` | 链后产兵格 **4** |
| `probe:yield5` | **25 / 25** 个农民动过 |
| `probe:bridge-block` | 工人距 **5→5**、5×5 内 **10→10**、桥 **0** |
| `probe:combat-trap` | **8 回合完全停摆**、一次没出城 |

第 1 步（关键格表）就是拿这张表验的：四项全同，`test:rules` 1005 项、
`test:ai-optimization` 60 项、`probe:unit-ai` 全过。
