# 2026-10-30 · 两条：聊天只到一半、军营扎不进桥头

两条都是"看起来像网络/像随机"的问题，实际各有一个确定的成因。

---

## 1. 聊天：对方只收到一部分

拆开看是三个独立的洞，都能让同一句话在对面变成残句。

### 1.1 水位被自己发的那条推走了（真丢消息）

拉新消息是增量拉的：`id > 上次拉到的最大 id`。所以那个"上次"必须来自**服务器**。

以前 `pushChatLine` 收一行就把水位推到这一行的 id，**包括自己刚发出去的那一条**。于是：

```
我上次拉到 99
  对方发了 100（我还没轮询到）
  我发了一条 → 服务端给它 id 101 → 界面立刻把水位推到 101
下一轮问 id > 101 → 100 永远拉不回来
```

对方那句只在我这儿没了，在他那儿好好的。刷新一次又全都在（重新从 0 拉），
于是很容易被归到"网络不好"头上。两个人几乎同时说话就会踩到——而联机对局里，
几乎同时说话恰恰是最常见的情形。

**修法**（`src/net/chat.ts` 新增 `ChatFeed`）：水位只由服务器返回的那一页推，
自己那条走 `adopt()`——只显示、**不动水位**。下一轮照样会把它拉回来，按 id 去重。
`pollChat` 里是唯一推进水位的地方：

```ts
const fresh = chatFeed.accept(res.lines);  // 水位 = 这一页的最大 id
```

顺带修了一处观感问题：自己那条是"先显示、后拉回"的，可能比夹在中间的那条
（别人的、我还没拉到的）先到，所以收进来之后按 id 排一次序——同一间屋子里
id 就是先后，排序＝按时间线。不然会看见"我的回复排在对方那句前面"。

### 1.2 输入法组字中按 Enter，发出去的是半句话

中文一句话要打几个字才组成词，按 Enter 是**选词**。那一刻输入框里只有已经上屏的部分，
剩下的还在输入法里。不拦这一步，选词那一下就触发了表单提交，发出去的是半句——
而发的人以为自己发的是整句。

浏览器对"组字中按 Enter 该不该提交表单"处理不一致（Chrome 拦、Safari 放行），
所以不能赌默认行为：自己记一个组字状态，`compositionstart` 置位、`compositionend` 清位，
组字中不发送。另有一条兜底——某个环境不发 `compositionend` 时，下一次"不在组字中的按键"
把状态清掉，免得这个人从此再也发不出消息。

（`src/ui/chat-input.ts`，抽成函数是为了能在 jsdom 里真的派发事件来测；
参谋部搜索框那边早有同类处理，只解决"组字中不重建输入框"，管不到提交。）

### 1.3 超长消息被静默截断

`<input maxlength>` 是输入框自己在拦，但输入法（以及某些粘贴）并不总是听话。
以前超了就直接 `slice(0, 120)` 发出去：发的人看到一整句，收的人看到半句，两边都不知道。

现在发送前先问一句 `chatBodyOverflows()`，超了**不发**、把字留在框里并说明：
"太长了，最多 120 字（现在 N 字）。拆成两条发吧，字还留在框里。"
宁可拒发，也不让对面读到半句话再回你。

## 2. 军营：扎不进"有桥的水边"

**根因**：`requiresWater` 的判定自己写了一遍"四邻有没有水"：

```ts
DIRS.some(([dx, dy]) => tileAt(s, tx + dx, ty + dy)?.terrain === 'water')
```

而桥那一格的地形是 `bridge`（见 `rules.ts` 架桥那段 `tile.terrain = 'bridge'`）。
所以"岸边那格水架了桥"之后，岸上这格就**不临水**了，回一句"必须扎在水边"。

规则书里写的一直是"四邻还要有一格水面（**桥面也算**，桥下就是河）"——
文档没错，是代码和文档不一致。而且界面上的建造高亮用的是 `adjacentToWater`（认桥面），
于是一路高亮成可建，点下去才被拒：最容易让人以为"是不是我没钱/没行动力"。

**修法**（`src/core/rules.ts`）：判据改走 `adjacentToWater`，不再自己写一份。
那个函数的注释本来就写着"地图生成、AI 选址、界面高亮都要用同一套口径，各写一份必然走偏"——
这次是核心自己走偏了。

**顺带**（`src/main.ts`）：界面高亮那一份判据整段删掉，改成问 `buildSiteError`。
以前那里是第二份实现（地形、桥要两侧有陆地、军营要临水），每条单看都对，
但和规则是两套代码，改一处忘一处就会再出现"高亮了、点了却被拒"。现在高亮的含义
由构造保证："点下去一定建得成"。

开销：32×32 全图问一遍 `buildSiteError` 是 **0.39ms**，而且只在选中建造单位时才跑，
比它替掉的那段循环贵不了多少。


新增的用例：

- `聊天水位只由服务器推：两个人同时说话不能丢`——重放上表那个时间线，
  断言 `adopt` 之后水位仍是 99、下一页能把 100 捞回来、101 不会重复显示。
- `超长消息不发出去，而不是截一半发出去`——含"首尾空白不占额度""换行先压平再算"。
- `军营能扎在桥头：桥面也算临水`——并**反向**断言"一格水都没有时仍然不许扎营"，
  免得放宽成随便扎；同时断言界面用的 `adjacentToWater` 也认桥面。
- `输入法组字中按 Enter 只选词，不发送`（jsdom 派发 `compositionstart` / `submit`）。

变异验证（都已还原）：

| 变异 | 应该红的那条 | 结果 |
|---|---|---|
| 临水判据退回 `terrain === 'water'` | 军营能扎在桥头 | 红（回显"军营必须扎在水边"，正是玩家看到的那句） |
| `adopt()` 重新推水位 | 聊天水位只由服务器推 | 红（"自己发的那条不能推水位"） |
