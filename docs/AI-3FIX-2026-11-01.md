# AI 三类问题修复：建造 / 选卡 / 交战（2026-11-01）

承接 `ANALYSIS-AI-2026-11-01.md`。那份体检的结论是"AI 输在防线，不输在经济"，
这一份处理三个具体的窟窿：**它盖了太多没用的东西、它在选卡就把自己选死了、
它的伤害是散的**。

三类的排法不是随手写的：建造和选卡都是**一次决策、长期生效**的杠杆，改一个常量
就能改变整局形状；交战层相反，它是每次行动都在发生的局部判断，改坏了很难看出来。
所以前两类改得狠，第三类只动"打谁"、不动"打不打"。

---

## 一、建造：AI 在给自己盖一座集市

### 1.1 定位

建造决策只有一条链路：

```
unitCandidates → scoreBuild → rawBuildScore
```

`rawBuildScore` 按兵种分成五档（桥 / 军营 / 经济 / 自动开火 / 纯工事），各自有
数量上限，但**没有一层总闸**，而且有两处把"不该建"写成了"分数很低"。

实测（`scripts/diag-build.ts`，3 局 16×16 双 AI）：

| 兵种 | 次数 | 平均敌距 | 敌距 > 8 格 |
|---|---|---|---|
| bridge | 49 | 5.9 | 7 |
| camp | 8 | 7.4 | 3 |
| tower | 7 | 4.9 | 1 |
| mill | 5 | 10.4 | 4 |
| 其他 | 5 | — | — |
| **合计** | **74** | | **15（20%）** |

两个直接问题：

1. **架桥占了 66%**。判据只看"对岸离目标够不够近"（`24 - farDist`），
   于是任何一座通向地图中间的桥都能拿到十来分——包括架在后院池塘上、
   或者架在"绕过去也就多走两步"的小河上。
2. **纯工事在没敌人时返回 4 分**。建筑候选和走位候选在同一个池子里比大小，
   而一步普通行军常常只有几分——4 分是真的能赢的，于是在平静的后方一块一块地砌墙。

另外线上对局库里出现过 **31 座建筑**的局（id=54，77 回合），产能全在盖房子。

### 1.2 改法

| 位置 | 改动 | 为什么 |
|---|---|---|
| `rawBuildScore` 开头 | 建筑总量上限 `min(16, 城数×4)`（桥不算） | 各兵种自己的上限加起来能把一座城的设施区撑到十几座，需要一层总闸 |
| 架桥分支 | 加"**这座桥缩不短路**"判据：过桥之后到目标的距离必须真的更近，否则 `-999` | 直接用 `advance` 距离图比较"站这儿"和"过了桥"，不省路就别为一个建造回合付钱 |
| 纯工事分支 | 敌人不在 7 格内：`return 4` → `return -999` | "挨打才砌墙"这句话写成 4 分等于没写 |
| 经济建筑分支 | 格子产出 ≤ 0 时 `-999` | 一格不产出的地盖上磨坊，产的是 0 |

### 1.3 结果

同样的 3 局：

| 指标 | 改前 | 改后 |
|---|---|---|
| BUILD 总次数 | 74 | **50（-32%）** |
| 其中 bridge | 49 | **33** |
| 远离战场（>8 格）的建造 | 15 | **4** |

桥仍然是最大项（11 座/局，16×16 河图）——这座地图上确实有几条要过的河，
新判据只是把"不省路"的那些删掉了。

## 二、选卡：AI 把六个名额全砸在造不出来的兵上

### 2.1 定位

`src/core/draft.ts` 的 `aiDraftPick` 只有一个评分：

```ts
function draftValueOf(def) { return def.atk + 0.4 * def.maxHp + 3 * def.armor + 3 * def.range; }
```

**纯数值，没有任何"这一局用不用得上"的概念**。而数值和时代几乎单调相关，
于是 AI 每次都挑最高时代的大件。

问题是：城市是从 `startEra`（默认 1 级）起步的，`eraWindowOk` 只放行
`def.era <= 城市等级` 的兵——**选到 ≠ 造得出**。城市从 1 级升到 5 级要几十个回合，
这几十回合里它的产兵表全是"还造不出来"的兵。

实测（`scripts/draft-compare.ts`，6 局同种子，只看乙方的 8 个名额）：

| | 平均时代 | 平均单价 | 开局就能造 |
|---|---|---|---|
| 老评分 | **4.48** | **325 金** | **0 / 48（0%）** |
| 新评分 | 1.38 | 64 金 | 31 / 48（65%） |

老评分选出来的队伍，**48 个名额里没有一个在开局城市里造得出来**。
这和线上数据对得上：13 局人机败局里 AI 的开局阵容常年是 0~2 个单位，
人类是一整队——差距在 BP 那一屏就已经拉开了，跟后面打得好不好没关系。

### 2.2 改法

`draftValueOf` 改成三件事相乘：

```ts
raw      = atk + 0.4*hp + 3*armor + 3*range          // 数值，不变
ready    = 1 / (1 + 0.55 * patience * lead²)          // lead = def.era - startEra
perGold  = (80 / max(20, cost))^0.45                  // 每金多少战力
score    = raw * ready * perGold
```

- **时代折扣用平方**：线性的话 5 级兵只掉 40%，还是压得住 1 级兵，那正是要修的病。
- **单价也进来**：选卡选的是"这一局我能反复造的东西"，不是收藏品。
- **`patience`**：名额过了六成之后放松到 0.35——前几签买"现在能打的"，
  后几签买"以后很能打的"。全按"现在能用"选，会得到一支没有上限的队伍。

另外四条覆盖规则（`aiDraftPick`）：

| 规则 | 目的 |
|---|---|
| 手里没有便宜身体（cost ≤ 70）时 +20 | 前二十回合总得有东西能出门 |
| 手里一张"现在造得出"的都没有时 +26，且只在此时代里挑 | 防止签位全落空 |
| 已经有一张建筑卡就不许再选建筑 | 线上 AI 终局常摆着两座塔，同一局却凑不出一支部队 |
| 水军按地图水面占比打折（≥14% ×0.9 / ≥8% ×0.5 / 否则 ×0.2） | 旱地图上选两条船，整局开不出港口 |

禁用（`aiDraftBan`）**没有动**：ban 掉对面最贵的核心本来就是正确打法，贵＝对面指望它。

### 2.3 结果

同一批种子下，队伍从"六个 5 级大件"变成"四五个 1 级兵 + 一个攻城器 + 一个后续主力"。
一个实际序列（startEra=1）：

```
anc_ram       era1 46金  ✔   anc_elephant era1 54金  ✔   anc_hoplite era1 42金 ✔
med_trebuchet era2 128金      anc_legionary era1 49金 ✔   militia     era1 25金 ✔
med_manatarms era2 78金       archer        era1 35金 ✔
```

## 三、交战：从"伤害散着打"到"打在一个点上"

### 3.1 定位

`scoreAttack` 是**逐单位、逐目标**算的：每个兵各自挑一个"自己这一刀最划算"的目标。
没有任何机制让全军的伤害落在同一个敌人身上，于是五个人打五个目标，每个都打到半血，
对面回一轮血、换一个目标，全程没有人被击杀。

线上数据对这一点的指向很明确（15 局带 timeline 的败局）：
**AI 造 432 个兵、死 375 个（87%）；人类同期只死 114 个。**
这不是"伤害不够"，是"伤害散了"——打不死人，就一直在被人打死。

### 3.2 改法：集火目标

新增 `pickFocusTarget(s, me)`，每回合选**一次**，全军共用：

```
对每个看得见的敌方战斗单位：
  reach = 有几个我方能在一回合内扑到它
  worth = 兵价 × (1 + 残血加成 0~1.5)
  score = worth × reach / hp
选 score 最高的那个；一个都够不着就返回 null（退回各自挑最优）
```

`scoreAttack` 里加一句：`if (target.id === all.focusTargetId) score += 26`。

取 26 的理由：高于普通的掉血收益，低于"能打死一个单位"的 120 档，
**不会**把一次本来就不划算的交换变成"值得打"——加完 26 还是负分的照样不打。
它只改"先打谁"，不改"打不打"。

### 3.3 试过但**没生效**的两条（已删，不留代码）

先试的是"让兵靠在一起"，两个版本，都测了：

| 方案 | 48 局子集结果 |
|---|---|
| 基线（都不加） | 32 胜 14 负 2 未决（66.7%） |
| 战力密度：孤军 −16 / 集结 +10 / 攻击端 −20 | 29 胜 15 负 4 未决（60.4%） |
| 只留集结 +10 | 29 胜 16 负 3 未决（60.4%） |
| **集火（最终采用）** | **32 胜 15 负 1 未决（66.7%）** |

"站在一起"这一路在两个版本上都是**负收益**：AI 一扎堆就没人去占点和推城，
镜像局里被对面铺开的那一方吃掉。所以空间上的聚拢不是这个游戏里"成建制"的正确形状，
**打在同一个点上才是**。

集火在本地测出来是**中性**的（胜率一模一样，只是负局和未决局互换）。
这在预料之内：镜像对局里两边用的是同一套集火逻辑，收益互相抵消；
它与"不集火的冻结基线"打也只是打平。真正的差别只会在**被人集火的局**里出现——
人类每一局都在集火，而 AI 之前从不。这条只能等线上数据回过头验，
`warchess_reports` 的 `made`/`lost` 会直接告诉我们对不对。

## 四、验证

| 项 | 结果 |
|---|---|
| `tsc --noEmit` | 干净 |
| `npm test` | 规则 456 / AI 29 / 评估 7 / UI 154 / 服务 11 全绿 |
| 全量 `evaluate-ai`（13 套 × 8 对 × 双向 = **208 局**，对冻结基线 5fb8e5b） | **139 胜 64 负 5 未决 = 66.8%**，非法行动 0 |
| 上一版（同样的 208 局） | 136 胜 65 负 7 未决 = 65.4% |

按设置看，**火药 +3 胜、英雄 +2、沼泽 +2、峡谷 +1**，中世纪 −3、工业 −1，其余持平：

| 设置 | 改前 | 改后 |
|---|---|---|
| gunpowder | 10-4-2 | **13-2-1** |
| heroes | 13-3 | **15-1** |
| marsh | 11-5 | **13-3** |
| canyon | 10-6 | **11-5** |
| medieval | 9-6-1 | **6-10** |
| industry | 5-11 | 4-12 |
| volcanic | 5-11 | 5-11 |

中世纪和工业这两档退步，和建造改动有直接嫌疑：它们的开局时代是 2 和 4，
城市少、设施区本来就窄，`min(16, 城数×4)` 的总闸在这两档更容易咬到正经建筑。
这一条留给下一轮：把总闸从"城数×4"改成"城数×4 + 时代"再看。

> 加分项：这一轮为了做 A/B，把 `evaluate-ai` 用成了 `--profiles` 子集 + `--pairs`
> 的小跑法（48 局约 5 分钟），改交战评分这种"说不准哪边好"的东西时，
> 先用子集筛、再用全量确认。注意它有源码指纹校验——跑的过程中改 `src/` 会直接
> `Source changed during evaluation`，必须先把代码冻结。
