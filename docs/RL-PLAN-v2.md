# RL v2：把观测改成"扩展无关 + 带意图"

> 这份文档只做一件事：把"要改哪些字段、改成什么样、spec 变成什么、要重录多少数据"写清楚，
> 供过一遍再动手。理由是同一个：**观测一改，已录的 600 局数据和所有权重全部作废**，
> 所以正确顺序是先把规格定死，再一次性改完、一次性重录。

## 一、为什么要改（每条都有具体证据）

### 1. 只编了金币，其它资源对策略不可见

```ts
f[1] = nz(me.gold, 150);
f[2] = nz(me.income, 30);   // incomeOf() 只取 GOLD
```

而引擎里的资源是动态表：`PlayerState.gold` + `res?: Partial<Record<ResourceId, number>>`，
`ResourceId = string`，扩展可以随时加（粮食、建材、灵石）。也就是说在「城郭与物料」里
粮材怎么分配、在「修真」里灵石够不够，**策略完全看不见**——它只看到金币。

### 2. 标度写死，数值一变就整体失准

| 字段 | 现在的写法 | 平衡性调整后的后果 |
|---|---|---|
| 兵种价值（动作特征） | `unitValue / 200` | 均价翻倍 → 所有价值类特征幅度减半 |
| 金币 | `gold / 150` | 起始金/收入调高 → 长局全部顶到 clip 上限 |
| 收入 | `income / 30` | 同上 |
| 兵力总值 | `value / 1200` | 同上 |
| 城市规模 | `maxCitySize / 3` | 扩展加新城市等级 → 全部饱和 |

`f[37] = gold / cheapest`（"钱够买几个最便宜的兵"）就是正确写法：分母是活的参照物，
整体缩放时这个商不变。v2 要把所有"除以常数"的字段都改成这个思路。

### 3. 动作空间缺一整类

`legal.ts` 只枚举 6 类：MOVE / ATTACK / SIEGE / RECRUIT / UPGRADE / END_TURN。
`ACTION_DIM` 里的类型 one-hot 有 7 格（RECRUIT 按城市/军营拆成两格），其余类型全部落到
"都不亮"。

- 后果一：老师的 **7.0% 决策做不出来**（盖建筑、上下船、英雄技能、遣散、放蛋），
  这部分在模仿数据里只能跳过。
- 后果二：换扩展时缺口更大——「修真」的单位与技能、「地形高差」的机制很可能带新动作类型，
  而策略的动作空间里没有位置。

### 4. 一回合步数写死 50

`rollout.ts` / `play.ts` 用 `AI_MAX_STEPS = 50` 当每回合步数上限，
`f[28] = acted / mine.length` 也按"每个单位一步"来估进度。
「行动点扩展」改的正是这个节奏——一回合能走几步不再是"单位数"决定。

### 5. 没有"意图"这个输入

`ai.ts` 里有三套 doctrine（rush / harass / boom），是"这局怎么打"的分岔；造兵打分里还有
一个确定性噪声 ±2（`aiNoise(s, 兵种id)`）。这两层让老 AI 既不死板也不乱来。
策略这一侧**没有任何对应物**：观测里没有意图维度，造兵多样性只能靠 softmax 的残余熵，
训练一收敛就没了（实测熵已从 2.52 降到 2.38）。

## 二、新观测规格

### 2.1 全局块（`GLOBAL_DIM`：40 → 50）

原则：**能用比值就不用绝对值；能查引擎就不写常数。**

| 块 | 格数 | 内容 | 分母/参照 |
|---|---:|---|---|
| 时间 | 2 | 回合进度、本回合已行动比例 | `turn / capTurns`；引擎给的行动预算 |
| **资源（我方）** | 5 | 每种资源"够花几个回合" | `stock / max(1, income)`，按当前扩展的资源表填槽，缺的置 0 |
| **资源（敌方）** | 5 | 同上 | 同上 |
| 资源存在位 | 1 | 有几种资源（归一化） | `资源数 / 5` |
| 兵种池形状 | 4 | 可造兵种数、最便宜价/收入、最贵价/收入、可用域数 | 分母全是**收入**，不是常数 |
| 兵种构成 | 4 | 双方兵种分布的熵（归一化）、远程占比、经济单位占比 | `H / ln(兵种数)` |
| 规模 | 6 | 单位数比、城数比、总价值比、时代差、被毁城市比 | 全部是"我/(我+敌)"或差值 |
| 地理 | 5 | 水域占比、我方重心 x/y、最近敌我距离 | 距离除以棋盘边长 |
| 态势 | 6 | 最近敌兵距离、已动/已战比例、围城压力、双方城墙血比 | 距离除以边长、其余比例 |
| 空地比 | 2 | 双方"最便宜可造"的囤积倍数 | `gold / cheapest`（现有的 f[37] 思路） |
| **意图** | 4 | rush / harass / boom / auto 的 one-hot | 见 §4 |
| 预留 | 4 | 扩展开关位（迷雾、血战、行动点…） | 0/1 |

合计 50。`STATE_DIM = 50 + 108 = 158`（现在是 148）。

> 108 的粗化棋盘不动：它已经是"地形/兵力/城市归属"三个平面，与扩展无关。
> 但「地形高差」若要单独成面，可以再 +36（`BOARD_PLANES 3 → 4`），这一条需要拍板（见 §7）。

### 2.2 扩展描述块（`ENV_DIM`：新增 27，**路线 A 已定**）

已选定 **A：一个网络 + 扩展描述作为输入**。这里有一个关键设计取舍要写清楚：

**不用"扩展 one-hot"，用"结构属性描述"。** one-hot 只能覆盖见过的那几个扩展，
新扩展进来是一个全零向量——那不是泛化，是回避。所以这一块描述的是环境的结构：

| 范围 | 格数 | 内容 | 来源（尽量结构化，不认 id） |
|---|---:|---|---|
| 资源表 | 6 | 资源种数、gold/food/material 存在位、其它资源数、平均每兵种耗几种资源 | `RESOURCES` 注册表 + `def.costRes` |
| 兵种池 | 11 | 总数、按类别数（战斗/经济/建筑）、带 `ap` 的占比、平均 ap、平均造价、价格离散度、平均血量/射程/移动 | `s.config.enabledUnits` + `utype()` |
| 机制开关 | 6 | 迷雾、血战、先行补偿、地形高度占比、非金币资源数、扩展总数 | 前三条里两条按 id（无结构痕迹），其余结构化 |
| 棋盘开局 | 3 | 边长、人数、起始时代 | `s.config` |
| 行动点 | 1 | 开关位 | 按 id（默认值不在兵种表里，见下） |

实现：`scripts/rl/env-desc.ts`（`ENV_DIM = 27`），自检 `scripts/rl/test-env-desc.ts`（12 项全过）。

**两个实测结论值得记下来**（都是写这个模块时才知道的）：

* **行动点没有开局可见的结构信号。** `def.ap` 只是个别兵种的覆盖项，缺省值在
  action-points 模块内部按分档算；真正落到状态里的 `u.custom.ap` 要等第一回合开账才写。
  所以它只能按 id 认。测试里专门有一条断言记录了这个事实。
* **地形高度是"地形类型"的属性**（`TERRAIN_HEIGHT`），不是每格的字段。
  描述向量走 `heightOfTerrain(s, terrain)` 统计"高于地面的地块占比"，
  扩展没开时它对所有地形都返回 0，这一格自动归零——不需要认 id。

新观测的总维度：

    STATE_DIM = GLOBAL_DIM(50) + ENV_DIM(27) + BOARD_DIM(108) = 185

（若 §7 第 1 条决定给粗化棋盘加"高度面"，则是 `BOARD_PLANES 3 → 4`，STATE_DIM = 221。）

### 2.2 动作块（`ACTION_DIM`：56 → 62）

类型 one-hot 从 7 格扩到 13 格：现在的 7 格 + BUILD / LOAD / UNLOAD / HERO_SKILL / DISBAND / PLACE_EGG。
其余 49 格不动（发起单位、目标、结果预估、距离、地形…）。

类型格变多是为了**扩展兼容**：修真/地形高差将来加新动作类型时，至少还有空位，
不必再动 `ACTION_DIM`。

### 2.3 spec 与版本

- `WEIGHTS_VERSION` 1 → **2**，旧权重文件直接拒读（`weightsFromJson` 已有版本检查）。
- 旧的 600 局模仿数据（4.2GB）、`init64.json`、所有 `weights-*` 全部失效，需要重录重训。
- 旧数据**不删**：留在 `.tmp/bc/` 作为 v1 的对照组，`weights-v1-specialist.json` 冻存。

## 三、动作空间补齐（`legal.ts`）

| 动作 | 工作量 | 备注 |
|---|---|---|
| BUILD（野外盖建筑） | 中 | 落点合法性依赖 supplyEra / 地形 / 相邻规则；"盖在哪"本身是二维决策 |
| LOAD / UNLOAD | 小 | 照 `doLoad/doUnload` 的判据写 |
| DISBAND | 小 | 低频，但残局有价值（换钱） |
| HERO_SKILL / PLACE_EGG | 小 | 低频，跟着扩展走 |

每一类都要过 `scripts/rl/verify-legal.ts` 的硬测试：**枚举出来的每个动作，applyAction 必须接受**。

## 四、意图怎么来（关键设计点）

**标签来自老师，不是我随机编的。**

1. `ai.ts` 已经会为每个决策挑一套 doctrine（rush/harass/boom）。加一个导出函数
   `currentDoctrine(s)`，让 `imitate.ts` 在录每一步时把老师当时的 doctrine 记下来。
2. 观测里那 4 格 one-hot 就填这个标签 → 行为克隆学到的是"**在这个意图下怎么下**"。
3. PPO 阶段：rollout 时**随机指定**意图（四个值等概率），让同一批棋局覆盖多种打法；
   评估时按意图分别测，看它是否真的按意图行事（同一张图、同一位置，三种意图的前 20 手应当明显不同）。
4. 推理时可以给 `auto`（四格全 0），由网络自己决定——保留现在的行为作为兜底。

## 五、迁移步骤（顺序不能乱）

1. **改 `features.ts`**：新字段表 + 所有标度改成活的参照物；末尾保留现有的维度断言。
2. **改 `legal.ts`**：补动作类型；跑 `verify-legal.ts`。
3. **改 `policy.ts` / `net.py` / `ppo.py`**：`WEIGHTS_VERSION=2`、`spec` 新维度、
   `TYPE_NAMES` 补新的动作名（分桶诊断要用）。
4. **改 `imitate.ts`**：录意图标签（`SLOTS` 布局加一列）。
5. **重生成 `init64.json`**（`init-weights.ts --topk 64`）。
6. **重录 + 重训**：见 §6。
7. **对照组**：新权重 vs `weights-v1-specialist.json` 在同一批种子上各 160 局，
   确认"没变弱"再继续。

## 六、成本（按今天实测的速率）

| 项 | 单位成本 | 血战一个扩展 | 四个扩展 |
|---|---|---|---|
| 代码改造 | — | 约 3~4 小时（含 verify-legal、对账） | 同左 |
| 模仿数据 | 600 局 ≈ 21 分钟 | 21 分钟 | 1.5 小时 |
| BC 训练 | ≈ 4 分钟 | 4 分钟 | 16 分钟 |
| PPO 12 轮 | ≈ 1.5 小时 | 1.5 小时 | 6 小时 |
| **合计** | | **≈ 5 小时** | **≈ 8~9 小时** |

先只做血战一个扩展，把 v2 跑通、验证不弱于 v1，再逐个扩展开。

## 七、需要拍板的四件事

1. **粗化棋盘要不要加"高度面"**（`BOARD_PLANES 3 → 4`）？
   加：地形高差扩展能用上；不加：那个扩展里高度信息只能靠全局块间接表达。
   建议**加**（一次性成本 36 维，`STATE_DIM 158 → 194`）。
2. **资源槽位固定 5 个够不够**？（金币 + 4 种）现在项目里最多同时出现 3~4 种。
   建议 **5**，留一个位。
3. **意图用 4 维（三套 + auto）还是先只做 3 维**？
   建议 **4 维**，auto 是兜底，也方便和现在的行为对比。
4. **v2 先只做血战扩展，还是同时上 2~3 个扩展**？
   建议**先只做血战**：v2 是一次大改，先在单一环境里证明"不比 v1 弱"，
   再扩环境；否则改坏了分不清是"结构问题"还是"扩展差异"。

## 八、评估规矩（这次就写进脚本，不等出问题）

- **分扩展报，绝不允许平均**。每行必须带：扩展名、局数、得分率、95% 区间。
  （一个扩展 60%、另一个 20%，平均 40% 看起来还行，实际是一半崩了。）
- **分削弱档报**（`--ai-handicap`）。只报"不削弱"那一档会在长时间里全是 0，看不出进展。
- **分意图报**（v2 之后）：同一批种子、三种意图各跑一遍，才能说"它确实会按口令打"。
- 每次报告都要写清口径：种子范围、局数、地图尺寸、扩展、AI 难度、削弱概率。

## 九、落地时量出来的东西（2026-11-05，按 §5 的顺序改完）

### 9.1 维度最终版

| 常量 | v1 | v2 | 说明 |
|---|---:|---:|---|
| `GLOBAL_DIM` | 40 | **50** | 资源 5+5 槽、兵种池 4、构成 4、规模 6、地理 5、态势 6、空地比 2、意图 4、机制开关 5、预留 1 |
| `ENV_DIM` | — | **27** | `env-desc.ts` 早写好了，这一版才真正接进 `encodeState` |
| `BOARD_DIM` | 108 | **144** | `BOARD_PLANES 3 → 4`，第四面是地形高度（§7 第 1 条按"加"落地） |
| `STATE_DIM` | 148 | **221** | 50 + 27 + 144 |
| `ACTION_DIM` | 56 | **62** | 类型 one-hot 7 → 13（其余 49 格不动） |
| 参数量 | 22,786 | **32,798** | 预筛涨 79、scorer 涨 5,061、value 涨 4,672 |

`WEIGHTS_VERSION` 1 → 2，`net.py` 的 `DEFAULT_SPEC` 和 `ppo.py` 的 `TYPE_NAMES` 同步跟上。
v1 的权重（`init.json` / `init64.json` / `v1-specialist.json`）现在会被直接拒读——
这正是版本号存在的理由。

### 9.2 成本：每步 0.55 → 0.70 ms，但摊到采样只有几个点

`joint` 从 204 涨到 283，而重排那一步是 `16 × (joint × 64)` 次乘加，占 `decide` 的七成以上，
所以它单独贵了 39%。不过采样循环里 `legalActions` 才是大头（47~60%），
摊到整步大约 +7%。M1 的预算断言从 0.6 抬到 0.85 ms，附了算式。

顺手修了一个自己造的坑：`encodeBoard` 逐格调 `heightOfTerrain`，而那个函数要遍历
扩展钩子——12×12 就是 144 次。改成按"扩展组合 + 地形"记忆的查表（一张图最多 13 种地形）。

### 9.3 动作空间：老师的跳过率 7.0% → **0.0%**

补完六类动作之后：探路 6 局 2485 条决策只剩 1 步找不到；600 局整批 776/289,979 = 0.27%，
缺口表是 `{"BUILD":769,"DISBAND":7}`。顺着查下去，剩下的**全是桥**：
扫描半径读的是**工兵**的 `def.bridges`（永远是 false），而应该读**要盖的那个东西**的——
桥要靠 `bridgeChainOk` 的 +2 才能往河心递。改完之后复测 7654 步 0 跳过。
`verify-legal.ts` 全量校验 95,842 个枚举动作 + 12×12 抽样 33,162 个，**0 个被拒绝**。

动作构成（8×8、全量两步校验）：MOVE 61% · ATTACK 14% · RECRUIT 10% · BUILD 6% ·
DISBAND 3% · SIEGE 2% · END_TURN 2% · LOAD 1% · UNLOAD 1%。

三处**写下来免得下次重犯**的细节：

1. **`blockedByAlly` 是多余的，而且是错的。** 枚举里原本自己扫一遍"格子上有没有友军"，
   但 `reachableTiles` 返回的**已经是**能停下的格子——它内部按 `blockedAnchor` 过滤过，
   而那套判据细得多：不同飞行层不占位、自家的塔/军营/**桥**可以站、墙连自己人也停不上去。
   自己写第二遍的后果是过度过滤：剩下的 4.0% 跳过里 98/99 都落在**自家桥上**，引擎允许站，
   枚举把它踢了。删掉之后归零。判据只能有一处。
2. **UNLOAD 的"贴着船"要看船体，不是锚点。** 2×2 的大舰锚点在左上角，
   按锚点 ±1 扫出来的 3×3 里有一半是斜角、`distance` 算出来是 2。
   现在按 ±3 扫再用 `distance(ferry, 格) === 1` 过滤。
3. **BUILD 有三道关，少一道就出事。** 落点（`buildSiteError`）、
   **落点**的时代供货（`supplyEraAt(s, seat, {x,y})`，不是工兵脚下那格）、
   以及钱（`canPay(recruitResCost(...))`）——但"续建自家同型工地"那一支不收钱，
   所以钱关要放在 `!site` 的条件下。

### 9.4 意图：标签只能在 `tactic` 档拿

读 `ai.ts` 才发现：**高级档（advanced）根本没有战术层**。`moodFor` 会把三种权重压成均分、
`drive` 清零、也从不弃城——三套 doctrine 只在**中级档（tactic）**上生效。

后果：
- `imitate.ts` 里用的是 `--ai-level advanced`（和 v1 同一个老师），
  所以录下来的 `lead` 只是"证据指向哪一边"的**状态派生特征**，不是"老师按它下了这一步"；
- 想要真正的"按意图下棋"标签，得用 `--ai-level tactic` 另录一批。
  两种录法都留着，用途不同：advanced 是更强的老师，tactic 才有意图信号。

也就是说 §4 那条"标签来自老师"的前提**只在 tactic 档成立**。

于是这一版按**局交替**录：偶数局贴"证据指向的那套打法"（状态的派生标签），奇数局贴 `auto`。
两头都不能走极端——

- 全贴 lead：`auto` 那一格在训练集里一次都不亮，而推理默认就是 `auto`，
  等于往一个没训过的输入上喂 1。这不是泛化，是漏了一格。
- 全贴 auto：四格全是死的，想让策略听懂口令就得从零学。

（第一版录到一半才发现这件事，600 局作废重录。记在这里，免得下次又"先跑了再说"。）

指令跟随到底学没学到，交给评估回答：`eval.ts --intent rush|harass|boom` 同一批种子各跑一遍，
比"三种意图下前 20 手是否明显不同"。答不出来就是没学到，不猜；
真要教出"按口令下棋"，得用 `--ai-level tactic` 另录一批——那一档 doctrine 才真的驱动行为。

### 9.5 新增的口径开关

- `rollout.ts --intent auto|random|rush|harass|boom`：`random` 按种子给每一方抽一个，
  是训练指令跟随的口径；默认 `auto`，和 v1 一致。
- `eval.ts --intent ...`：同一批种子换意图各跑一遍，专门用来回答"它听不听话"。
