# 更新公告 · 2026-10-28 · 「不卡了」

> 一句话：**32×32 不卡了。** 单帧脚本耗时从最快的 18.7ms（超过 16.7ms 的 60fps 预算，
> 也就是**没有一帧**赶得上）压到最快 5.6ms / 中位 8.7ms，掉帧率 **100% → 0%**；
> 每帧新建的 DOM 从 1 106 个降到 41 个。
>
> **规则、平衡、存档格式一行没改。** 同一张种子图、同一串操作，走出来的棋和以前逐格相同，
> 改的只是"怎么把它画出来"。

**怎么确认**：开 32×32，在几个兵之间来回点、让一支兵走八格以上、打一整回合。
以前点兵那一下会"噎"住，现在不会了。

---

## 一、先报数

32×32、43 支部队、同一台机器、同一个脚本、每次 50 帧：

| | 改之前 | 改之后 |
|---|---:|---:|
| 单帧最快（画面真在变的帧） | 18.7ms | **5.6ms** |
| 单帧中位 | 21.2ms | **8.7ms** |
| 单帧 p95 | — | **12.2ms** |
| 单帧最慢 | 39.9ms | **13.1ms** |
| 掉帧率（超过 16.7ms 的帧） | **100%** | **0%** |
| 每帧新建 DOM 元素 | 1 106 | **41** |
| 每帧写进 innerHTML | 66.4 KB | **3.8 KB** |
| 每帧调 `getBoundingClientRect` | 86 | **0** |
| 12×12 单帧最快 | 5.0ms | **2.8ms** |

两点补充，都不利于"好看"，但得说：

- **哪一档都不掉帧了。** 改之前那 18.7ms 是**最快的一帧**——最乐观的那个数都没进预算。
  现在报表里 12/16/20/24/32 五档的掉帧率全是 0%，最慢的一档（p95 12.2ms）也还在预算内。
- **尺子没动过。** 新脚本里专门保留了"每帧全量重画"这一档，它量出来是 21.3ms——
  和改之前的 18.7~21.2ms 对得上。也就是说这不是"把测量条件放宽"换来的数字，
  同一个脚本、同一个局面，改前改后各量一遍。

## 二、你实际会感觉到什么

不看数字，是这几件小事：

1. **点兵不再"噎"一下。** 以前每点一次，棋盘上 1 024 个格子连同棋子全被丢掉重画一遍。
   现在只擦真的变了的那些格。
2. **长距离行军动画变顺了。** 以前每帧节点都是新的，动画起点等于"从空白里冒出来"，
   走八格看着像闪了八下；现在节点是同一个，位移是连续的一整段。
3. **拖地图、滚侧栏不再抖。** 顶栏和侧栏内容没变的那一帧不再重写 DOM，
   滚到一半被弹回顶部的机会也就没了。
4. **大图不再随兵力线性变卡。** 顺带量清楚了一件反直觉的事：卡的主因**不是兵多**
   （43 → 85 只只差 2%），是**格数**（144 → 1 024 格让单帧翻了两倍多）。
   所以小图一直"能用"、32×32 一开就崩。

## 三、改了什么（玩家版）

一句话：**以前每帧把整张棋盘拆了重画，现在只擦改动的那几格。**

打个比方。以前的画法是每帧把黑板擦得干干净净、整幅重画一遍——就算这一帧只是某支兵
挪了一格。现在改成：格子本来就长在那儿，只把这一格擦了重画，别的一笔不动。

七处，全是"画"的方式，没有一处动规则：

| 改动 | 一句话 |
|---|---|
| 格子层节点复用 | 1 024 个格子节点建一次就留着，只改变化那几格的 class |
| 棋子层按 id 复用 | 节点留着，只补变了的字段（血条、行动完的灰、选中框） |
| 侧栏按内容跳过 | 拼出来的 HTML 先和上次比，一样就一个字都不写 |
| 行军动画不再问浏览器 | 位移自己乘格子宽算，不再逐帧去读元素的位置 |
| 尺寸只在真变时才量 | 窗口 / 缩放 / 参谋部栏变了才重新量棋盘多大 |
| 顶栏按签名跳过 | 十几个字的签名一样就整段跳过，连带省掉一次布局 |
| 雾视图每帧只算一遍 | 以前棋盘和侧栏各算一次同一份雾视图 |

**为什么"读位置"值得单列一条。** 每次问浏览器"这个元素现在在哪"（`getBoundingClientRect`），
浏览器都必须先把整套布局算完才能回答。以前的顺序是"写完一大块 DOM → 读 86 个矩形 →
再写动画"，真机上这一次读比动画本身贵得多。现在这 86 次读变成 0 次。

## 四、顺手留了件工具：`npm run perf`

这批改动是**先写体检脚本、再照它排的顺序改的**，不是凭感觉猜。脚本留在仓库里了：

```
npm run perf                                          # 五档全量（12/16/20/24/32）
npm run perf -- --sizes=32 --frames=80                # 只量 32×32，多采几帧
npm run perf -- --baseline=docs/perf-baseline.json     # 和上一次比，看是真省了还是噪声
```

它输出：各规模的最快 / 中位 / p95 / 最慢、掉帧率、每帧新建多少 DOM、写多少 HTML、
堆增量、四个阶段的拆解（雾视图 / 棋盘 / 侧栏 / 威胁圈），外加"缓存省了多少"三档对照。

玩家用不上，但**如果你那台机器还卡，跑一下 `npm run perf -- --sizes=32` 把输出贴出来**，
能直接分清是"脚本还没压干净"还是"瓶颈在浏览器绘制那一半"（见下一节第 4 条）。

怎么读这份表见 [docs/PERF.md](PERF.md)，里面专门写了三个容易误读的地方——
比如"最快"那一列是反复跑取最好的，它代表能力下限，不是你平时的体感。

## 五、还没解决的，摊开说

1. **AI 回合还是会顿。** 单次决策 11.4ms（p95 12.7ms），一回合十几步会累加成肉眼可见的停顿。
   顶栏的 AI 速度档能缓解（慢 180ms / 快 70ms / **极快 0ms** 间隔），但那只是"少等"，
   不是"不卡"。真正的解法是把决策挪出主线程，还没做。
2. **换选中还是整块重写侧栏。** 那 1.9ms 里，顶卡和战报卡明明一个字都没变。
   拆成几块各自缓存还能再省 60~70%，下一步做这个。
3. **地形层没有 canvas 化，而且现在不划算。** 格子层已经不重写了，canvas 只能省
   "样式重算与绘制"那部分，却要动掉所有依赖 `.tile.t-water` 这类选择器的样式与测试。
   等真机上确认瓶颈在绘制时再说，不为了表格好看去动它。
4. **脚本测的是下限。** 它跑在 jsdom 里，**不含浏览器的布局与绘制**。
   现在 JS 侧已经进预算了，所以：**如果某台机器还卡，瓶颈大概率在绘制 / 合成那一半**——
   那种情况该开 DevTools 的 Paint flashing 看是不是整屏在闪，而不是继续压脚本。

第 4 条是这个公告里最该记住的一句。我们改的是能测的那一半，剩下那一半得在真机上抓。

## 六、三分钟自测

1. 开 32×32，选一支兵，在五六个兵之间**快速点来点去**——应该没有"噎住"的停顿。
2. 让一支兵走 **8 格以上**，看动画是不是一口气滑过去，而不是一格闪一下。
3. 侧栏滚到战报中间，然后在棋盘上点别的地方——战报不该被弹回顶部。
4. 打一整回合（含 AI），把顶栏速度档切到「**极快**」，AI 那几步应该明显顺一些。
5. 关键一步：同一张种子图、同一串操作，改前改后的棋局结果应该**完全一致**。
   规则没动，这一点必须成立——有专门的用例守着。

```
tsc --noEmit        干净

test:ui             120 项全过（新增 5 条缓存护栏）
build               ✓
manual              14 册 · 兵种 49 · 能力 51 · 扩展 26
```

新增那 5 条 UI 用例是给缓存上闸的，断言的全是"缓存不许把画面停住"：
节点身份不许变、高亮摘干净、换地图必须重建、棋子死了要摘节点、侧栏内容变了必须重写。

它们不测性能，只测"**优化没有把功能改坏**"。老实说，这比性能数字更重要——
把画面画快了的办法有很多，画对了的办法只有一种。

每一处的实现细节（节点缓存怎么存、DOM 顺序为什么不能靠 `z-index`、上帝模式换货架时
那个会让货架赖在屏幕上的坑）在
[`docs/UPDATE-2026-10-28-perf.md`](UPDATE-2026-10-28-perf.md)，没有藏。
