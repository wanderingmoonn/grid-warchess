# v4 代码地图：每个文件管什么

> 这份是"读代码前先看"的地图。结构不对的时候，先回来对一遍这里说的是不是还是那样。
> 计划本身见 `PLAN-V4-2026-11-23.md`；这里只讲**代码分成哪几块、每块为什么存在**。

```
src/core/v4/
├── world.ts      服务层：算一次，全上层读（阶段 1a）
├── types.ts      三层的"数据契约"：每层准输出什么
├── decide.ts     决定层：做什么 + 期限 + 理由
├── constrain.ts  约束层：哪几格必须空、谁归哪队、打哪座城
├── tactics.ts    打分层：产出一个引擎认的动作
└── ai-v4.ts      入口：把三层接起来，对外的签名和 v1/v3 一样
```

调用顺序是单向的，没有回调、没有共享可变状态：

```
GameState ──► buildWorld ──► decide ──► constrain ──► actFor ──► Action
              (数)          (决定)      (约束)        (动作)
```

## 1. `world.ts` —— 服务层（这一层最先做，也最好验收）

**它回答的全是"数"，不做选择。**

| 它提供 | 为什么必须只在这里算 |
|---|---|
| `marchTurns(a, b)` | 从 A 到 B 要几**回合**（不是几格：森林两回合、平原一回合）。v3 每个模块自己算一张距离图，结果同一格在不同模块里能算出不同的回合数 |
| `roleOf(city)` | 城的角色（home / threatened / front / safe）。v3 有**三个口径**，谁也说不清"前线"到底指哪座城 |
| `keepClear` | 产兵格。造兵要落在这儿，所以它们必须空着——这是约束层的原料 |
| `affordableCombat(city, gold)` | 这城现在买得起什么兵 |

**为什么单独成关**：它输出的是数，能和引擎真值对拍；上层输出的是选择，只能看结果。
先把最容易验收的一层打牢，前两周才不会陷入"感觉变好了但说不清"。

**已知取舍**：`marchTurns` 用的是"层数 BFS ÷ 移动力"，把森林的额外消耗拍平了。
真值要按地形代价算 Dijkstra——等它开始出错再换，现在不值得。

## 2. `types.ts` —— 数据契约（这个文件没有算法）

v3 的病根是"三层都能往同一张分数表里加一项"。所以 v4 干脆把**每层准交什么**写成类型：

| 层 | 只能交 | 交不了的东西 |
|---|---|---|
| 决定层 | `Decision`（做什么 / 管到第几手 / 为什么） | 交不出"进攻意愿 +40" |
| 约束层 | `Constraints`（keepClear / squads / forbid） | 交不出"让位意愿 +50" |
| 打分层 | `Action`（引擎认的那一个动作） | 交不出"这个兵值 12 金"以外的价值判断 |

`Decision.untilTurn` 是硬要求：**没有期限的决定会悄悄变成常数**，然后没人记得它是谁写的。

---

## 3. `decide.ts` —— 决定层

三条规则，很粗，故意的：

1. 自家城被压着、兵力不占优 → **守**（把外面的兵收回城下）
2. 我明显更强 → **推**最近的敌城
3. 其它 → **发展**

"更强"用的是**身价**（atk + hp + 射程×4，按血量比例打折），不是个数——一个四代兵不等于一个民兵。

**为什么只有三条**：细则要靠题库一题一题长。v3 那六千行系数不抄，那些系数正是"改一处不知动到哪"的来源。

---

## 4. `constrain.ts` —— 约束层（v4 的关键投资）

把"要做什么"翻译成"哪几格必须空、谁归哪队、打哪座城"。

三条铁律：

- **不把自己人排到 `keepClear` 上**（那是"必须空"的格子，排上去自相矛盾）；
- **每个兵最多属于一支队**（v3 的一兵多队让两套指令互相覆盖）；
- **守城的兵不出去**（`hold` 是约束，不是倾向）。

**为什么这层排在打分层之前**：直觉是"打分才是现成资产，先做它"。但 v3 每次翻车都在
**分数表达不了的约束**上——桥头要让开、产兵格要让开。这些"必须"塞进分数里，
就会和"别送死"互相打折，最后谁也不让。

`keepClear` 就是这条思想的实体：打分层发现自家单位站在上面，**第一件事就是挪开，不许权衡**。

## 4.5 关键格与让位搬迁（阶段 2 的核心）

### 什么算"关键格"

判据是**功能**，不是几何：**占住它会让某个动作发生不了**。三类：

| 类 | 条件 | 占了会怎样 | 来源 |
|---|---|---|---|
| `spawn` | 产兵格被自家单位占住 | 这座城**造不出兵** | v3 的 `buildSlotPlan` |
| `exit` | 城格全被战斗单位占、外圈又被经济兵占满 | 军队**出不了城** | v3（`probe:combat-trap` 逼出来的） |
| 桥头 | 邻格有 ≥2 片水的桥面格 | 过河的唯一通道被堵死 | v4 新加（S-005） |

**"桥点周围 2 格"那种软区域不进硬约束**——v3 自己也标了它是"最好别站"，
按计划 4.3，软的东西不许伪装成硬约束。

### 让位为什么要"计划"而不是"判断"

关键格后面常常排着一串自己人。让一个人走开没用，整条链要一起挪一格：

```
关键格  自己人 自己人 自己人  →  空格（洞）
```

v3 用 `buildYieldPlan` 解决：**多源 BFS**，种子是"所有空格"，得到每格到最近洞的距离，
再沿 `prev` 指针把链上的人逐个朝洞挪。**一回合能清多格**（单链版只能清一格）。

v4 抄思路、不抄代码：

- 结果放进**约束层**（`Constraints.yieldMoves`），打分层只执行——v3 把它和 `yieldPlan`
  的分数混在一起，于是"让开"和"别送死"互相打折，最后谁也不让；
- **推进/攻城的兵不算挡路**：它们正在过桥，有理由待在那儿；把让位也对它们生效，
  过桥的兵会被自己的规则赶回去，在桥上来回横跳。

### 一个反直觉的坑

关键格的语义是**"不许停"，不是"不许过"**。
早期把 `keepClear` 当墙（`stepToward` 跳过这些格），结果桥头一进 `keepClear`，
**全军过不了河**（S-005 从过河 3 个掉到 0）。现在允许踩，"别停"由搬迁计划负责。

## 5. `tactics.ts` —— 打分层（第一版故意笨）

一个单位一步，优先级是**硬的**，不是分数：

| 顺序 | 条件 | 动作 |
|---|---|---|
| ① | 站在"必须空"的格子上 | 让开 |
| ② | 任务叫我去打城，且引擎说够得着 | `SIEGE` |
| ③ | 引擎说能打到某个敌人 | `ATTACK` |
| ④ | 有任务、没到目标 | `MOVE` |
| ⑤ | 没任务 | 什么都不做（交 null） |

### 两个坑（都写在代码注释里了）

**坑一：② 必须排在 ③ 前面。**
一开始"能打就打"排在前面，结果 S-000 上 30 手打掉 **0 城血**——敌人一直站在城格上，
永远有目标可打，永远轮不到攻城。**约束优先于战术自保**：约束层说了去打这座城，到了就打城。

**坑二：能打谁、能不能攻城，一律问引擎。**
我自己算距离判射程，而引擎按 `strikeDistance`（含高度差、空中 +1）算，
于是每回合都提一个必被拒的攻击（"目标超出射程"），30 手一次没打出去。
现在改成 `attackableTargets()` / `siegeTargets()`——**一份真相，别自己再算一遍**。

## 6. `ai-v4.ts` —— 入口

对外的签名和 v1/v3 完全一样（`aiNextAction(s, budget, rejected)`），所以游戏、判分器、
跑批脚本都能直接换，不用改调用方。

它只干一件额外的事：**按回合缓存**。

`aiNextAction` 是**一个动作**调一次。如果每调一次都重建 World、重做决定，那就是 v3 的老毛病
（每步都在重新评估，行为在动作之间抖动）。所以按"回合"缓存，只有局面真变了
（回合号 / 单位数 / 金币 / 城数）才重建。

### 第三个坑：造兵必须有上限

不设上限时，200 金会被一口气换成 8 个民兵，而动作数是有预算的——钱花完了这一步也走不动了，
最后 0 城伤、一兵未动。上限语义是"这回合补两个人"，不是"这回合把钱花光"。

### 第四个坑：新兵会堵住产兵格

新兵出生就在产兵格上，而且它的行动已经用掉了。① 那一步如果只看"站在 keepClear 上"，
就会一直给它派"让开"，然后被引擎反复拒（实测每回合空烧十几次）。
**跳过本回合已经动过的单位**，并且**城格不算 keepClear**（新兵本来就生在城里）。

## 7. 在游戏里看它想什么（右下角面板）

`src/ui/v4-hud.ts` + `main.ts` 的两个 URL 开关：

| 地址 | 效果 |
|---|---|
| `?ai=v4` | 这一局的 AI 换成 v4（压过"高级 = v3"的档位映射） |
| `?debug=v4` | 右下角出面板（不影响用哪个内核） |
| 两个一起 | 边打边看 v4 的三层输出 |

面板里有三块：

1. **决定**：做什么（推/守/发展）、管到第几手、理由原文；
2. **队伍**：每支队的任务和人数（`main 推进 10`）；
3. **迷你地图**：一格一方块。我方战斗青、我方经济琥珀、敌方红、敌城深红、
   **"必须空"的格子橙色空心框**（这是最该被看见的——约束在哪）。

面板是**只读**的：关掉它行为必须一模一样。它出错的代价只是"看不见"，所以面板内部
`try/catch`，出错就在面板上写一行字，不往对局里抛。

按回合缓存：`buildWorld + decide + constrain` 不便宜，而 render 每帧都跑，
所以只有「回合号 / 当前方 / 单位数 / 金币」变了才重建。

## 8. 流水账的读法（先看这一句）

**8.x 是按时间记的施工日志**，每一节的数字都是**当时那一刻**的读数（尤其"几绿几红"），
后来被推翻的很正常——看现状一律看第 0 节，看待办看第 9 节。
被后来推翻的节，标题上会写"已回滚 / 净负 / 已被 X 取代"。

## 8.5 试过但失败的：编队级"算账"（2026-11-24，已回滚）

想给编队加一条"这仗值不值得打"。三次写法，三次把绿的题弄红：

| 写法 | 结果 | 死因 |
|---|---|---|
| 预计损失 = 能开火的敌人 × 攻击 × 还要走几回合；`剩余血量 ≥ 守军血量` 才打 | S-000 / S-005 / S-011 **一起变红** | 把损失估高一个量级：假设敌人每回合都开火、且不会被打死 → 结论永远是"打不了" |
| 同上，但只数"同时能打到前沿的敌人" | 仍然全红 | 换了个口径，还是同一个假设 |
| 卡住 3 手就收拢重整 | 锁死在退守 | **没有出口**：退回去 → 离城更远 → 更算"没推进" → 继续退 |

**根因不是实现细节，是缺一样东西：目标价值。**

人的判断是"城伤 45 值得折 20 条命"——人手上有这条判据。
AI 不知道"45"，所以任何"损失 vs 收益"的规则，其中"收益"那一侧只能拍一个数，
而这个数会变成下一个要调的旋钮（v3 的老路）。

**结论：先把"牙齿"装上（打分层能打穿），再回来算账。**
现在的 v4 打不动，任何成本收益分析都会得出"别打"——那不是判断力，是没能力。

## 8.6 试过但失败的：集火按"威胁"排序（2026-11-24，已回滚）

现在的集火口径是"能打死的挑血最少的，打不死的挑伤害/血量最高的"。
试过换成"按威胁排"（威胁 = 它的攻击 × 它能打到我几个），两种写法都失败：

| 写法 | 结果 |
|---|---|
| `威胁 × min(1, 伤害/血量)` 一个连乘式 | **S-001 四种子全红**，S-002 纹丝不动 |
| 分两档：能打死的按威胁挑，打不死的按"削得最狠"挑 | 仍全红 |

**S-001（该赢必赢）是最灵的探针**：任何让"打谁"变聪明的改动，只要把兵引向
一个够不着的目标，这题立刻红。

**教训**：两个量乘起来看着漂亮，实际把"先打死"和"先打疼"两个意图搅在一起。
现在的"挑血最少的"虽然笨，但它有个好性质——**目标和当下能打到的位置一致**。

## 8.7 S-002 的"压不到城下"：两次尝试都失败（2026-11-24）

先量清楚：拿人手答案（55 城伤 / 22 损失）和 v4 逐手对照。

| 手 | 人（最近距离 / 城血） | v4（最近 / 城血 / 能打到的单位数） |
|---|---|---|
| 1 | 6 / 99 | 4 / 99 / 0 |
| 2 | **3** / 99 | 4 / 99 / 0 |
| 3 | **2** / 99 | 4 / 99 / 1 |
| 6 | 2 / **62** | 5 / 99 / 0 |
| 7 | **1** / **1** | 6 / 99 / 2 |

**不是"打不过"，是"挤不进去"**：30 个兵排成一列纵队，前排被敌人挡住、后排被自己人挡住，
火枪永远停在 8 格外——每回合只有 1~2 个兵够得着，人的同一项是 5+。

两次尝试，都失败：

| 写法 | 结果 |
|---|---|
| **队形闸门**：比队伍中位距离领先 >1 格就等 | 自我强化——后排远 → 中位远 → 前排等 → 没人靠近。中位距离连续 7 手停在 8~9，比改之前更差 |
| **横向绕行**：距离不变但两轴更均匀的格也允许走 | S-002 只从"打 3 次"变"打 4 次"，而 **S-005 过河 4→0 变红**，净负 |

**结论**：单列队形的微调救不了。要的是**分路**——把 30 人拆成 2~3 支，各走一条走廊。
那是约束层的事（谁走哪条路 = 约束），不是打分层能解决的。

## 8.8 分路与占用声明：也失败了（2026-11-24，已回滚）

按"人下意识会分左中右三路"的直觉做了两件事：

| 机制 | 做法 | 结果 |
|---|---|---|
| **分路** | 沿"队伍质心→城"的法向把成员排序、均分三组，各给一个城边引导点 | S-002 仍是 0 城伤；且 S-000 / S-005 / S-011 **三题一起红** |
| **占用声明** | 每回合记下"这格已经有人要去了"，后来的兵不许抢 | 修掉了"两个兵提同一个目标格"（实测 u1、u2 都提 (2,5)），但成绩无变化 |

**为什么失败**：两者都在改**局部走位**，而 S-002 的差距是**整体的**——
30 个兵的中位距离连续 6 手停在 8~9 格，根本没在推进，分不分路都一样。
人从第 1 手就是整体压上，第 2 手到 3 格、第 3 手到 2 格。

**下一步该看的不是"路怎么走"，而是"为什么整队不往前"**：
每回合能打到敌人的单位是 0~2 个，而人有 5+。要么是射程内没人（位置问题），
要么是**动作预算被别的事吃掉了**（造兵、经济兵、让位）。这个还没量。

## 8.9 S-002 到底卡在哪：量出来的结论（2026-11-24）

三次猜测（预算、采购、队形）都被数据否掉，最后量到了真东西。

| 假设 | 量法 | 结果 |
|---|---|---|
| **动作预算不够** | 每回合用了几步 / 上限多少 | 用 **22~28 步**，上限 50；`aiStepCap`（30 兵）= **206**。AI 自己收手 → **不是配额** |
| **兵没在动** | 每回合逐单位位移 | 21~24 个兵每回合确实挪 **1~2 格** → **动了** |
| **造兵稀释队伍** | 每回合 RECRUIT 数 | v4 **2 个/回合**（7 手 14 个），人 **0 个**。关掉造兵后：S-002 不变、**S-005 变红** → 不是根因 |
| **队形/路线** | 分路、横向绕行、队形闸门、占用声明 | 四种全失败（见 8.7 / 8.8） |

**真正的数据**：3 手之后，大部分单位还在西南角（(1,8)、(3,9)、(4,10)），
只有 3 个兵（u20/u21/u23）摸到中部，能打到 1~2 个目标。

**结论：拥堵，而且"每回合挪 1~2 格"是互挤/横移，不是推进。**
前排被 12 个步枪兵挡住（进不去），后排被自己人挡住（过不去），
净位移接近 0。人的解法是**第 1 手就横向展开**——但从正面看，那只是"往两边散"，
在桥/窄道上做同样的事会掉进水里（我之前试过，S-005 就是这么红的）。

**下一步的方向：横向展开要看地形宽度。**
开阔地才展开，窄道保持单列。这需要先算"这一格朝目标方向的走廊有多宽"——
一条几何查询，属于服务层（`world`），不属于打分层。

## 8.10 展开宽度（地形约束）已实现，但真凶是"人墙"（2026-11-24）

按用户意见把展开宽度做成**约束**（不是打分）：

- `world.corridorWidth(p, toward)`：横向能并排站几格（桥=1，开阔地 8~9）；
- `planLanes`：宽 ≥5 三路、≥3 两路、**窄道退回单列**；引导点是滚动航点（前沿+3格）。
- 结果：**没有回退**（S-005 仍是 4、S-000/S-011 都绿），但 S-002 仍然 0 城伤。

**然后量到了最后一个数**：从开局到第 5 手，单个兵只前进了 **3~4 格**——

```
u9  (1,9) → (5,10)   5 手 4 格
u16 (1,10) → (4,8)   5 手 3 格
u20 (5,10) → (7,7)   5 手 3 格
```

火枪移动力是 **2**，也就是每手该走 2 格。实际只有 **0.6 格/手**。

**原因：人墙。** 每个兵每回合只能挪 1 格，因为"跳 2 格"的那个落点被前面的自己人占着。
30 个兵挤成一坨，前排挡的不只是敌人，还有后排的路。

**下一步的方向**：分排行动——前排先走开（走满 2 格），后排再补位。
关键不是顺序（现在已经按离城远近排了），而是**前排必须先腾出空间**，
而后排的 `stepToward` 需要知道"这一手哪些格会被前面的人腾出来"。

## 8.11 人墙破了：同距离选"两轴更均匀"的格（2026-11-24）

**改了一行判据**，S-002 从 0 城伤变成 54（线 45），S-001 也回来了。

```
stepToward 里，距离相同的两格，选两轴差更均匀的那个
```

为什么有效：距离一样的两格——一格直着往前、一格横着往旁边——
原来谁先被遍历到就用谁。30 个兵各走各的，实际走成**之字形**，
净推进只有 0.6 格/手（移动力是 2）。选"更正对"的那格就变成直着走。

**但它不能无条件开**：S-005（10 个兵过桥）、S-011（12 个）一开就掉。
差别是**队形有没有纵深**——S-002 是 25 个兵的多排队列，那两题是单排。
所以闸门是：`有纵深（≥16 人）且分了路` 才走直线。

（"≥16"是人数近似，本质是"有没有三四排"。等有更好的几何量再换。）

## 8.12 留档：群体移动算法（用户 2026-11-24 提的，先不做）

用户原话：

> 这或许需要群体移动算法而不是每个单位各自移动，因为人类考虑问题时经常会在
> 整体移动一群兵的视角和局部战术穿插视角之间切换。

**为什么记下来**：今天所有"人墙"类问题（战斗兵推进慢、经济兵堵路、新兵往最远处空地跑）
都是同一个根：**每个单位独立算一步，没有人算"这一群该怎么动"**。

**如果以后要做，可能的形状**：
- 一层"编队级位移"：先决定整队的**目标阵形**（方阵/横排/纵队），再让单位去认领阵位；
- 认领用最优匹配（匈牙利/贪心），而不是让每个兵各自挑最近格；
- 局部战术穿插（"我要绕过他"）作为第二层，只在阵形冲突时触发。

**代价**：这是新增一层，不是改一条判据。要先有"阵形"这个概念（现在 `Squad` 里没有）。

## 8.13 距离口径：全部按曼哈顿（2026-11-24）

**一条规矩：所有距离用曼哈顿距离**（`|dx| + |dy|`）。斜着走一步要花两步，
所以斜向的格子不能算"更近"。视野那一处按引擎原有画法保留，不参与判远近。

v4 早期用"斜向算一格"的口径，系统性高估推进能力（"离城 4 格"在引擎眼里是 6 步）。
现在两层各归各位：

| 用途 | 口径 | 在哪 |
|---|---|---|
| 规则判定（`distToCity` 等）、v4 里一切"谁更近" | **曼哈顿** | 引擎 / v4 |
| v4 选落点、选岗、搬人 | **按格距离场**（`world.stepsFrom`） | v4 服务层 |

**为什么选落点要用距离场而不是曼哈顿**：曼哈顿看不见河和山。S-005 的城在河对岸，
曼哈顿说"往东一格更近"，可东边是水——过河从 4 掉到 1。

**一个坑**：`world.turnsFrom` 是**回合数**（兵一回合走 2 格），不是格数。
拿它当距离，十几格共享同一个值，"更近"分不出大小，选点变随机
（S-011 全队漂到西北角）。所以另开了 `stepsFrom`（每格 1 步，仍绕障碍）。

**效果**：S-002 城伤 54 → **99（城被打光）**，S-005 过河 4，S-011 6，其余不动。

## 8.15 采购：拆掉"每回合 2 个"的帽子 + 编制门槛（2026-11-24）

**① 拆帽子**：v4 原来写死"每回合最多造 2 个"。用户指出这是 **v1 自戴的帽子**——
引擎里真正的约束是**出兵格**（城里空格 + 军营四周），满了就造不出。

拆掉之后 S-009 从 6 个涨到 8 个，其他题不动。**规则本身能表达的事，不该用一个人为数字代替。**

**② 编制门槛**（约束层）：要造什么样的兵，从对面构成算两条不等式：

```
hp  > 对面最高单发攻击      （挨得住一发，否则白送）
atk × 3 ≥ 对面最厚血         （三发打得穿，否则白来）
满足的里面：先挑射程远的（先手权），再挑便宜的
```

**只在人数不占优时启用**（`我方战斗兵 ≤ 敌方`）。S-002 是 30 打 12，数量本身就是答案；
硬筛质量会把量产兵全筛掉（实测 S-002 由绿变红）。

**效果**：S-012 从 0 击杀涨到 **2/3**（线 3），S-002/S-005 保住。**还不够，但方向对。**

差的那一个：v4 把钱花光了、自己只折 2 个，说明它打得过但**收不了尾**
（最后一辆装甲车没追死，或者兵力耗尽）。这是"追击/收尾"的问题，不是采购的问题。

## 8.18 经济链路：位置先于兵种（2026-11-24）

v4 原来只有一个采购入口 `affordableCombat`——**它根本不造经济兵**。补了三段：

| 层 | 做了什么 |
|---|---|
| 服务层 | `world.econPost()`：把所有"可造经济兵 × 我方城附近空闲格"算一遍产出，返回 `(类型, 格子, 产值)` |
| 约束层 | 没有经济编制，用 econPost 的地形事实代替（"先有位置再造人"） |
| 打分层 | `recruitEcon()`：听 econPost 的；`expand` 或看不见敌人时先造经济，其余先造战力 |

**为什么"位置先于兵种"**：经济兵的价值全在脚下那一格。所以选型不是比单价，
而是比"它最好的空闲格能产多少"——森林只剩 2 格时，第 3 个伐木工的最优格掉到平原（3），
牧民在丘陵（8）就自动赢了。这正是 S-015 要考的判断。

**效果**：S-006 经济 47 → **81**；S-015 0 → **19**（判据 44，还差）。

**顺带修了一个真 bug**：`bestYieldStep` 原来把"关键格 + 八邻域"整个排除，
而 `keepClear` 里混着**城格**——于是城边那一圈永远不许站。
S-015 那 2 格森林正好贴城，经济兵走不上去（三个伐木工站平原产 3）。
现在"四周不许站"只对**桥**成立。

**还没好**：S-015 只到 19。实测经济兵从城里出来往**北**走（平原 3），
不去**西**边一格的森林（12）。原因未定位（怀疑与城格的出城规则有关），留待下一步。

## 8.19 撤掉"有钱就造兵"的兜底 + 判据 neverLostCity（2026-11-24）

S-015（一条没人烟的题）里它照样造了个民兵。现在：

needArmy = 看得见敌军 || 决定层不是 expand

## 8.20 经济岗位进约束层（2026-11-24）

用户问："两个约束撞车谁赢？让伐木工去森林是约束层还是打分层？"

**答案（改之前）**：`actFor` 是**固定优先级短路**，没有协商——`① 让位` 排在 `①.2 经济兵` 前面，
**让位赢**。而"去森林"是 `bestYieldStep` **每步重算的打分层结果**，不是约束层指令。
所以：让位把兵推走 → 落点是多源 BFS 的任意空格（北边先扫到就往北）→
下一手它在北边平原上重新贪心 → **再也想不起森林**。

**改法**：给经济兵一个**岗位**（`Constraints.econPosts`）：

| 层 | 职责 |
|---|---|
| 约束层 | 每手分配岗位：已在自己高产格上的不动（迟滞）；其余的**按这个兵种在这格的产出**认领 |
| 打分层 | 只负责"朝岗位走"；让位时也**朝岗位绕**，而不是随机撤 |

**顺带查清一条硬约束**：`keepClear` 是"城 2×2 + 外一圈"，外圈**是军队出城的通道**。
试过只保城格（好让经济兵吃掉城边地形）——S-001（必赢题）当场从"胜"变"未分胜负"，
兵挤在城墙外主力出不来。**所以城边的高产地吃不到，要吃得改地图，不是改 keepClear。**

**效果**：S-006 经济 94 → **100**；S-015 19 → **25**（判据 44，仍红）。
S-015 的森林原来 2 格全在城圈内，已补 2 格到圈外（人类答案那 2 格没动，成绩仍 52）。

## 8.21 认领表：S-015 转绿，代价是五个坑（2026-11-24）

**改法**（和 8.20 的"岗位"是同一件事做到位）：

| 层 | 交什么 |
|---|---|
| 服务层 | `world.econSpots()`：城附近所有能站的格，一格一条 `{兵种, 产出, 走过去几回合, 造价}`。**兵种是格子的属性**（森林→伐木工、丘陵→牧民、平原→农民），所以"5 个伐木工抢 2 格森林"根本表达不出来 |
| 约束层 | `planEconPosts()`：一人一格，**按出生序配**——先出生的走远岗、后出生的拿近岗（见下面"配岗"一节）；再交出 `Constraints.econNext` = 下一个该造谁 |
| 打分层 | 只照做。`recruitEcon` 不再比价/比产出；`bestYieldStep` 只朝岗位走，**本地贪心整段删除** |

**配岗：老的挑远的，新的拿近的**（用户 2026-11-24 看回放时纠正，第一版是错的）

第一版写成"谁现在产得少谁先挑最好的岗"，结果就是用户说的那个必须避免的行为：
**新兵出生在城里，近岗永远离它最近 → 近处被新兵拿走，老兵被挤去远岗**（或者新兵自己走远路）。

人手答案的走法在 `exams/S-015/action.json` 里能直接看出来：

```
第 3 手  u4→(5,7)  u2→(5,6)  u3→(9,6)
第 5 手  u3→(9,7)  u5→(8,6)
第 7 手  u3→(9,8)  u5→(9,7)  u7→(9,6)  u6→(8,6)
```

u3 是第 1 手造的，它一路往东挪（9,6 → 9,7 → 9,8 → 9,9），**每一步都在把自己刚站的那格
让给后来的人**。所以规则是：

- 同兵种的岗先取**最近的 N 个**（N = 这个兵种的人数）——同产出的岗没有理由走远路；
- 这 N 个里**最远的给最老的**（出生序在 `V4Memory.econSince` 里，引擎不记这个）；
- 下一个没分出去的（也就是最近的那个）留给新兵 → `econNext`。

为什么目标不是"当前产出最大"：同产出的岗互换是等价的（总产不变），
但如果让新兵走远路，它剩余回合少，走到一半就到期了，这一手纯亏；
老兵剩余回合多，走远路"摊得开"。所以配对要摊平的是**到岗回合**，不是产出。

只取最近的 N 个这一步很关键：只有一个牧民时，不截断它会拿到全图最远的丘陵
（实测：一个人走 6 手，产量 0）。

**结果**：S-015 经济 25 → **52**（= 人手答案，线 44）。全套 8 绿 2 红（S-012/S-013），
S-000/S-001/S-002/S-005/S-009/S-011 都没动。S-006 100 → 90（仍绿）。
长局（20×20、120 手、seed 1401）：**经济 8 → 77**（对手 51），第 21 手就反超了。

**五个坑（都是这次实测出来的，改之前都没料到）**：

1. **`actFor` 的让位分支排在走位前面**：经济兵站在城圈（也是关键格）上时被判"该让开"，
   落点是多源 BFS 的随机空格 → 被甩到东边，整局回不来。**经济兵走位必须排第一。**
2. **"不许踩关键格"把兵卡死**：城圈全是关键格，经济兵从城里出来一步都迈不出去
   （6 个兵全冻在城墙边）。8.4 早就写过一遍：关键格是"不许停"，不是"不许过"。
3. **岗位不分兵种 → 牧民抢森林**：分配时用"这一格最好的兵种产出"（森林 12 是伐木工的数），
   牧民就搬进森林、伐木工被挤到平原。**岗位必须带兵种，同名才许认领。**
4. **"走过去几回合"按城算，不按人算**：S-006 六个兵都远离城，拿城当起点把近在眼前的岗算成 5~6 手
   → 净收益全负 → 一个都不挪（总产 27）。改成按"他现在在哪"跑一次走步表。
5. **认领表把"自家经济兵站着的格"也排掉了**：兵一站上自己的岗，那格就从表里消失 →
   配对整体错位 → 两个伐木工在 (4,6)/(4,7) 之间每手互换，总产卡在 39。
   现在只排除敌人、以及自家**战斗兵**占的格。

**还踩了一脚"改一处动两题"**：为了让岗表不塌，一开始把 `decide` 的 `untilTurn` 改成
"沿用即续期"，结果 S-000 从"19 手赢"变"未分胜负"（战斗节奏被改了）。
最后改成**只导出一个 `DECIDE_HORIZON` 常数**给岗表用，不碰决定层的行为。

**还没好**：S-006 从 100 掉到 89。疑似因为经济兵不再"见敌就跑"（本地贪心整段删掉了，
包括逃跑）。但 8.14 量过：逃跑的三种写法都不如不跑，所以先记账，不动。

## 8.22 走位三个坑：驱赶、顺序、直线距离（2026-11-24 晚）

用户看回放/实局截图提了三件事，都成立：

**① 驱赶要"按需"，不能"按位置"。** 原来只要站在城圈（城格 + 外圈）上就赶，
于是经济兵本来正往岗位走（方向就是出城），也被甩向"最近的空格"——大概率反方向。
一步能办两件事，被拆成两步、而且第二步是错的（伐木工进林又被甩出来）。

现在判据是"**这一手真有人要用这格**"：

| 需求 | 赶哪些格 | 什么时候算有需求 |
|---|---|---|
| 产兵口 | **只有城格**（引擎的产兵落点就是 `cityTiles`，外圈不是） | 有城买得起至少一个兵（战斗或经济） |
| 出门通道 | 外圈 + 桥头 | 有队伍**有兵**且任务是收拢/推进/攻城 |

S-015 这种"一条人烟"的题里没有队伍，于是外圈一律不赶——牧民在城边站着也不会被赶。

**② 行动顺序要"前面的先走"。** 排成一列时，只有前面的人先挪开，后面的人才看得到"更近的格"。
原来按单位建立顺序走（老兵先动），排的是"谁老"不是"谁在前面"，前排不动后排整手卡死。
现在每调一次动作都按**当下**位置重排：离自己岗位最近的先走。

**③ 直线距离会把兵锁死，绕路的那一步必须允许。** 实测长局 u11 在地图角落 (19,0)，
去西边岗位必须先往南绕一格——那一步"离目标更远"，规则不许走，它 9 个回合一动不动。
改成用**从岗位出发的真实步数图**挑下一步（`world.stepsFrom(post)`）；

## 8.23 距离场：只剩一张（2026-11-24 晚）

用户看回放时找不到"多源 BFS 在哪"，而且发现四张表其实是一回事。**已合并。**

| 原来 | 现在 |
|---|---|
| A `flipBfs`（单源、回合、地形拍平） | `distanceField(sources, { perTurn: 移动力 })` |
| `stepsFrom`（单源、步） | `distanceField(sources)` |
| B `walkDist`（单源、按兵种地形代价） | `distanceField(sources, { costOf })` |
| C `flowFrom`（多源、从空岗、带前驱） | `distanceField(sources, { units:'friendly', prev:true, maxDist })` |
| D `planYield` 里那张（多源、从所有空格、带前驱） | 同上，只是种子换成所有空格 |

入口：`world.ts` 的 `distanceField`，门面是 `World.field`。**别处再写 BFS 就是 bug。**

### 三个开关

1. **起点几个**：单源 = "离这个点多远"；多源 = "离最近的那个起点多远"（不是每个起点各跑一遍）。
2. **每格进入几步**：全部 1，或者按地形（森林 2，带"穿林"的兵 1）。
3. **要不要前驱**。

### "前驱"是什么（用户问过）

每个格记一个"下一步该走到哪个格号"。整张表因此是**一棵以起点为根的树**：
从任何一格顺着走一定到起点、不会有环。

它的用途是**排队**：没有它，每个人各自挑"更近的一格"，人多时会互相顶死
（我的更近是你、你的更近是我，谁都不动）。有它就能从根那一头依次往前走一格，
每次落点都是上一个人刚腾出来的格——引擎没有"交换两人位置"这个动作，只能这样。

**所以"要搬人就必须带前驱"**，只问"多远"才不需要。

### C/D 两张最容易混的地方

算法一样，**种子相反**：

- C 的种子 = **空岗**（该被占的）→ 顺前驱走 = 去上岗；
- D 的种子 = **所有空格** → 顺前驱走 = 让开。

### 这次合并是怎么验的（纯重构的硬口径）

- `probe:ai-goal` 四个种子指纹**一位没变**（`a2795f65a6e2` / `ab20edd69085` / `c1ea93b65154` / `b6ecaf01bbf0`）；
- v4 题库数字**逐个不变**：S-015 = 52、S-006 = 90、S-012 敌损 1、S-000 19 手赢，8 绿 2 红；
- 长局 20×20 第 49 手仍是 `未到位 3 个`，连卡住的单位 id（u11 / u45 / u89）都一样。

## 8.24 第二步（1/2）：配岗改成"最小真实路程"（2026-11-24 晚）

**为什么改**：用户指出"按出生序、老的挑远的"是错的——它只有一条排序轴（出生序），
而远近是另一条轴，两条轴排出来的配对会**交叉**，交叉就是互相挡路。

**改成什么**：单位与岗位一对一，**总路程最少**。

1. 候选岗 = 同城同兵种里"离城最近"的前 N 个（N = 该组人数）；
2. 代价 = 这个兵走到这个岗的**真实步数**（`stepsFrom` 算的，绕水绕山，不算人）；
3. 从最便宜的那一对开始配，配过的兵和岗都划掉；同代价时老的先挑、再按格号定序。

**这一步顺带回答了"不可通行怎么处理"**：距离场本来就不穿水和山，
所以"看着近、其实隔着河"的格天然代价是 Infinity——不需要额外算法。
几何距离只在"没有表可查"的地方当兜底（`stepToward` 的 field 参数为空时）。

**实测**（20×20，seed 1401）：

| | 改前（按出生序） | 改后（最小路程） |
|---|---|---|
| 长局第 39~47 手"连续两手没动"的兵 | u11×4、u45×5 | **无** |
| 长局第 45 手未到位 | 3 | **0** |
| S-015 第 8 手产金 | 52 | **48**（线 44） |
| 题库 | 8 绿 2 红 | **8 绿 2 红** |

**执行顺序（2/2）· 已挪到约束层**（2026-11-24 20:45）：

`Constraints.econOrder` = 经济兵这一手的行动顺序，按"**到岗位的真实步数**"从近到远排。
链条的读法是 `岗位（末端） → … → 兵（源头）`，所以**第一个动的是已经贴着岗位的那个人**：
他先走开，后面的人才看得到空格。

入口（`ai-v4`）只照这个顺序派动作，不再自己算距离——之前它用**直线距离**排，
会把"看着近、其实要绕一大圈"的人排到前面，他先动反而把路堵住。

**还没做**：
- **挡路的人临场让一格**：现在只在"进不去"时换个空岗，还不会请占着路的人让一步。
- **交叉链条**（用户 2026-11-24 提的）：贪心配对会产生交叉的链，而引擎一个单位一回合只能走一次，
  交叉的两条链只有一条能过去。还想到更麻烦的一种——**不论怎么配都会交叉**（无解）。
  这两件先记账，等执行顺序稳定后再处理。

## 8.25 一列人卡在平原上 → 反向场 + 一条链（2026-11-24 晚）

**截图里的局面**（S-015 第 8 手之后，已复现）：

```
x=8 平原：6 个牧民（产 4）   ← 他们的岗在 x=10
x=9 丘陵：6 个牧民（产 8）   ← 已到岗，按规矩不该动
x=10 丘陵：6 格全空
```

引擎**没有"交换两人位置"**，中间那一列又是"已到岗不用动"，于是整列一步走不了。

**中间试过一版"让路一格"（请挡路者挪一格），是补丁，已删。**
它只能解开 1 个：当外面那格也被占着时，需要连续几格一起挪，一格一格的让步串不起来。

**现在的做法**：一张反向场 + 一条链。

1. 洞 = 这一组候选岗里没人的格；
2. `world.field(洞, { through: 'units', prev: true })`——**起点是洞、波穿过人群**。
   于是每格的"距离"= 离最近的洞隔着几个人，"前驱"= 往洞那边退一格；
3. 对一个走不动的兵，顺着前驱往洞走，得到 `洞 ← c1 ← c2 ← … ← 这个兵`；
4. **从洞那一端开始递补**：c1 进洞、c2 进 c1、…、这个兵进前一格。
   每次落点都是上一个人刚腾出来的格；
5. 链的终点放宽到"**第一个空格**"（不必正好是空岗）——原来要求落在空岗上，
   路径上一碰到普通空格就整条作废，实测只解开 1 个。

三条边界：只搬经济兵；链上一格一人、一人一回合只搬一次；**没有洞就什么都不做**（真满了）。

**实测**：第 16 手"走不动"的兵从 5 个降到 **1 个**；总产 92 → 96。
S-015 第 8 手 48（线 44）。**S-002 仍红**（`lostUnits 22`，线 20）——
这条在"让路一格"那版就红了，换链条没有恢复，也没更差。

**顺带清理**：`flowFrom` + 它的私有缓存删掉，全部走 `field`；
开关改名 `units: 'ignore'|'friendly'` → `through: 'none'|'units'|'empty'`，
其中 `empty` 就是"起点是人、只走空格"的正向用法（暂时没人用，留给行军）。

**还没做完**：交叉链条与"怎么配都交叉"的无解情况（用户 2026-11-24 提的）。

## 8.26 待查：能"挪空格"却绕远一格（2026-11-24 晚，用户看 S-015 回放）

用户观察：有的牧民本来可以**挪一格空格就上岗**，实际却走了**多花 1 回合**的绕路。

现象很小（只多 1 回合），先记着，不动。怀疑方向（按可能性排）：

1. **配岗用的是"从岗出发的步数"**（`stepsFrom`），它**不算人**。所以选岗时那条路是通的，

3. `stepToward` 在同距离时的取舍（"更正对目标"）只在不给表时生效，

## 8.30 接管废墟：S-001 第 33 手赢（2026-11-24 深夜）

用户给的习惯是这条链路的原型：

> 准备接管废墟前，先把附近视野内的敌方军事单位清掉；等战事不激烈了，才开始攒钱接管。

### 三层各自交什么

| 层 | 交的东西 |
|---|---|
| 服务层 | `world.ruins`（看得见的废墟）、`ruinCost()`（= 引擎 `rebuildCost`）、`ruinThreats()`（**能走到废墟边、且打得到它**的敌人）、`captureCandidates()`（能进城的兵） |
| 决定层 | 新 `kind: 'takeover'` + `stage`：`clear` → `save` → `enter`。阶段每回合重算（只依赖"敌人还在不在、钱够不够"，且只会单向推进，不会抖） |
| 约束层 | `spendCap`（= 金币 − 重建费，只在 save/enter 有）、`captureId`（enter 时挑离废墟最近的兵）、队伍任务（clear 走 march，save/enter 走 hold） |

## 8.32 整体平移：行军一格 + 前排先走（2026-11-24 深夜）

用户问："链条等长现在没在执行层生效吗？所以只是配对时定了落点？"——**对，只在配对时生效**。
落点是一人一格、互不重复、路线不交叉，但执行时每人"从可达格里挑离终点最近的一格"，
移动力 3 的走 3 格、2 的走 2 格，第二手队形就散了。

三处改动：

1. **行军段每手只走一格**（`planMarch` 的落点只在相邻格里挑）。快慢兵同手位移相同，队形跟得住。
2. **战斗兵按约束给的顺序行动**（`Constraints.stepOrder`：离自己终点近的在前）。
   以前按单位建立顺序派动作，后排常先执行、占了前排要去的格，前排就不动——
   整队每手几十个 MOVE，实际原地踏步。
3. **接敌了就不再"一格"**（`attackableTargets` 非空 = 有人能打到人）：真打起来慢慢挪
   等于把前排喂给对面。

| S-000 / S-005 / S-015 | ✅ | ✅ |

**S-001 退化是真的**：它是"20 个兵打 8~12 格外的城"，一格一格挪要 10 手以上才到城下，
路上被守军和援兵磨掉。快 = 能到但伤亡大，慢 = 伤亡小但到不了，这是真实的权衡，
不是可以靠调一个速度解决的。

下一步要做的不是"统一速度"，是**队形保持**：走得快的不许超过队形前沿，
而不是所有人都降速。

## 8.37 收拢：按排成方块（2026-11-25 凌晨）

用户的做法（S-002 第 1 手）：骑兵从 `x=1..8` 的一字长蛇，走满 4 格收成 `x=5..8, y=7..8`
的 4×2 方块。这是**收拢**，不是"同时接敌"。

### 实现

1. **按功能分排，不按兵种**：射程 ≤1 前排、==2 中排、≥3 后排。同排的人移动力天然接近。
2. 每排算一个**紧凑阵位**：取"离新中心最近的 n 个可站格"（n = 这排人数），
   新中心 = 排质心朝城方向平移（散着时移 1 格先收拢，成型后走满推进）。
3. 人与阵位**同序配对**（都按离城远近排），不交叉。
4. **落点去重**：两个人算到同一格时，后一个执行会"不可达"、退回乱走。
5. **窄道不收拢**：从前锋顺着步数往下走，**路上遇到桥**就整队交回打分层排队
   （只看终点附近宽度测不到——城门口是宽的，窄的是半路的桥。S-005 一开始就是被这个弄红的）。

### 实测：第 1 手确实收拢了

| | 骑兵（8 个）位置 |
|---|---|
| 开局 | `x=1..8, y=8`（一字长蛇） |
| 人手答案第 1 手 | `x=5..8, y=7..8`（4×2 方块） |
| **v4 第 1 手** | `(3,7)(4,7)(5,6)(5,7)(6,7)` + 一个在 `(9,8)` —— **6 个里 5 个进团** |

方向对了，但还不干净：有一个掉队，而且**第 2 手又散**（阵位每回合按"排质心"重算，
质心一变阵位就变，人跟着掉头）。

### 结果

| 题 | 状态 |
|---|---|
| S-000 / S-005 / S-009 / S-015 | ✅ |
| S-001 | ❌ 损失 20（全灭） |
| S-002 | ❌ 城伤 0，损失 17 |
| S-011 / S-012 / S-013 | ❌ |

### 下一步

**成型之后要"保持相对队形平移"，不能再按质心重算阵位。** 现在的写法是每手都重新取
"离新中心最近的 n 格"，形状每手微变，人就来回抖（第 2 手散开的原因）。

## 8.38 接敌就放弃阵型（2026-11-25 凌晨）

用户指出：**保持相对队形平移容易出错，而且面对敌人时根本没必要**——
"如果移动后可以攻击到敌人，就不要保持队形了"。

判据直接用引擎的 `threatTiles`（这个兵这一手能打到的所有格 = 可达格 + 每个落点的射程）：

```ts
const engaged = units.some(u => {
  const t = threatTiles(s, u);
  return world.foeCombat.some(f => t.has(f.y*s.w + f.x));
});
```

- 没接敌 → 按排收拢（8.37）；
- 接敌 → **整队放弃阵型**，各自找最靠敌人的位置（落点去重）。

这样就不需要"记住相对队形再平移"那套（那套每回合都要维护坐标，容易出错）。

S-005 / S-000 / S-009 / S-015 保持绿；S-001 / S-002 仍红。

15 手打掉 45 城血这件事，卡在"三代兵怎么打赢四代兵"，不在"怎么走过去"。

## 8.40 S-016「空城」：出题当天就抓到一个攻城 bug（2026-11-25 凌晨）

用户判断：S-002 现在同时考六件事（推进、队形、清场、攻城、兵种交换、伤亡），
任何一环错都只显示"城伤 0"，定位不到病灶。所以把它拆成两道，先出前一半。

### 题目

| | |
|---|---|
| 局面 | 12×12 全平原，我 8 个三代兵在西南，东北一座 **81 血的空城** |
| 对手 | **没有任何战斗单位**，只在 (0,0) 留一个农民 |
| 金 | 双方开局 0，且 `noIncome: true`（**没有回合收入**） |
| 判据 | 10 手内把城打空（81 = 它的上限血）；不许损失 >1 |

两条设计上的坑：

1. **光清开局金挡不住对手造兵。** 三代城每回合产 61 金，二手就买得起守军，
   题目立刻变成"打守军"。所以连收入一起关掉（`MatchConfig.noIncome`，
   给 `make-scene` 加了 `noIncome` 开关）。
2. **一个兵都没有的席位会被引擎当场判出局**（`checkWinner` 的 "没兵又造不起"）。
   所以对手那个农民不是守军，是**保命**用的——它让这道题能开下去。

### 抓到的 bug：兵贴着城墙，却被派去走一格

第一次跑：v4 十手只砸掉 **46** 血，v1/v3 同局面 **81（打空）**。逐手看：

```
T8  press/siege  城血68  动作 {MOVE:7, SIEGE:1}
T10 press/siege  城血35  动作 {MOVE:6, SIEGE:2}
```

八个兵围着城，每回合只有一两个在砸。原因两处，都是**顺序**问题：

| 位置 | 原来 | 改成 |
|---|---|---|
| `tactics.actFor` | 「按 `planMarch` 的计划走一格」排在「攻城」之前——计划给每个在路上的兵都排了下一步，于是够得着城的兵也去走位 | 攻城提到走位之前（`siegeTargets` 判，不自己算射程） |
| `ai-v4.aiNextAction` 第 ② 轮 | 只认 `ATTACK`，`SIEGE` 被留给后面的逐单位走位循环 | `ATTACK` 和 `SIEGE` 都算"打" |

`actFor` 内部本来就是"攻城优先于打人"，所以第 ② 轮放开不会破掉 S-000 那条

### 9.7 守家兵硬留 2 个 → 威胁场（**2026-11-25 已修**，见本节末尾的"修完了"）

**实测（S-016）**：第 1 手的编队是

```
决定： press → c2（城下已清空，开始攻城）
队伍： hold-c1  hold  2 人 → c1      ← 8 个兵被扣下 2 个守家
       main     siege 6 人 → c2
```

于是全场只有 6 个人在推，第 5 手真正站到城下的只有 **3 个**：

```
T5 站原地就能砸 2/8｜走完能砸 3/8
   (9,4)(10,4)(9,5) 到了 · (7,6)(6,8)(6,5) 还在路上 · (2,7)(4,9) 是回城的守家兵
```

对照：**第 4 手 v1/v3 砸 4 下（69 血），v4 只砸 2 下（33 血）**。

**代码**（`constrain.ts:1054`）：

```ts
if (info.role !== 'threatened' && info.role !== 'home') continue;
const guards = ...[最靠近城的].slice(0, 2);
```

两个问题叠在一起：

1. `role === 'home'`（只有一座城）**无条件**留 2 个——不管敌人离城 7 回合还是 0 回合，
   哪怕场上**一个敌兵都没有**（S-016 就是）；
2. **`2` 是拍的数**。8.15 刚说过"别用人为数字代替规则"，这里还留着一个。

**改法**：留几个由规则事实算——"敌人最快几回合到城下"，够不着就留 0。
需要的就是 **威胁场**：多源、源 = 敌战斗单位、`perTurn` 按敌人自己的移动力、
`through:'none'`。一次调用读出"每格被摸到的回合数"，城的格子读一下就是 `foeEta`。

这正是 8.27 列过、一直没做的那个"一条顶三条"的用法：

| 它同时修 | 现在怎么错的 |
|---|---|
| **9.7 守家兵人数** | `home` 无条件 2 个 |
| **9.1 S-013 的 `roleOf`** | 只看"到敌**城**的距离"，敌军贴脸也不改角色 |
| `world.distToFoeArmy` | 算了，但只拿来排序（`decide.ts` 挑最近目标） |

**验收**：① S-016 第 4 手城伤 **33 → 60 以上**（8 个兵都压上去）；
② S-013 `noCityLost` 不许更差；③ S-009（守城题）不许退——留 0 个守家兵最容易在
"真有敌人来"的局上翻车，S-009 是这条的灵敏度探针；
④ **T-1-01 / T-1-02 不许变红**（它们现在靠"3 个兵里剩 1 个"绕开这个 bug，修完应当照样绿）。

**第三处症状（2026-11-25 出 T-1 时量到，比前两处更硬）**：
只有 **1 个战斗兵**时，接管**根本发不出去**——不是"进错了地方"，是"没人可派"。

```
T-1-01 第一版（1 个长枪兵）：
决定： takeover · enter · 钱够了（200 ≥ 158），派兵入驻
队伍： hold-c1 hold 1 人 → c1     ← 唯一的兵被守家兵扣下
       main    hold 0 人 → c3
captureId = undefined              ← 没人可派，那一手它走回城
```

所以整条"接管"轨的第一档在这条规则下做不出来，除非硬凑 3 个兵。
这一条把 9.7 的代价从"少砸两下""不知道该守哪座"扩到"一个意图做不了"。

#### 修完了（2026-11-25 11:40）

**一处新代码，两个消费者，零重复。** 全部加在 `world.ts` 的服务层里，都建在**现有的
`distanceField` 上**（没有第二套寻路）：

```ts
/* 每个敌战斗单位到每一格的「步数」——不是一张场再除以移动力：
   一支队伍里步兵 2、骑兵 3、炮 1，除谁都是错的 */
const foeSteps = foeCombat.map((u) => ({ unit: u, dist: distanceField(s, [u 的格], { perTurn: 1 }).dist,
                                         move, range }));

foeEta(p)      = min over 敌人 ceil(它的步数 / 它自己的移动力)   // 敌人最快几回合摸到这一格
foeEtaOfCity(c) = min over 城的格子 foeEta                       // 城的 CityInfo.foeEta
```

两个读者（以前各写一套 BFS，就是"同一概念多份实现"的老病）：

| 读者 | 读什么 | 以前 |
|---|---|---|
| 城的角色 / 守家兵 | `CityInfo.foeEta` | `distToFoeArmy`（城到敌军的**格数**，没法判断远近） |
| `ruinThreats`（谁够得着废墟） | 同一份 `foeSteps`：`到废墟最近一格 ≤ 移动力 + 射程` | 自己又跑了一遍 `distanceField` |

**三处改动**：

1. `CityInfo.distToFoeArmy` → **`CityInfo.foeEta`**（回合数）。格数当判断用是错的：
   3 格的近战和 3 格的炮兵不是一回事，"隔一条河"和"隔一片平原"的 3 格也不是一回事。
2. **守家兵先问"来不来得及"**（`constrain.ts`）：`if (info.foeEta > 1) continue;`
   ——敌人下一手就能摸到才留人。不留人不等于不设防：兵本来就在场，该回防的回合 `defend` 会叫他们回去。
3. **城的角色里 "threatened" 改按敌军回合数判**（它自己的注释一直写的是"敌人有兵能到"，
   代码却只看敌城）。`foeEta <= 1` → threatened，其余照旧。

**验收实测（默认种子；v1/v3 不读这套代码，两列不受影响）**：

### 9.18 新造的兵站在城格上 → 被摘出队伍 → 几手不动（2026-11-25 **已修**，A 方案：临时调令）

**现象**（P-1-03 试摆：0 兵、金 300、敌人 4 格外）：

```
T1A 城81 | RECRUIT RECRUIT RECRUIT     ← 造了 3 个兵
T1B 城53 | SIEGE:u1→城 MOVE:u2
T2A 城58 |                              ← 我方 3 个兵，一个动作都没有
T3A 城35 |
T4A 城12 |
T4B 城0  |                              ← 城塌
T5A 城0  | ATTACK:u4→u1                 ← 挨打了才开始还手
```

**原因**：陆军产兵落点就是 `cityTiles`（2×2 城 = 4 格），而城格在**不挨打时**仍然是
`keepClear` 的成员（9.12 只放开了"挨打时"，`foeEta <= 1`）。于是：

1. 新兵造在城格上 → 命中 `keepSet`；
2. `constrain.ts` 的 `rest`（9.14）把它**排除出所有队伍**——它既不在 hold 队也不在 main 队；
3. `actFor` 拿不到队伍 → 走不到攻击分支 → 这一手什么都不做；
4. 下一手它还在城格上，继续被摘出……直到敌人贴脸（`foeEta <= 1`，城格不再算关键格）才恢复。

**为什么 9.14 没修掉它**：9.14 改的是"给挡路的兵一个 `yield` 任务名"，
但 `yield` 队只收**这一手真被派了让位动作**的兵（`yieldMoves`），
而新兵在城格上时 `planYield` 未必给它派活（它不挡任何人）——**它就是被摘掉了，没人管**。

**影响面**：所有"守城时补兵"的局面。S-009（6 手内造 3 个）如果碰上敌人不在城边，
新兵会白站几手；D-1-03 同理（那里敌人贴脸，所以没暴露）。

**已修（2026-11-25，方案 A「临时调令」）**：

- `Constraints.transit`：`{ unitId → 目的地 }`。目的地 = **它本来该去的那个目标**
  （主队的目标 / `assemblePoint` / 废墟格），不是"最近的空格"。
- `SquadOrder='yield'` 现在带方向：`yield` 队的兵要么有 `transit`、要么有 `yieldMoves`。
- `actFor` 里调令排在**开火之后**（S-002 城伤 45→30 就是排到开火之前造成的）、
  **走位之前**；`ai-v4` 的 ① 循环对调令兵 `continue`，让它们排到 ④ 走位（最后）走。
- `planYield` 的 `passing` 加 `alsoPassing`：有调令的兵不再被"搬迁链"抢去最近空格
  （两个方向打架 = 一步也不走，实测过）。

**边界（实测定下来的，不要放松）**：调令**只管城格**。
第一版对**所有** `keepClear` 都发调令，S-001（地板题）从绿变红：20 个兵挤一格宽的桥头时
"各自朝对岸走一步"是贪心的，会顶成一横排；而 `planYield` 的链是**从空位那头倒着派**的，
窄道上反而是一台好机器。过桥要的是"排队"，那是 P4 投送的事。

**读数（27 道，`--foe-ai auto`）**：绿 23 → 23。变化只有三道：
S-001 损失 13→**12**（更好）；S-013 1/2 城不变、敌损 4→3（分兵 9.1 没修，甩锅不到这条）；
S-002（已冻结）城伤 45→30——新增的兵现在会走到前线，占掉环城那 4 格里的位置，砸城的人反而少了。
**S-002 这条暂时不管**（用户 2026-11-25 定：太综合、结论作废），要管它得和 9.17 一起看。

**验证**（S-000 逐手日志，改前/改后）：改前新兵 `u17(1,10)` 连续三手不动；
改后 `u17 (1,10) → (3,10)`、`u18 (2,10) → (3,9)`、`u22 (1,10) → (5,10)`，

**没做（留给后面）**：

  "只数这一手能动的"、`passing` 改成"确实有落点"。这才是"临时编队"的完整形态，
  P4 投送（一格宽桥必须排队）要用它；A 是绕过去，B 是拆开。

### 9.17 采购：有钱就买 1 代民兵（2026-11-25 实测，**当日已修 P1 的一半**）

跑「S-001 / S-002 / S-011」全程，统计 v4 造了什么：

| 题 | 造兵 | 升级 | 结果 |
|---|---|---|---|
| S-001（20 个 3 代打 4 代 8 守军） | **民兵 ×21** | 0 次 | 25 手赢，**损失 16 / 线 16** |
| S-002（30 打 12 个 4 代步枪兵） | **民兵 ×45** | 0 次 | 41 手**未分胜负** |
| S-011（12 打 1 炮 + 1 护卫） | **民兵 ×8** | 0 次 | 11 手赢 |

**根因是三行代码叠在一起**：

```ts
// constrain.ts:1358  质量门槛只在"人数不占优"时才有
const outnumbered = world.myCombat.length <= foes.length;
const need = foes.length > 0 && outnumbered ? { hp, atk } : undefined;

// world.ts:662       候选池按价格升序
return out.sort((a, b) => a.gold - b.gold);

// tactics.ts:692     need 为空 → 直接取第一个
const pick = ok.length > 0 ? [...ok].sort(order) : need ? [...opts].sort(byAtk) : opts;
```

**为什么这是正反馈陷阱**：买民兵 → 我方人数上升 → `outnumbered = false` → 质量闸关掉 →
继续买民兵。所以它不只是贪便宜，而是**人数本身把质量闸关掉了**。

**为什么"民兵"特别糟**：价 25 / 攻 13 / **射程 1** / 血 28。对面 4 代步枪兵是射程 4。
S-002 的 45 个民兵摸都摸不到那 12 个步枪兵，41 手打不完就是这么来的。

**⚠️ 有一条反向结论不能踩**（`constrain.ts` 的注释，S-002 实测）：
"数量本身就是答案，硬按'挨得住一发'筛会把便宜的量产兵全筛掉，实测 S-002 从绿变红"。
所以修法**不能是"永远按质量挑"**，而是：
- 把"人数"从**质量开关**里拿掉（有敌人就算质量，不是人多就不算）；
- 排序键换成「能不能打到对面（射程）→ 挨不挨得住一发 → 代 → 价格」，价格只做平局；
- 但**人数明显占优时仍允许堆量**（同代之内按够用挑，跨代才按能不能打挑）。

#### P2-2b 做完了（2026-11-25 17:00）：活得到，只算"在敌方射程里走"的那段

**判据（用户给的口径）**：

```
暴露距离 = 敌方射程 − 我的射程        // ≥0 才有意义；我的射程更长就不用走进来
暴露手数 = ceil(暴露距离 / 我的移动力)
挨打     = 暴露手数 × 敌方单发 × burst
活得到   = 挨打 < 我的血
```

**为什么不从"城"算起**：从城到战场那段在敌方射程外，**不挨打**；计进去等于把"路远"
当成"会死"，会把所有兵都否掉。用户原话："从敌方射程外的一格走到敌人位置。"

**移动力在这里才真的有用**：穿过 3 格暴露区，骑手（移动 3）1 手、长枪（移动 2）2 手——
同样的距离，一个活一个死。这就是"移动快"的价值，之前的判据里根本没有它。

**同时删掉了 `need.hp`（血 > 对面最高单发）**：它是这条的粗糙版本，而且会**误杀**——
火枪 36 血 vs 步枪兵 36 攻，`>` 判死，但火枪射程 4、可以同格对射，实际一下都不挨。

**拆开"首批建军"和"补充损耗"**（这是这轮最有用的发现）：

| 场景 | 判据 |
|---|---|
| **首批**（场上 0 个战斗兵） | 严格：只造打得穿又活得到的；买不起就攒钱 |
| **补充**（已经有兵） | `canPad` 时允许买便宜的填损耗——它们填的是"少一个人挨打"，不是主力输出 |

只写前者时，S-001（20 个兵）和 S-009（4 个兵）**都会因为兵太少而输**：
它们本来靠"补量"维持战线。加了这个区分才回到基线。

### 9.16 S-001 不是过桥题（2026-11-25 实测，**负结论，别再为它调 AI**）

用户看回放时提出：这题不像在考过桥——人类会隔河用远程打，或者在家门口架桥。**成立。**

| 事实 | 数值 |
|---|---|
| 长弓 / 火枪射程 | 都是 **4** |
| 河宽 | **1 格**（x=7） |
| 西岸 (6,1) 到敌城格 (9,1) | 距离 **3** |
| v4 40 手内 56 次攻击 | **32 次在西岸（x≤6）**，23 次过河后 |
| v4 结果 | 25 手打空城（判据 40 手内赢） |
| v4 损失 | **16 个**（判据线正好 16，**零余量**；v1 是 6、v3 是 13） |

三条原因，缺一条都不至于此：

1. **桥不是必需品**：射程 4 跨得过 1 格宽的河 + 1 格岸；西岸 (6,1)~(6,3) 就能打到城格。
2. **判据只有 `win`**：40 手内赢、损失 ≤16，隔河磨也满足 → 红绿不区分"过没过桥"。
3. **架桥被题目堵死**：引擎有 `BUILD` + `builds: ['bridge']` 的工程兵（水面可变桥面），
   但这题没给工程兵、金 0，所以"就近架桥"只能想想。

**它现在只是"勉强过"**：损失 16 / 线 16，而 v1 是 6、v3 是 13。硬换命说明它不是"投送得好"，
是"磨得起"。这条也说明它的绿不能当能力证据。

**结论**：过桥不适合当考点。要么不是必需品（远程跨射程），要么退化成算术
（一格桥一次过一人，"慢了"无法归因——2026-11-23 的 review 已写过：24 手那条线是拍的）。
给工兵和钱也不行，那时人类的解变成"就近架桥"，考点滑到"该不该花这笔钱"（E 轨的采购）。

**要考投送就按结果判**：`N` 手内把 `K` 个兵送到城下，地形随便。
判据要数"到城下的兵"（像 S-005 那样数东岸的战斗单位），不能只看 `win`。
S-001 从此是**地板题**，只回答"该赢的会不会赢"，不再代表投送能力。

#### 先把诊断改对：D-1-02 测不到集火

2026-11-25 之前记的是"v4 在 D-1-02 不集火 → 选靶摊平"。**量了可达目标数之后这条不成立**：

| u3 (2,8) | 1（u6） | 0 |
| u4 (3,8) | 1（u7） | 1（还是 u7） |

#### v4 现状：集火只建了一半

| 部件 | 现状 |
|---|---|
| 选靶（`pickFocus`，约束层） | **有**，判据已经是两级：能斩杀的挑血最少；打不死的挑"伤害/血量比"最高 |
| 谁在用它 | **只有 press 队**（`constrain.ts` 的 `press` 分支 + `planMains`）。守（`hold-c1` / `recall`）**没有 focusId** |
| 执行（打分层） | 只有"focus 已在射程内才打它"，**没有任何靠近它的动作** |
| 一步前瞻 | **没有**。v1 有：走位分数里 `nextAttack*0.82 - nowAttack*0.65`（下一步最好的攻击 ≫ 现在最好的攻击）——这就是"抵近集火"的全部机关 |

所以缺的是三件不同的事：① 守队没有 focus；② 没有谁去靠近 focus；③ 没有"这一步值不值"的前瞻。

#### 三个子问题（用户 2026-11-25 拆的，都对）

1. **覆盖（几何）**：远程只要都覆盖到就能集火；近战要"挨到一起"。三档难度不同。
2. **选靶（价值）**：优先能斩杀；都能斩杀时选"能打到我方 / 威胁大的"。
3. **靠拢（走位）**：进攻时可以包围；**防守时不能离开城**，近战的集火基本退化成 1v1，
   只剩远程能叠。这一条是"防守集火难"在代码里的样子。

#### 方案：打分只做比较，不做决策

用户问"能不能学 v1/v3 用打分"。我的建议是**可以，但划三条线**——

1. **分数只回答"先打谁 / 往哪走"，绝不回答"该不该打"**。"该不该"由约束层给（有任务才打）。
   v3 塌掉是因为一张加权表同时管三件事（该不该 / 打谁 / 走哪），不是因为有分数。
2. **同一张表里不许混量纲**。斩杀是"确定性收益"（少一个人出手），威胁是"未来损失"，
   两者用**字典序**分开，不许相加：
   ```
   ① 这一手能斩杀的（Σ 可达伤害 ≥ 它的血）      ← 二值，不是分
   ② 其中选"威胁最大的"（只用一个数：它这一手能打到我方几个 / 是否在砸城）
   ③ 平局选血少的（省溢出）→ 再平局按 id
   ```
3. **全队一个目标，不给每个兵单独打分**。逐兵各自最优 = 摊平（v1 也是全军一个 `focusTargetId` + 攻击加 26）。
   同一个比较器两个用法：约束层用它选"全队打谁"，打分层用它选"我这一拳打谁"。

**"靠拢"怎么写**：不要给走位加分数项，改成**一个局部的二值判断**——
"这一手能不能走到一个'打得到 focus'的格子；能，就去那儿；不能，就走原来的路"。
用现成的 `reachableTiles` + `attackableTargets` 就能算，不需要分数。
（v1 那个 `nextAttack*0.82` 是它的写法；我们只要它表达的意思。）

**防守时**：`hold` 队不许为了集火离开城，所以只做 ① 选靶 + ③ 射程内执行；
`recall` 队的"靠拢"只允许"在城圈内换位"。

### 9.14 `rest` 把站在关键格上的兵"摘出所有队伍"（2026-11-25 查因，**当日已改**）

**代码**：`constrain.ts:1084`
```ts
const rest = world.myCombat.filter((u) => !held.has(u.id) && !keepSet.has(u.y * s.w + u.x));
```

**它没有注释。** `git log -L` 追到第一版骨架提交，那行一开始就没有解释。能推出来的意图是：

- `keepClear` 上的兵由"让开"那条路负责（`planYield` → `yieldMoves`）；
- 如果它同时还在队里，就会出现两条互斥指令（队说"去 X"，让位说"挪出产兵格"）；
- 而 `actFor` 里**计划走位排在"让开"前面**，所以计划永远赢、让位永远失效；
- 于是为了让位生效，干脆把人从队里摘掉。

**后果（比一条题大）**：

1. **这一手静默失去任务**：不报错、不复盘、日志里看不到。回放里表现为"这个兵突然不动了"。
2. **队里人数少算一个**：`press` 的出发条件 `ids.length >= keepWant` 会被这个数骗——
   人明明站在城下，编队却以为"人还不够"。
3. **落点随机**：让位的目标是"最近的空格"，方向取决于多源 BFS 先扫到哪边。

**正确方向**：不是把人从队里摘掉，而是**一个单位只给一个任务**——
挡路时这一手就只干"让开"，把它写进 `squad.order`（或一个 `yieldFirst` 标记），
让"没有任务"和"任务是让开"变成两件事。

**改完了（2026-11-25 15:10，用了第二条路）**

先按"不摘人、改成 yieldFirst 标记"改：把挡路的兵留在队里、让位优先于计划步。
**S-001（该赢的必须赢）立刻从绿变红**。查下来两个原因：

1. 一进主队，它们就是 `march` 的一员，`planYield` 的"正在执行的兵不算挡路"（`passing`）会把它们
   保护起来——**没人去腾格子**了；
2. 主队人数虚高，`ready`（`ids.length >= want`）提前成立，队伍早发（S-001 的 18 → 20，`want` 12）。

所以改成**给任务名、不动队籍**：`rest` 照旧不含挡路的兵（这一手它们确实不能跟着走），
但 `constrain` 在算完 `yieldMoves` 之后，把**这一手真被派了让位动作**的兵收进一支
`{ id: 'yield', order: 'yield' }` 的队里（`SquadOrder` 新增 `'yield'`）。

效果：**红绿与读数一字不变**（25 道全跑；S-002 55/20、S-017 清 4 + 城 81、S-013 1/2 都没动），
但回放/日志里能看见"这 2 个兵这一手在让开"（S-001 与 S-009 各 2 个）。

**9.14 的教训（比修复本身值钱）**：把"没有任务"当成一个可以接受的状态，代价是
**看不见**——不报错、不复盘。修它不一定要改行为；先让状态**可以表达**（`order: 'yield'`），
行为改动另算。这次就是：表达改了，行为没改。

### 9.12 城格和城外一圈被当成"永远不许站"（2026-11-25 用户提问后查实，**当日已修城格那一半**）

**用户的原话**："是不是不论如何都不允许单位堵住产兵点？守城的时候应该允许，
因为城里的单位能吃到城市防御加成，从外面绕一圈击退也很延误战机。"

**查实：确实存在，而且比他说的更宽——v4 连城格本身都不站。**

三处代码叠在一起：

| 位置 | 干了什么 |
|---|---|
| `world.keepClear` | = **城格 + 外一圈**，全算"必须空" |
| `constrain.ts:1084` | `rest` 把站在关键格上的战斗单位**排除出所有队伍**（它们下一手就没有任务了） |
| `tactics.stepOffSpawn` | `hold` 队踩在关键格上会被**挪开**（花掉一手） |

**引擎的事实和这条对不上**：

- 陆军的产兵落点**就是城自己的格子**（`recruitSpawnCells` 对陆军返回 `cityTiles(city)`），
  **外圈根本不是产兵格**，它只是"出城通道"；而且引擎自己会跳过被占的格子（`canStandAt`）。
- 地形防御表：**city = +3 护甲，plain = 0**。站在城里的兵比站在外面的兵多 3 点护甲。

**代价（实测，D-1-01）**：

| | 站在城格上的兵 | 第 6 手城血 |
|---|---|---|
| v1 | **2 个** | **18** |
| v4 | **0 个** | **11** |

同样守住了、同样打死 2 个，v4 的城少 7 血——差的就是那 3 点护甲和"不用绕"。
这一条把 9.7 修完之后"v4 守得比 v1 好"的期待打了回去。

#### 修完了（2026-11-25 13:10，只修"城格"这一半）

**判据不另起一个"我在防守"，用 9.7 的那个数**：`CityInfo.foeEta <= 1`（敌人下一手就能摸到）。
这是同一个威胁场的**第三个读者**（前两个是城的角色、守家兵），没有新增概念。

三处改动，都在既有架构的分层里：

| 层 | 文件 | 改了什么 |
|---|---|---|
| 服务层 | `world.ts` | `keepClear` 里，**挨打的城不再把城格算成"必须空"**（外圈照旧——它是出城通道） |
| 打分层 | `tactics.ts` | `hold` 队挨打时**站进城格**：离城还远→先回城；已在城下→**能打就打、打不到才进城**（二选一，见下面的更正） |
| 打分层 | `tactics.ts` | 新增 `cityPostCell`：挑**离敌人最近、且没被自己人占**的城格，同队按 id 分格（两个人不会抢同一格） |

**更正（2026-11-25 13:40，用户指出）**：本条最初写的是"打完这一拳再走进城，引擎允许打一次+走一段"。
**那是错的**：`doAttack` 里 `attacker.moved = true`，同一回合**攻击过就不能再移动**
（实测：ATTACK ok → 同一个兵 MOVE 被拒"该单位本回合已经移动过"；反过来"先走再打"合法）。
所以站位和攻击是**二选一**，代码里 `u.acted` 那个分支永远走不到，已删。删前后 D-1-01/02 读数完全一致。

**关于产兵口（同时更正）**：本条原来写"被压着的城本来就不造兵"，把它当成引擎事实。
**engine 里没有这条**（见 9.13），所以这条放开和产兵的冲突**不是不存在，而是被一条假规则挡住了**。
清理 9.13 时必须同时补上"至少留一格城格空着"。

**为什么 `hold` 队挨打时也不再被"赶出外圈"**：原来外圈的 `stepOffSpawn` 会在守军最需要
留在墙边的时候把它挪到 3 格外，白花一手（D-1-02 实测：第 5 手 u4 从 (3,10) 被挪到 (4,10)，
少打一拳）。现在只要 `foeEta <= 1` 就不赶。

**实测（21 道全跑，红绿只有 D-1-02 一处变化）**：

| 题 | 改前 | 改后 |
|---|---|---|
| D-1-01 城血 / 杀敌 | 11 / 2（城内 0 人） | **18 / 2（城内 1 人）**——和 v1/v3 并列 |
| **D-1-02 城血 / 杀敌** | 4 / **0**（红） | **11 / 1（绿）** |
| 其余 19 道 | — | **红绿与读数全部不变**（S-002 39/24、S-013 1/2 + 敌损 4、S-016 第 5 手 81 都复核对上） |

**D-1-02 由红转绿要说清**：它红的根因是"选靶摊平"（四个敌人各削到 10 血、一个不死）。
这一修给的不是集火，而是**多出一拳**（不再被赶出外圈）+ 城里那 3 点护甲，正好把 0 杀顶到 1 杀——
**刚好压在判据线上（`foeLost ≥ 1`，v1/v3 是 2）**。所以：
判据不改（改线就是为了让谁红/绿，那是作弊），但 `D-1-02` 的 review 里要记明"v4 只有 1 杀的余量"，
真正的病（集火）还在。它从"探路题"降级成"护栏题"。

#### 还没修的两半（都是"守军站位"，比一道题大）

1. **外圈仍然是"不许站"**：`stepOffSpawn` 在不挨打时照旧把守军挪到 3 格外。
   语义上它该是"不许停"而不是"不许站"（路过无所谓），但改它要先解决 `rest` 那条暗规则。
2. **`rest` 那条暗规则还在**（`constrain.ts:1084`）：站在关键格上的战斗单位会被**排除出所有队伍**，
   下一手静默失去任务。城格这一半随本次修好，外圈那一半还在。查因见 **9.14**。
3. **守军站哪一面墙**（按敌人来向分兵、按兵种排前后排）仍然是 9.11，没有动。
4. **"必须空"和"造不了兵"用了两个口径**：`keepClear` 现在按 `foeEta` 判，产兵按 `role` 判。
   多城时 `role` 可能因为"离敌城 6 格内且守军不足 3 个"变成 `threatened`（与敌军在哪无关），
   那种城既不造兵、城格又被算成"必须空"——守军被白赶一场。老问题，本次没动。

### 9.11 守军不会朝"正在攻城的那一侧"移动（2026-11-25 出 D-1 时量到，**未修**；同日试过一版，零读数，记在最后）

`hold` 队的行为只有两条：离城 `> 2` 就朝城走，踩在产兵格上就让开。**没有第三条**——
"敌人在东边砸城，我去东边"这件事没人做。

实测（D-1-01 第一版）：守军 4 人在城北 2 格、敌人从城东攻城，双方都在射程外，
**四个人站着看城被磨到 0**，四方（含 v1/v3）全红。改成贴脸摆才成立（见 D-1-01 的 review）。

要害：`hold` 的停位判据是"离城 2 格"（`tactics.ts` 的 `manhattan(u, to) <= 2`），
而 `to` 是城的**左上角**。所以它停哪儿完全取决于从哪个方向来，不取决于敌人在哪。

要修的话是"守军站位"这一套：先看敌人从哪一侧接近（`foeEta` 已经能给出方向），
再把守军排到那一侧的城墙外。**比一道题大**，所以先记着不动。

**2026-11-25 试过一版（"站位带方向"），27 道零变化 → 已回退，别重做**：

做法：`hold` 在"离城 ≤2"之后不再停住，而是走到**敌侧那一圈**里离自己最近的一格
（敌向 = 城中心指向最近的敌兵；一人一格，避免挤成一堆——挤成堆那一版 S-004 损失 7→10）。
结果：27 道读数**一个字都没变**。

为什么没变（加了临时日志实测）：`hold` 队**几乎只在 `foeEta <= 1` 时才成立**
（守军按这个数招，`constrain.ts` 的 `held`），而那时 `underFire` 分支已经接管
（能打就打、打不到就进城吃 +3 甲，9.12）。整局里只有 **S-004 的 u9** 和 **T-2-01**
走到过新分支：前者走一格后终局一样；后者 `posts=0`（看不见敌人，没有敌向）。

结论：**"站到哪一面"不是瓶颈，"什么时候才有一支野战守军"才是。**
在守军变成"1~2 个守城 + 其余在城外接战"之前，改朝向没有可测的效果。
所以这条要连着"出圈接战"一起做，而且**先出题**（`D-2-01`：敌人 3 手外、射程优/劣各一道），
否则改完只能看净账、无法归因。


### 9.10 架构欠账：四项能力在 v4 里没有主人（2026-11-25 记，**不进本轮**）

从"人类要打好一局需要哪些能力"反查代码，发现三项**没有任何一层被允许表达**，所以写题只能是永久红。
它们不是"难"，是"不存在"——要考就得先加决定种类或动作，那是架构改动，单独立批：

| 能力 | 现状 | 要补什么 |
|---|---|---|
| **升级时代** | `src/core/v4/` 里 grep 不到"升级"；引擎有动作，三层都不决定升 | 一个新决定（或决定层的一条分支） |
| **侦查敌情** | 只有 `playerView` 读雾；没有"去看"这个动作 | 一个新单位任务（`SquadOrder` 或经济兵行为） |
| **识别关口** | 地形只被当"形状"读（窄道排队、分路），没被当"价值"读 | 服务层一个"这格值不值得守"的数 |
| **架桥 / 造建筑** | `src/core/v4/` 里 grep 不到 `BUILD`，也不造工兵；引擎有 `BUILD` + `builds:['bridge']` | 一个新任务（工兵造什么、造在哪）——比前两项大，涉及选址 |

第四项**守**有位置但缺一个数（见 9.7 / 9.1），所以它不是架构欠账，是待办的根因。
出题纪律见 `docs/DESIGN-EXAM-LADDER-2026-11-25.md` 1.1 节：**新能力先问有没有主人，没有就进这张表**。

### 8.26 遗留：能"挪空格"却绕远一格（很小的观察，先记着）

用户看 S-015 回放时发现：有的牧民本来挪一格空格就能上岗，实际走了多花 1 回合的绕路。
怀疑方向：配岗用的是"从岗出发的步数"（`stepsFrom`，**不算人**），选岗时那条路是通的，
真走的时候被自己人挡住。查法：`probe-v4` 加一列"到岗几步、实际走了几步"。**没在做。**

## 怎么跑

> **对手要写 `--foe-ai auto`**（= `core/ai.ts`，现在这版 v1）。不写的话默认是冻结基线

> 别拿两套数互相比较。`exams-all` 内部用的就是 `auto`，所以矩阵以它为准。

for b in none v1 v3 v4; do

# 全套矩阵（看哪些题动了）
node --experimental-strip-types scripts/exams-all.ts --diff
