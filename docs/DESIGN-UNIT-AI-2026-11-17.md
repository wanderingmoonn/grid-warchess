# 单兵 AI（自主分）· 改动清单

> 2026-11-17。这是**改动清单**，不是数值设计。boss 的数值、演出、阶段流程都还没定，
> 这份文档只回答"机制怎么接进引擎、接在哪、有哪些不许碰的地方"。
> 实施顺序见 `PLAN-UNIT-AI-2026-11-17.md`。
>
> 需求来源：修真扩展包要做一个"按特定流程行动"的 boss（扩展包「黑暗动乱」），
> 而现引擎只有一套按席位算分的 AI，兵种之间没有行为差异。

---

## 1. 目标 / 不目标

| 要做 | 不做 |
|---|---|
| 让兵种可以带一份**自己的**行为（什么时候放技能、往哪走、打谁） | 不让单兵 AI 管造兵、升级、换血、复活（席位级） |
| 用"自主分"当权重：0＝全听全局，1＝全局只在它没意见时补位 | 不改全局估值 `positionValue`、不改寻路、不改队形 |
| 接口是通用的，任何扩展都能用 | 这一轮不做 boss 的具体数值和演出 |
| 默认 0，**老对局行为一个字节都不变** | 不给普通兵种填非 0 的默认值 |

一句话：**核心只提供"什么时候问、问到的东西怎么接进去"；想怎么打，归扩展包。**

## 2. 现状（改之前必须知道的东西）

AI 选招是四步，全部在 `src/core/ai.ts` 的 `aiNextActionCore`（约 5876 行）里：

1. **生成候选**：`unitCandidates`（3298）为每个兵生成"打谁 / 围哪座城 / 走到哪一格"，
   `heroSkillCandidate`（3545）为每个兵生成一个技能候选。
   结果是**一张全局扁平的候选表**——所有兵、招募、建造、升级、换血混在一起排序。
2. **打分**：`score` 是经验凑出来的：推进距离×6 + 地形值×1.5 + 这一步能打到谁×0.82
   − 会被几个人打的惩罚。分数≤0 等于"这一步不值得做"，最高分≤0 时直接返回 null（6290），
   也就是这一手什么都不干。
3. **推演削分**：前 6 名（`LOOKAHEAD_K`）会被真的试走一次，再按
   `0.35 ×（试走后对手最狠的一刀 − 现在最狠的一刀）` 扣分（6216）。这是防送设计。
4. **挑最高**：分差在 1.5% 以内按 `aiNoise` 随机挑一个（6302）。

另外两个会影响设计的事实：

- **深推现在是关的**（`PLAN_ON = false`，5735）。它会把前几名各试走三回合再重排，
  一旦打开，单兵 AI 的分会被整体推翻。现在可以不管，但要知道它在。
- **AI 只认雾图**：`const view = playerView(s, me).state`（5899）。它和玩家看到的信息一样多。
  单兵 AI 必须守同一条线，否则 boss 会隔墙开大。

## 3. 数据模型（两个字段 + 一张表）

### 3.1 兵种表加两个字段（`src/core/types.ts` 的 `UnitTypeDef`）

| 字段 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `aiAutonomy` | `number` | `0` | 自主分，0~1。**0＝完全听全局**，写字段＝写"这个兵自己那套判断打几折" |
| `aiProfile` | `string` | 无 | 行为表的名字，指向扩展注册的实现。没有这个字段就算自主分也是 0 |

约定：**两个字段缺任何一个，行为都等于现在的 AI。** 老存档里没有这两个字段，读出来是
`undefined`，按 0 处理——所以不会因为升级版本改变旧对局。

> 为什么不把"怎么想"也写进兵种表：兵种表是纯数据（要进存档、要序列化、规则书要读）。
> 函数塞进去会让它不能序列化。和装甲模块、留痕种类是同一个理由。

### 3.2 扩展表加一段（`src/core/expansions.ts` 的 `Expansion`）

```
unitAi?: UnitAiProfile[]
UnitAiProfile = { id: string, handler: (c: UnitAiCtx) => UnitAiResult }
```

和 `abilities` / `marks` 完全同构：**实现跟着扩展走，删掉扩展就跟着消失。**

### 3.3 注册表（新文件 `src/core/unit-ai.ts`）

照 `mark-registry.ts` 的写法：遍历 `EXPANSIONS`，把每个包的 `unitAi` 收进一张表。
对外两个查询：

- `unitAiOf(s, unit)` → 这个兵有没有可用行为（没有就返回 null）
- `allUnitAiProfiles()` → 给界面/规则书用（"这个兵有专属行为"这类说明）

查不到 profile（兵种写了名字、包里没注册）时：**按 0 处理，并打一次 `console.warn`**。
静默降级是这套代码里最容易查不出问题的一类 bug（参考关卡 `spawn` 落空那次）。

## 4. 接口契约

### 4.1 输入（核心给扩展的）

| 名字 | 是什么 | 注意 |
|---|---|---|
| `state` | **雾图投影**（`playerView` 的结果） | 看不到的敌人不在里面。**不许**再回头读真局 |
| `unit` | 这个兵 | 已经是克隆体，改它没有副作用，但也没意义 |
| `def` | 兵种定义 | 读 `aiAutonomy` / 技能表用 |
| `api` | 能力层那套工具（`canStandAt` / `distance` / `spawn` / `pushLog`…） | 只用来**查询**，不许在 handler 里改局面 |
| `candidates` | 全局已经给这个兵算好的候选（只读） | 想知道"全局本来想让它干什么"就看这里 |
| `rejected` | 这一回合已经被拒过的动作 | 别重复提同样的东西 |

### 4.2 输出（扩展还给核心的）

```
UnitAiResult = {
  add?:  Array<{ action: Action; score: number; ignoreRisk?: boolean }>
  must?: { action: Action; reason?: string }
}
```

就两项，别再扩。理由见 4.4。

- **`add`**：这个兵"自己想做"的动作。`score` 是**已经换算成全局量级**的分
  （换算表见第 5 节）。生效分 = `aiAutonomy × score` —— **自主分就是这里的权重**。
- **`must`**：这一回合**必须做**的那一手。不受自主分打折，给固定高分
  （沿用代码里已有的量级，见 4.3）。最多一条。
- **`ignoreRisk`**：让这一条候选跳过第 3 步的"推演削分"。只给演出型招式用。

### 4.3 三道门的处理（最关键的一节）

| 门 | 单兵 AI 会怎样 | 处理 |
|---|---|---|
| `best.v <= 0` → 什么都不做 | 局部分如果落在负区，boss 会站着发呆 | `add` 的 `score` 必须为正；文档里给量级表（第 5 节） |
| 推演削分 ×0.35 | 跳进人堆放大招会被削成负分 | 这类候选标 `ignoreRisk: true`；普攻**不许**标 |
| 分差 1.5% 内随机 | "必须做"如果只是略高，会被随机吃掉 | `must` 给固定高分。现有先例：英雄技能 +300（6088）、指挥官指定升级 +1000（6163）。**取 1000** |

另外：`must` 被规则拒掉（冷却没好、目标死了）之后，**不能反复重提**——`rejected` 表
已经覆盖这一步，前提是扩展不要绕过它自己造 key。

### 4.4 为什么只有两项，没有"偏好加权"

讨论时提过"用自主分给全局分乘一个偏好系数"。落地时改成现在这个形状，原因是尺度：
全局分是经验凑出来的（推进×6、地形×1.5…），局部分如果也乘上去，两套量纲会互相污染。
现在这个写法里，**乘法的方向是"自主分 × 局部分"**——乘的是同一个已经换算好的量，
只是打折，不会改变量纲。

好处还有一条：接口越窄，以后越不会自己咬自己。如果哪天真需要"改全局估值"，
那是另一个需求，不该从这个小口子里长出来。

## 5. 分数换算（唯一需要经验的表）

扩展自己提的动作（放法术、召唤、横扫）没有全局分，得自己给。这张表是**起点**，
最后要靠探针实测校准（`probe:unit-ai` 会把每个候选的排名打出来）。

| 这个动作大概值 | 参考分 |
|---|---|
| 走一步（有推进） | 3 ~ 6 |
| 走一步（只是躲避/占位） | 1 ~ 3 |
| 打一下（没打死） | 10 ~ 40 |
| 打死一个普通兵 | 40 ~ 120 |
| 打死一个贵兵/英雄 | 120 ~ 300 |
| 抢一座城 / 打掉城防 | 60 ~ 150 |
| 造一个兵 | 20 ~ 80 |
| **必须做（`must`）** | **1000** |

校准方法：先给一个估的数，跑探针看它在候选里排第几；如果它一直选不上，是分给低了；
如果它抢走一切（比如该补刀的时候去放法术），是分给高了。**这一步没有公式，只能试。**

## 6. 插入点（`ai.ts` 里具体接在哪）

位置：`aiNextActionCore` 里那个 per-unit 循环（约 6085 行，现在是
`for (const u of unitsOf(view, me)) { unitCandidates(...); heroSkillCandidate(...) }`）。

顺序：

1. 先跑原来的 `unitCandidates` + `heroSkillCandidate`（不动）。
2. 如果这个兵有 `aiAutonomy > 0` 且有 profile → 调 handler。
3. 把 `add` 里的每一条 **乘 `aiAutonomy`** 之后推进候选表。
4. `must` 存在且不在 `rejected` 里 → 用固定高分推进候选表。
5. 后面的四道门原样生效（不插队、不提前返回）。

三条硬约束（写进实现注释，别省略）：

- handler 拿到的必须是 `view`，不是 `s`。
- handler 每步都会被调用一次（一回合最多几十次 × 单位数），**必须便宜**，
  不许在里面做全图 flood fill、不许 `structuredClone`。
- handler 不许有副作用（不许 `u.hp -=`、不许 `s.units.push`）。想改局面只能靠 `action`。

### 6.1 允许返回哪些动作（白名单）

单兵动作：`MOVE` `ATTACK` `SIEGE` `HERO_SKILL` `USE_DEVICE` `MOUNT` `UNMOUNT`
`LOAD` `UNLOAD` `LAUNCH` `RECOVER` `RECHARGE` `BUILD`。

禁止：`END_TURN` `RECRUIT` `UPGRADE` `SET_ORDERS` `SET_DIRECTIVE` `DISBAND`
`DRAFT_*` `SURRENDER` `PLAN_*`。

理由：后面这些是**席位级**决定。让单兵 AI 能造兵，等于绕过整套招募规划
（编制、省钱、换血、时代取舍），一定会出现"某个兵自作主张把钱花光"。

还有一条：`action.unitId` 必须等于被问的那个兵。核心要**断言**这一条，
否则一个扩展能替别的兵做决定，那套"协同"就废了。

## 7. 步数上限：50 是历史遗留，要拆

### 7.1 事实

- `AI_MAX_STEPS = 50`（`ai-meta.ts`），注释写着"防止无限循环"。
- `CONFIG.maxUnits = 24`（`config.ts:45`）。一个兵一回合能走一步、打一下 = 2 个动作，
  24 个兵就是 48，再加上 2 次招募（`DEFAULT_BUDGET`）+ 1 次升级 + 建造/装配/换血，
  **理论上限确实超过 50**。
- **但实测从未接近它。** 2026-11-17 用 `npm run probe:ai-steps` 跑了 18 局
  （中世纪 16×16 / 信息化 20×20，各 3 局 × 2 档，另 2 局短测），结果一致：
  每回合动作数 **平均 8.2~8.5，p90 12~16，最大 23**，撞上限 **0 次**。
  原因很实在：AI 在"没有值得做的事"时就返回 null 收手（`best.v <= 0`，ai.ts:6290），
  20 个兵里常常只有 8 个觉得该动。**所以"24 兵 × 2 = 48"是个走不到的上限。**
- 结论修正：50 **现在不是瓶颈**。拆它的理由是"将来"——单兵 AI 上线后扩展会主动
  提正分动作，步数才涨得起来；那时再动它，会把"名额变化"和"单兵 AI 效果"混在一起，
  说不清是谁造成的。

### 7.2 改成什么

不是"取消上限"，而是**换成按规模算 + 卡死检测**：

| 机制 | 值 | 作用 |
|---|---|---|
| 自然上限 | `8 + 6 × 本单位数 + 6 × 本城数` | 每兵 6 = 走一步 + 最多 4 段攻击（`burst` 最高 4）+ 技能；每城 6 = 招募 2 + 升级 1 + 建造余量。24 兵 + 3 城 = 170 |
| 卡死检测 | 同一个动作 key 连续成功、局面指纹没变，第 3 次判定卡死 → 交棒 | 真正的无限循环保险。**只认同一个动作重复**，不是"连续三步都没变化"（后者会误伤"三个兵依次进架势"这种正常打法） |
| 指纹 | 站位 / 血量 / moved·acted / 单位数 / 金币 / 城 / 留痕 / 胜者 | **不含 `unit.custom`**——扩展开关形态只改那里，算进去就永远抓不到空转 |
| 告警 | 撞上限、判卡死都 `console.warn` | 下次有人撞到能立刻看见，而不是静默截断（`main.ts` 已加） |

`AI_MAX_STEPS` **不要删**：`scripts/baselines/*` 和几十个脚本 import 它，删了等于
把基线一起打断。做法是保留常量并标 `@deprecated`，新加 `aiStepCap(s)` 给主流程用；
跑批脚本的迁移单独一步做（见计划）。

### 7.3 为什么必须单独一步做

改步数＝改 AI 行为＝**208 场基线不再可比**。所以它必须是一个独立提交，
而且要在单兵 AI 之前做完——否则两种变化混在一起，跑出来分不清是谁的效果。

### 7.4 为什么不直接删掉（2026-11-17 讨论过）

结论：**值得保留的是"有界"，不值得保留的是"50 这个数"。**

"有界"真正救了什么——一个死循环长什么样：

> AI 每一步都会重建候选表。如果某一类动作**成功了但局面没变**（形态切换、
> 开关类 buff、"进入防御姿态"这种），它下一步还是会看到同一个正分候选，
> 于是无限次重复。`rejected` 只记"被规则拒掉的"，记不住"成功但没用的"。

这正好和本项目有关：boss 的"切换形态"就是这种动作。**也就是说，
单兵 AI 会让"无进展动作"的来源变多**（动作来自扩展，引擎管不到），
所以"拆 50"的前提是"先有卡死保险"，顺序不能反。

直接删掉的四个坏处，按严重程度：

| 坏处 | 后果 | 能不能避免 |
|---|---|---|
| 死循环没有任何兜底 | 整局卡在同一回合，**而且每次读档都卡**（存档就停那一帧） | 不能，必须先有保险 |
| 56 个文件 import 它 | 编译直接失败一片 | 能：保留符号，只改主流程的使用点 |
| 跑批的循环上限跟着变 | 同一批种子的对局长度变了 → 历史结果不可比 | 能：跑批脚本这一轮不动它 |
| 统计字段失真（`steps === AI_MAX_STEPS`） | `capHits` 永远为 0，看着像"问题解决了" | 能：改成 `>=` 或跟着换名字 |

顺带一个发现：**"基线冻结"本来就没冻干净。** 12 个基线里，10 个是
`export { AI_MAX_STEPS } from '../../src/core/ai-meta.ts'`（转发活常量），
只有最老的两个自己写死了 50。所以动 `ai-meta.ts` 那个值，会连带改掉这些基线的
回合长度。冻结的是"决策函数"，不是"回合长度"——这件事以后调基线时要知道。

三档选择：

| 方案 | 做法 | 评价 |
|---|---|---|
| A 直接删 | 删常量、删循环条件 | **不做**：编译炸、无兜底、历史数据全废 |
| B 换自然上限＋卡死检测 | 主流程用 `aiStepCap(s)`，老常量留着给跑批 | **推荐**，就是本方案 |
| C 只把 50 调大（如 200） | 一个数字的事 | 可作**过渡**：能立刻量出"截断到底影响了多少"，但没有"为什么是 200"的理由 |

## 8. 红线（不这么写就会坏）

1. **默认 0。** 任何兵种默认有自主分，都会改变现有对局，208 场基线全部作废。
2. **只在 `level.units` 的关卡 boss 上填值。** 普通兵种一个都别填。
3. **handler 只拿雾图。** 拿了真局＝boss 开图，玩家一眼看出来，而且回放/联机会坏事。
4. **不许用 `Math.random` / `Date.now` / `performance.now`。** 回放是重跑同一串动作，
   联机是两边各算一遍。随机只能用 `aiNoise(s, salt)`。
5. **不许有副作用。** 想改局面只能通过返回动作。
6. **`add` 的动作必须合法。** 提了非法动作不会崩（`rejected` 重试兜着），但会白耗步数；
   boss 一回合被拒五六次，表现就是"它站着不动"。
7. **`ignoreRisk` 只给演出型招式。** 普攻、走位标了它，等于让 boss 站着送。
8. **`must` 最多一条，且要能给足分差。** 两条 must 互相打架时，谁都赢不了。
9. **不许在 handler 里遍历全图。** 每步调用一次，热路径。
10. **同一 profile id 重复注册要报错**，不能后来者覆盖——那会变成"开了某个包，boss 换了个脑子"，
    玩家永远查不清自己漏了什么（和核心能力表同一条理由）。
11. **注册表不看"这一局勾了哪些扩展"**：和 `abilities` / `marks` 一样，行为是内容的一部分。
    真要按扩展过滤是规则层的事，不进注册表。
12. **改完要能证明"默认 0 时行为一个字节不变"**：同一批种子逐动作比对。这是验收硬指标。

## 9. 明确不管的事（写在这里，免得以后反复讨论）

- **席位级决策**：造什么、打到哪座城、要不要复活/换血/升时代、指挥官序列。
- **投送和队形**：过河、卡桥、大部队堵在窄桥。单兵 AI 让每个兵更有个性，
  不会让一支军队更会渡河，甚至可能更散。
- **演出**：预告格、播报、阶段感、镜头。这些和 AI 无关，但决定玩家觉得"公平"还是"耍赖"。
- **难度**：单兵 AI 不产生难度。难度来自"必须回应的威胁"和"看得懂"。

## 10. 验收标准

| 项 | 标准 |
|---|---|
| 零行为变化 | 自主分缺失时，同一批种子的动作序列与改动前**逐条相同** |
| 一个兵能自己动 | 测试兵种在 `probe:unit-ai` 里能稳定做出 profile 指定的动作 |
| 三道门都能过 | 不被普攻抢走、不被推演削没、不被 1.5% 带宽随机吃掉 |
