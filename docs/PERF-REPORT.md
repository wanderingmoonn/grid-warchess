## 结论

- **[注意]** 32×32 单帧 p50 21.2ms，已经越过 60fps 的 16.7ms 预算（JS 侧上限 47fps）。真机加上布局与绘制只会更慢——这就是"明显卡顿"的来源。
- **[注意]** 32×32 上最大的一块是「棋盘重绘」：18.4ms，占全部脚本耗时的 90%（其余：侧栏重绘 6%、雾视图 4%、威胁圈 1%）。
- 按格数做线性拟合：**固定开销 5.34ms + 每格 16.01µs**（R²=0.98）。32×32 的 21.2ms 里，25% 与格数无关（侧栏、棋子、城市），其余 75% 是格子本身。拟合很贴，说明模型对得上——要压帧时间就压"每格成本"这一项。
- 从 12×12 到 32×32：格数 ×7.1、单帧 ×2.8。单帧涨得比格数慢，是因为固定开销在两端都占着——这也说明"只在 12×12 上试"永远发现不了 32×32 的问题。
- 每帧新建 1106 个元素、写入 66.4 KB HTML。这些节点**全部是丢弃重建的**（1168 个常驻元素里绝大部分每帧换一批），浏览器每次都要重算样式、重排、重绘。
- 侧栏每帧整块重绘花了 1.22ms。它和棋盘无关，但和棋盘捆在同一次 render 里——棋盘没变的时候它也在重画。
- AI 单次决策 9.55ms（32×32，p95 12.7ms）。单步可接受，但一回合十几步会累加成肉眼可见的停顿。
- **[注意]** 同一份活，最快 18.7ms、最慢 39.9ms，差 2.1 倍。这种抖动比"一直慢"更难受——它是"一顿一顿"。来源通常是 GC（每帧丢弃 1106 个节点）和强制布局，而不是算力不够。
- 32×32 跑 50 帧涨了 +3.5 MB 堆。量本身不大，但它全是短命的 DOM 节点——真机上这些节点会进 GC 的年轻代，频繁回收就是那种"隔几秒一顿"的节奏。

## 建议（按收益排序）

1. **棋盘改增量重绘**：现在每次 render 都重建全部 1024 格。格子内容只在地形/归属/高亮变化时才需要换，其余时候复用节点、只改 class 即可。按这次测出来的占比，这一项占全部脚本耗时的 90%。
2. **别用 innerHTML 重建**：每帧 1106 个元素走一遍"解析字符串→建节点→丢旧节点"。缓存格子节点数组、按需 patch，或者把静态地形层画到一张 canvas 上，只在底层数据变化时重画。
3. **顺手治一下强制同步布局**：`renderBoard` 先量一遍所有棋子的 `getBoundingClientRect`（旧位置），紧接着重写 `innerHTML`，然后再量一遍（新位置）。真机上"写 → 读 → 写"的交替会让浏览器每次都立刻做一次布局来回答矩形查询。棋子越多越贵，而且它和重绘叠在同一帧里。改法是先算好位置再动 DOM，或者把动画交给 transform + 一个 rAF。
