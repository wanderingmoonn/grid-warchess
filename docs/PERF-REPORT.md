## 结论

- 32×32 单帧 p50 8.73ms，JS 侧还在 60fps 预算内；如果真机仍卡，瓶颈更可能在布局/绘制而非脚本。
- **[注意]** 32×32 上最大的一块是「棋盘重绘」：5.37ms，占全部脚本耗时的 62%（其余：侧栏重绘 22%、雾视图 14%、威胁圈 2%）。
- **[注意]** 按格数做线性拟合：**固定开销 3.75ms + 每格 4.69µs**（R²=0.97）。32×32 的 8.73ms 里，44% 与格数无关。拟合很贴，说明模型对得上——要压帧时间就压"每格成本"这一项。
- 从 12×12 到 32×32：格数 ×7.1、单帧 ×1.8。单帧涨得比格数慢，是因为固定开销在两端都占着——这也说明"只在 12×12 上试"永远发现不了 32×32 的问题。
- 每帧新建 41 个元素、写入 3.8 KB HTML，约占常驻元素（1168 个）的 4%。节点已经按需复用了，剩下的这一点是"真的变了"的那部分。
- 侧栏每帧 1.91ms。按内容跳过已经做了，这个数代表"内容真变了"的帧——而它是一整块重写：换一个选中，顶卡、战报卡这些没变的也跟着重建。
- AI 单次决策 11.4ms（32×32，p95 12.7ms）。单步可接受，但一回合十几步会累加成肉眼可见的停顿。
- **[注意]** 同一份活，最快 5.58ms、最慢 13.1ms，差 2.4 倍。这种抖动比"一直慢"更难受——它是"一顿一顿"。来源通常是 GC（每帧丢弃 41 个节点）和强制布局，而不是算力不够。
- 32×32 跑 50 帧涨了 +1.1 MB 堆。量本身不大，但它多是短命的 DOM 节点——真机上这些节点会进 GC 的年轻代，频繁回收就是那种"隔几秒一顿"的节奏。

## 建议（按收益排序）

1. **棋盘这一列还剩下的钱**：5.37ms/帧，占脚本 62%。格子的节点已经复用（增量重绘），这一列里现在混着三件事：逐格算 class（1024 格过一遍）、改动的格子写 className、以及棋子层的整块重写。要看究竟是哪一件，得在这三处各插一次计时。
2. **侧栏的内容拆分**：1.91ms/帧。按内容跳过已经做了（一样的 HTML 不再写），所以这个数全是"内容真的变了"的那部分。要再省，就把侧栏拆成几块各自缓存：顶卡（金币/城市/回合）、详情卡（选中单位）、战报卡——现在换一个选中会把整块 30KB 一起重写。
