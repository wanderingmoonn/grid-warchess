## 〇、先给结论

| 方案 | 内容 | 对上一版胜率（60 局） | 机制有没有真的生效 | 判定 |
|---|---|---:|---|---|
| **P1** | 缩守阈值 `0.75 → 0.90` | 48.3%（−1.7 点，z=−0.26） | 几乎不动（攻/走、阵亡几乎不变） | **无效** |
| **P2** | 有钱（金 ≥ 1.2×收入）时把价格惩罚降到 elite 档 | 50.0%（±0，z=0.00） | **本来就已实现**，补丁等价于没打 | **伪改动** |
| **P3** | 攒升级时"咬住窗口" `4 → 8` 回合 | **58.6%（60 局）/ 54.2%（120 局复核）**<br>合并 **55.6%（180 局，z=1.49）** | 升级 2.3 → 2.7 次/局 | **唯一有效，已并入主线** |

一句话：**只有 P3（让 AI 真的停下来攒升级费）起了作用**；
P1 被更靠前的闸门挡住，P2 的条件仓库里早就有了——这解释了复盘里那个"越打越穷"的死循环，
根子不在"惩罚太重"，而在**它从来没富过**。

## 一、三个方案各自的条件与实现

### P1 缩守阈值 0.75 → 0.90

**原条件**（`buildPlan`）：

```ts
const weaker = myVal < foeVal * 0.75;
const stance = weaker && army >= 3 && atGate ? 'turtle' : elite ? 'elite' : 'push';
```

必须**同时**满足"身价不到对面 75%"和"敌人已压到某座城 5 格内"（`atGate`）才缩守。

**改动**：`0.75 → 0.9`（只动这一个数）。

**预期**：复盘里 AI 整场卡在 0.87~0.95 这段空白（既不够强去总攻，又没弱到缩守），
把阈值抬到 0.9 应当让它早点退守，减少零散接战 → 阵亡下降、交换比改善。

### P2 有钱时把价格惩罚降到 elite 档

**原条件**（`recruitCandidate`）：

```ts
const perGold = plan.stance === 'elite' || plan.stance === 'trade' ? 0.012 : 0.035;
score -= price * perGold;   // 贵兵被线性扣分
```

**改动**：追加 `|| s.players[me].gold >= inc * 1.2`。

**预期**：有钱时不再压价 → 战斗兵均价 100 → 130+，阵亡价值下降。

### P3 攒升级的"咬住窗口" 4 → 8 回合

**原条件**（`savingAllowance`）：

```ts
if ((targetCost - gold) / inc <= SAVE_TIGHT_TURNS) return 0;   // 4 回合内够得着 → 一分不花
if (phase !== 0) return 0;
return Math.floor(inc / sites);                                // 否则每回合照样放钱
```

**改动**：给函数加一个 `tight` 参数（默认仍是 4），**只对 `savingFor === 'era'` 传 8**。
即：攒升级时，"还有 8 个回合的收入才够"就开始一分不花。

**预期**：升级费是本局最大的一笔固定支出（4 代以上 540~780），
它的现金流是"每回合花到只剩一两百"——4 回合窗口意味着永远差一口气。放宽到 8 之后，
升级次数应当明显上升，城代与收入基数跟着上，形成复盘里人类走的那条正循环。

## 三、结果

### 3.1 胜负（每臂 60 局，对冻结的当前 AI）

| 臂 | 胜 / 负 / 未决 | 胜率 | z | 均回合 |
|---|---:|---:|---:|---:|
| **base（对照）** | 29 / 29 / 2 | **50.0%** | 0.00 | 61 |
| P1 缩守 0.90 | 28 / 30 / 2 | 48.3% | −0.26 | 62 |
| P2 有钱买贵的（1.2×收入） | 29 / 29 / 2 | 50.0% | 0.00 | 61 |
| **P3 升级咬住 8 回合** | **34 / 24 / 2** | **58.6%** | **1.31** | 62 |
| P3 复核（120 局，同一补丁） | 64 / 54 / 2 | **54.2%** | 0.92 | 61 |
| **P3 两批合并（180 局）** | **98 / 78 / 4** | **55.6%** | **1.49** | 61 |

对照臂打出 **50.0%**，说明"同种子换边"这套量法没有系统性偏移，
下面三个数的差不是量法造出来的。

### 3.2 行为（6 局自对弈，A/B 两侧平均）

| 臂 | 战斗兵均价 | 升级次数/局 | 平均持金 | 攻/走 | 阵亡/局 |
|---|---:|---:|---:|---:|---:|
| base | 169 / 195 | 2.3 / 2.2 | 623 / 511 | 483/1737 | 37.7 |
| P1 | 170 / 195 | 2.3 / 2.2 | 623 / 512 | 484/1741 | 37.5 |
| P2 | 169 / 195 | 2.3 / 2.2 | 623 / 511 | 483/1737 | 37.7 |
| P3 | **159 / 205** | **2.7 / 2.3** | 597 / 512 | 497/1625 | 39.8 |

### 3.3 怎么读这三行

**P1 为什么无效**：缩守要 `atGate`（敌人压到某座城 5 格内）才成立，而 AI 在 0.75~0.9 这段
通常还没让敌人贴到城下——**真正的闸门是 `atGate`，不是那个比例**。把比例抬到 0.9，
只是让它偶尔更早缩一下，行为指标几乎没动（攻/走 484 vs 483）。

**P2 为什么"像没打"**：因为**它确实等价于没打**。仓库里早就有这一行：

```ts
// buildPlan
const quality = savingFor !== null || gold >= inc * 1.2 || army >= CONFIG.maxUnits - 6;
const elite = quality || mood.weight.boom > 0.5 || trade;
```

`gold >= inc × 1.2` 时 `stance` **本来就是 `elite`**，`perGold` 早就降到 0.012 了。
我这条补丁只是把同一条件又写了一遍。四个指标与对照臂逐位相同，正是这个原因。

这条"伪改动"反过来解释了复盘里的疑问：AI 不是"因为惩罚太重才买便宜兵"，
而是**它从来没富到触发 elite 档**（平均持金 180，收入约 150）。所以病根在"攒不下钱"，
不在"惩罚太重"——而攒不下钱的病根，正是 P3 动的那个窗口。

**P3 为什么有效**：升级次数 2.3 → 2.7（+17%），己方均价反而下降（169 → 159）：
因为它把钱投给了城，而不是又买一个中价兵。阵亡略升（37.7 → 39.8）——升级期的兵更少，
这符合"停手攒钱会先吃亏几个回合"的直觉，但胜率是正的：
**它先吃亏，然后把城代和收入基数滚起来**，和复盘里人类那条线一致。

### 3.4 复核与置信区间（别过度解读）

60 局的 58.6% 看着很美，所以我加跑了 120 局复核：**54.2%**。
两批合并 180 局 = **55.6%，95% 区间 48%–63%，z=1.49（p≈0.14）**。

也就是说：**+8.6 点是 60 局样本的运气成分，真实效果大概在 +5 点上下，而且仍未达到显著。**
它的证据力来自三件事同时成立：

- 两批独立样本都为正（58.6% / 54.2%），不是一次性的噪声；
- 对照臂正好 50.0%，量具无偏；
- 机制层面对得上：升级次数确实涨了 17%，而升级正是复盘里 8 次 vs 2 次的那个差距。

正确的说法是：**P3 是目前唯一值得留下的改动，方向可信、幅度待定**，
而不是"已经证明它强 8.6 点"。

## 四、落到主线的是什么

只把 **P3** 并进了 `src/core/ai.ts`：

| 文件 | 改动 |
|---|---|
| `src/core/ai.ts` | `savingAllowance()` 增加 `tight` 参数（默认 4）；新增 `ERA_TIGHT_TURNS = 8`；两处调用点按 `era` 目标传 8 |
| `scripts/test-ai-optimization.ts` | +1 条用例：差 6 个回合时默认窗口放 50 金、升级窗口放 0；差 19 个回合时两个窗口都照常放 |
| `scripts/probe-econ.ts` | 新增：采购/升级/接战的行为指标探针 |
| `scripts/ai-duel.ts` | 新增 `--policy` / `--vs-new`（上一批已加的），本轮沿用 |

P1、P2 **没有并入**：一个无效，一个是伪改动。补丁文本留在本文档里，随时可复现。
