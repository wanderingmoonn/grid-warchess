# 给 AI 加"会玩某个内容"的能力 —— 请走产业链目标（AiGoal）

> 写给以后要改 AI 的人。目标只有一个：**别再往 `ai.ts` 里塞 if。**
>
> 机制代码在 `src/core/ai-goal.ts`；计划与进度在
> `docs/PLAN-AI-GOAL-2026-11-20.md`。这份是"怎么用"。

## 0. 一句话规矩

**要让 AI 会玩某个内容（建筑链、兵种组合、法术、机制），写一个 `AiGoal`。
不要在 `rawBuildScore`、`recruitCandidate`、`heroSkillCandidate` 里加特判。**

## 1. 为什么（真实代价，不是洁癖）

AI 的每个动作都是**当场比分数**选出来的。这套东西做"买一个兵、走一步、打一下"
很好用，但做不了**投资**——投资的第一步（建电站、建船坞、建宗门）当下一定
不如"再买一个弓兵"。

于是历史上每个"AI 不会用 X"的问题，都是在引擎里补一段 if：

| 内容 | 当年的补丁 | 位置 |
|---|---|---|
| 海军 | `seaDemand` + 船坞额度 + 特殊分支 | `rawBuildScore` |
| 装甲 | `armorSupportNudge` + 采购里给工程机组 +45 | 两处 |
| 组合 | `royalComboBonus`（国王 + 骑兵，数字试出来的） | `recruitCandidate` |

结果：**每加一套内容就要回核心改一次、再试跑标定一次**，而且没人说得清
"为什么这个数是 70 不是 90"。更糟的是它们互相压制——实测船坞在河道图上
80 回合造不出来，因为桥的分数刚好比它高几分。

## 2. 什么情况下必须用 AiGoal

满足任意一条就该写目标：

- 这件事**跨回合**（先建 A，才能建 B，才能买 C）
- 这件事**当下不划算**，好处在几回合之后
- 这件事需要**攒钱**（单价明显高于当前收入）
- 你想让 AI 买某个**面板不好看但机制很强**的兵

反例（**不要**写成目标）：走位偏好、选目标、攻击顺序——那些是单步判断，
属于 `unitAi`（单兵 AI）或现有评分。

## 3. 三步上手

### 第一步：想清楚"值不值"和"缺哪一段"

```
这条链什么时候值得做？（value > 0 的条件）
链上有哪几步？哪一步必须先完成？
```

### 第二步：写一个目标

```ts
const MY_GOAL: AiGoal = {
  id: 'my-chain',
  // ① 激活：返回 0 = 这条链现在不存在（不竞争、不进攒钱表、不加任何分）
  value: (c) => (c.era >= 5 ? 1 : 0),
  steps: [
    {
      id: 'first',
      // ② 这一段完成了吗
      done: (c) => c.count((d) => d.id === 'my-building') > 0,
      // ③ 管建筑：哪些建筑归这一段
      claimsBuild: (d) => d.id === 'my-building',
      // ④ 建它给多少分；返回 null = "现在建它没意义"（等价于旧的 -999）
      buildScore: (c, _id, spot, def) =>
        40 + 60 - (c.inDanger(spot.x, spot.y) ? 30 : 0) - def.cost * 0.01,
      // ⑤ 要多少钱（不写就不进攒钱表）
      cost: (c) => c.state.unitTypes['my-building']?.cost ?? 0,
      // ⑥ 为它停手攒钱值多少（和英雄/升时代同一把尺子，量级 2~15）
      saveScore: 10,
    },
  ],
};

registerCoreGoal(MY_GOAL);          // 核心自己的内容
// 或者：把这个数组放进 Expansion.aiGoals —— 扩展的内容
```

### 第三步：验收（两把尺子都要）

```bash
npm run probe:ai-goal          # 动作指纹 + 每局机制计数
node --experimental-strip-types scripts/diag-build.ts --exp <包> --era N --size 24
node --experimental-strip-types scripts/ai-duel.ts --era N --size 24 --exp <包> \
     --old ./baselines/ai-<改造前的 sha>.ts --games 20
```

**必须同时报"机制计数"**（建了几座、买了几个、放了几次）。
只看胜率会漏掉"机制根本没跑起来"——装甲的电站建了 4 座、素体 0 台，
胜率照样 50%。

## 4. 四个出口怎么选

| 你要 AI 做的事 | 用哪个 | 说明 |
|---|---|---|
| 建某个建筑 | `claimsBuild` + `buildScore` | 选址、钱够不够仍由核心算，你只给分 |
| 买某个兵 | `claimsUnit` + `unitScore` | 参考量级：采购基准 50~70，+30 足够翻盘 |
| 研发 / 研读 / 升级建筑 | `actions` | 直接生成候选动作，**没有插队**，一样参与比大小 |
| 攒钱 | `cost` + `saveScore` | 不进攒钱表，AI 永远不会为你停手 |

四个出口可以同时用（一个目标既建东西又买兵又攒钱，是常态）。

## 5. 五个坑（都真踩过）

### 坑 1：`value` 忘了写激活条件 → 死锁

素体目标最初写成 `value: (c) => c.era >= 7 ? 1 : 0`，和电、坞并列都值 1。
而并列是按注册顺序抢的 → 素体排前面，**40 回合一台电站都没建**，
因为 AI 一直在"攒一台装不了炮的素体"。

**规矩：`value` 要写"这条链现在真的能推进吗"**，包括前置是否具备。
素体现在写的是 `有电 && 有坞`。

### 坑 2：顺序链 vs 并行支线，别搞混

装甲一开始写成一个目标两段（先电、后坞），实测坞从 4 座掉到 1 座——
因为"余电不足"让第一段长期不算完成，第二段永远排不上。
旧代码里两者各查各的条件，**本来就是并行的**。
拆成 `armor-power` / `armor-dock` 两个目标才对。

**规矩：真的硬前置才用顺序段；互相独立的写成多个目标。**

### 坑 3：`buildScore` 返回 `null` 不是"给 0 分"

返回 `null` = 明确不许建（核心会转成 `-999`）。**必须在这里拦住**：
AI 提出一个必被规则拒的动作，执行方会中断这一步（实机会顺延，跑批脚本会中断）。
"这个局面下建它没意义"（离城太远、这一档产物一条都造不了）就该 `null`。

### 坑 4：不要依赖注册顺序

并列时先注册的赢。所以：
- `value` 要写清楚，别让两个目标无意义地并列
- 真需要优先级，就在 `value`/`score` 里表达，不要靠"我写在前面"

### 坑 5：改动会影响"承诺"（`AiCommit`）

正在追的那一段会额外 +`COMMIT_BUILD_BONUS`（15）。所以如果你的目标
`value` 频繁在 0/1 之间跳，它会反复立项又放弃——把 `value` 写成稳定的判据。

## 6. 什么时候才允许改核心

**判据是"这个内容属于谁"，不是"好不好改"。**

| 内容归属 | 允许改核心吗 |
|---|---|
| 核心自己的内容（海军、装甲） | 可以，但要写成 `registerCoreGoal`，**用同一个接口**，不留特例 |
| 扩展的内容（修真、太空、黑暗动乱） | **不可以**。核心不许出现 `'cultivation-sect'` 这种字符串 |

核心已经做到的：
- 判据用**数据**不用 id（海军的"水上产兵点"看 `buildOn` 里有没有水）
- 目标由扩展声明（`Expansion.aiGoals`）
- 扩展写坏了只警告一次，不打死整局

## 7. 提交前自检（八条）

1. `value` 写了"现在能不能推进"，不只是"到没到某个时代"？
2. 前置是**硬顺序**还是**并行支线**？段拆对了吗？
3. `buildScore` 里"建不了"的情况全部返回 `null` 了吗？
4. 需要攒钱的那一步写了 `cost` 吗？`saveScore` 量级对吗（2~15，不是 100）？
5. 核心文件里有没有出现扩展的兵种/建筑 id？
6. 跑过 `probe:ai-goal` 和对应的 `diag-build`，**机制计数**变了吗？
   有链的（海军/装甲/修真）还要跑对应的链探针：`probe:cultivation-chain`。
7. 有对照基线吗（`git show <改造前 sha>:src/core/ai.ts` 抄到 `scripts/baselines/`）？
8. 验收时长够吗？高时代要 24~28 的图、160+ 回合才是有效样本。
