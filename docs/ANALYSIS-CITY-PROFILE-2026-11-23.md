# v3 的"城市盲区"与三局负的死因（2026-11-23）

> 待办归口：新增条目已写进 `docs/V3-BACKLOG.md`（P0-0 / P0-4 / P1-3），
> 失败的尝试已登记进它的第六节"负结论登记簿"。
>
> 本文回答用户 2026-11-23 的两个问题：
> ① v3 分不清城与城（前线的城被威胁却让后方城出兵；平原城造牧民跋涉到丘陵城）；
> ② 最后 3 个败局怎么解决。
>
> 新增工具：`npm run probe:city-role`（出兵点前线度 / 经济兵站错地）、
> `npm run probe:collapse`（崩盘时间线 + 采购拒绝理由 + 跨回合攒钱目标）。

## 零、结论

1. **用户的观察成立，而且是真的同一个病：AI 没有"城"这个概念。**
   采购打分里**没有任何一项**依赖产兵点的位置（全表唯一例外是"国王 4 格内给骑兵 +80"
   那条特例；军营有 +6，城市没有）。同一兵种在两座城算出来的分数**逐位相同**，
   于是落进"同分里按 `aiNoise` 抽一个"——**等于在城之间均匀随机**。
   它不是在"选错城"，它是没在选。
2. **三局负的第一死因也在钱上，但不是"经济做太多"，是"攒钱目标永远差一口气"。**
   实测三局负从 T20~T24 起一直挂着 `savingFor='era'`（要 360~540 金），
   账上钱在 121~540 之间**来回震荡**，既没攒到、兵也只零星买。
3. **"打不过就不许攒钱"已经试过，净负，已回退**（Q1/Q2 10-2-0 → 9-3-0 → 8-4-0，
   两局原本的胜局变成负局，而三局负**一局没动**）。原因见第二节第 4 条：
   那个局面里 AI 的自我估值并不认为自己落后。**所以这条不能靠"关闸"解决。**
4. 两条的修法**互不依赖**，可以分开做：城画像（新机制、不动经济逻辑）先做；
   攒钱目标要改成"按存活折现重估"，单独立项。

## 一、城市盲区：先坐实代码，再给数

### 1.1 选产兵点时，城的位置完全不进打分

`recruitCandidate(s, src, …)` 的 `src` 就是"这一座城"（`{kind:'city', id, x, y, era}`），
但整个 score 里跟产地有关的**只有一行**：

```ts
// 军营是前线补给点：在军营出兵有额外价值（省了从后方跑一趟）
if (src.kind === 'camp') score += 6;
```

**军营在哪儿有 6 分的差别，城市在哪儿一点差别都没有。**

唯一的先例是 `royalComboBonus`："国王在产兵点 4 格内，骑兵 +80"，
注释自己写着"从地图另一头的城买出来的骑兵，走不到国王身边就不会晋升"。
思路是对的，但它是**给两个兵种写死的特例**，没有变成通用项。

后果链：

```
同兵种 → 每个城的分逐位相同
      → aiNextAction 的 tied 区间把它们全收进去（band 内）
      → pick = tied[floor(aiNoise(s) × tied.length)]
      → 等价于在"能出兵的城市"之间均匀随机
```

`aiNoise(s)` 只吃 `seed / turn / log.length`——确定的、可复现的，
但**跟局面毫无关系**。这就是用户看到的"它挑城像抽签"。

### 1.2 数据

```
T5  crossbow  出在 c2（离敌 8 格）· 最近的是 c1（3 格）· 多跑 5
```

这个病在那里不显眼。**地图越大越严重**，这解释了为什么人类测试员在大图上看得最清楚。

### 1.3 同一盲区的第二面：经济兵

三个缺陷叠在一起：

**(a) 兵种评估用"它最好的地形"，不是"这座城周边的地形"**

```ts
function maxIncome(def: UnitTypeDef): number {  // incomeByTerrain 的最大值
```

牧民 `{hill:8, plain:4}`、农民 `{plain:7, hill:4}` → `maxIncome` 恒 8 vs 7 →
**回本（payback）恒按 8 算，牧民永远赢**，不管城周边是丘陵还是平原。
用户看到的"平原城造牧民"，从这一行就注定了。

**(b) 经济兵没有"归属城"**

`tacticalMoveScore` 的 economy 分支全文只有：

```ts
const gain = 产出(目标格) − 产出(当前格);
return gain * 5 - 1.5 + (现威胁 − 后威胁) * 2 - 后威胁 * 1.5 - (致死 ? 100 : 0);
```

没有"我在哪座城的辖区"，也没有"这格被同类占了吗"
（后者 `ANALYSIS-ECON-FIELD` 第六节也点过：所有单位共享一张场，会朝同一个最优点挤）。

**(c) 实测**（Q3|31|A）

- **60%** 的经济单位-回合站在"另一个经济兵种更擅长"的格子上，平均少产 **6.35 金/回合**；
- 出生城 7×7 里它擅长的地形平均只占 **25~28%**。

```
T3 herder@forest   产出 2 · 该格上最好的经济兵能到 12
T3 lumberjack@hill 产出 5 · 该格上最好的经济兵能到 8
```

**注意**：这跟"要不要长途跋涉"是两件事。实测"走了 ≥4 格"的只有 1/11、
"开始产出的平均距离 0.6 格"——**它其实不太走**，因为 `gain` 只比相邻一格，
中间几步产出相同就没有坡度（`ANALYSIS-ECON-FIELD` 的结论）。
所以真人测试员看到的"跋涉"，在这几局里没复现；但"**出生在错的城、站在错的地上**"
是稳定复现的。修这一条要动**出生地 + 兵种选择**，不是走位——
这点很重要，因为"经济走位"这条路 2026-11-23 已经证明净负。

### 1.4 城里已经有五个各自为政的口径

这才是"没有城画像"的病根。现在每个消费者各拍一个：

| 消费者 | 取法 | 问题 |
|---|---|---|
| 攻击方向 `focusCityId` | 计划层给 | 只关心敌城 |
| 散兵回家 `homeCityId` | **hp 最高的自家城**（`ai-v3.ts:9841`） | 那通常是**后方**城——散兵被它往回拉 |
| 守城 `guardCityId` | `pickGuardCity`：最近敌兵 ≤9 格且 danger≥3 | 只用于"进城驻守"那一条走位分 |
| 弃城 `abandonedCityId` | `doomedCity`：敌人 ≤4 格 + 危险度 | 只用于"别往这儿填兵" |
| **产兵点** | 无 | 均匀随机 |
| **经济归属** | 无 | 无 |

所以准确的说法不是"AI 不会区分城市"，而是：**它有几条互相打架的特例，
而最关键的两条（产兵、经济归属）根本不存在。**

## 二、三局负：攒钱目标永远差一口气

### 2.1 探针读到的东西

```bash
npm run probe:collapse -- --queue Q3 --seed 31 --side A
```

它借用 `aiRecruitTrace`（`recruitCandidate` 自己记的拒绝理由），并在"没买到兵"
时顺带读 `aiFocus[me].save`（跨回合攒钱目标）。

**Q3|31|A（负 84）**

```
 回合 | 我兵 值 | 敌兵 值 | 我城(hp)  | 经济 | 金 |
  24 | 19 1474 |  6  660 | c1:63 c2:81 |  8 |  16 |
     └ 钱 195 一个兵没买 · …攒钱冻结×19
       攒的：era@c2 要 540（还差 345，立了 0 回合）
  40 | 13 1420 |  7 1040 | c1:0  c2:81 |  8 | 269 |
     └ 钱 269 一个兵没买 · …攒钱冻结×22
```

**关键不是"冻结"，是钱在 195 → 381 → 194 → 382 之间来回震**：
它名义上在攒 540 的升级费，实际每两个回合就被允许花掉一笔，
**从 T24 攒到 T76 一次都没攒到**。

**Q1|31|B（负 79）**

```
  16 |  6  420 |  3  150 | … |  4 | 466 |   ← 3 倍兵力领先，466 金不动
  28 |  5  390 |  8  960 | 10 econ | 454 |

```

**Q1|30|A（负 78）**：T20/T32/T36/T40/T44 各查一次，全是 `攒钱冻结`，
目标是 `era@c2 要 360`，账上 121 → 218 → 294（"立了 8 回合"、"还差 66"），
然后在攒够之前被打死。中途还切过一次 `rebuild@c1 要 158`（想把丢掉的城建回来）。

### 2.2 机制

`buildPlan` 里允许攒钱的条件（`ai-v3.ts:7718` 附近）：

```ts
const armyGate = mood.weight.boom > 0.45 ? 4 : 6;
if (!urgent && (abandonMode || army >= armyGate)) { …攒钱目标… }
```

- `army` 是**绝对人头**：9 个兵对 11 个兵也算"够多"；
- `urgent` 太窄（`isUrgentNow`）：只有"兵 < 3"或"敌人贴到某城 3 格内"；
- 允许攒之后，`savingAllowance` 每回合仍放行 `inc / 产兵点数` 的额度
  （离目标只剩 8 回合收入时才归零），而一个兵 45 金起——于是**小额豁免 + 收入分流**
  让目标永远差一口气；
- `reach(cost, SAVE_HORIZON=6)` 只问"6 回合内的收入够不够"，不问
  "6 个回合后这座城还在不在"。

### 2.3 我试过的那一刀，净负，已回退

假设：既然病在"打不过还攒钱"，那就加一条硬闸——
`outmatched = 敌方兵力价值 ≥ 我方 × 1.25` 时不许攒（含"复活上次目标"那条路）。

| 版本 | Q1/Q2 | 配对变化 | 三局负 |
|---|---|---|---|
| 基线 `cutfix` | **10-2-0** | — | 78 / 79 / 84 |
| v1：造价和 × 1.2，只闸主路径 | 9-3-0 | Q1\|32\|B 胜88 → **负33** | 逐局回合数完全相同 |
| v2：血量加权价值 × 1.25，连"复活"一起闸 | **8-4-0** | Q1\|30\|B 胜54→负49、Q1\|32\|B 胜88→负33 | 逐局回合数完全相同 |

**两个结论都很重要**：

1. **三局负的回合数逐局一字不差** → 那个闸在它们里面**从来没有触发过**。
   也就是说，AI 自己的估值**并不认为自己落后**（它贵兵多、对面便宜兵多），
   所以"按兵力比关闸"根本没碰到它们的病灶。
2. 在本来能赢的小图局上，这一刀**直接变成负局**——那些局里"攒钱升代"
   是对的，强行改成连续造兵反而输。**`savingFor` 不是 bug，是一个判断；
   错的是这个判断没有把"城还能撑几回合"算进去。**

已回退，登记进 `V3-BACKLOG` 第六节。

## 三、两者同源在哪

共同病根一句话：**所有决策输入都是席位级标量。**

| 现在用的 | 缺的 |
|---|---|
| `urgent: boolean`（兵<3 或敌人≤3 格） | 兵力**比**、以及"哪座城在挨打" |
| `threat: number`（最危那座城的伤害差） | 每座城一条威胁 / 交付时间 |
| `army: number`（绝对人头） | 同上 |
| `homeCityId`（血最多的城） | 每座城的角色（前线 / 后方 / 弃） |
| `targetEarners: number` | 每座城的地皮容量 |
| `savingFor`（攒什么、要多少） | **还差几回合 × 那座城还能撑几回合** |

用户说"这是同一个问题"——**方向对**：两个出口缺的是同一类东西
（城级向量 + 相对量）。但**修法不能合并**：一个是在采购里加位置项（安全、独立），
一个是把攒钱目标的评分改成"存活折现"（会碰经济逻辑，得单独立项、单独跑批）。

## 四、方案

### P0-4 城画像 `CityPlan`（**建议先做**，不碰经济逻辑）

每回合算一遍，别跟着每个候选重算（`buildPlan` 那种成本会炸）：

```ts
interface CityPlan {
  id: string;
  slots: number;      // 产兵格（复用 buildSlotPlan 的 spawnCount）
  heat: number;       // 威胁：最近敌方战斗单位格数 + 血线（复用 pickGuardCity 的公式）
  front: number;      // 到最近敌城的**路径**回合（advanceDistance，不要直线）
  econNear: number;   // 周边 4~6 格可经济化地块数（econSurvey 按城分组）
  role: 'front' | 'rear' | 'abandon';
}
```

**消费者 1：采购选址（只改战斗单位，只进采购不进走位）**

```ts
site = -k × deliverTurns(city, 这一回合需要它的地方)
```

- "需要它的地方"：该城 `heat` 高 → 就是这座城（守城，`deliver = 0`）；
  否则用 `guardCityId ?? focusCityId`；
- **幅度**：先 `k = 4`、封顶 −25。参照系：`camp` 的 +6 是"省一趟路"，
  实测平均多跑 1.93 格 ≈ 半趟路，所以城与城之间的差应该落在 6~12 分量级。
  **不能写成 50**——"桥位驱赶"用 50 分，配对 3↑5↓，那是把战术走位打乱了；
  这一刀只进采购，不进走位，风险低一个量级；
- **验收**：`probe:city-role` 的"平均多跑 / 落后 ≥2 格"必须显著下降；
  `probe:ai-goal` 的指纹会变（这里变了才是对的，它不是纯重构）。

**消费者 2：经济兵的兵种 × 出生城**

```ts
// 用"这座城周边它自己的最好地形"代替 maxIncome
localIncome(def, city) = max over city 周边 4 格 of def.incomeByTerrain[地形]
payback = price / localIncome(def, city)
```

- 平原城买农民（7）、丘陵城买牧民（8），而不是两座城都买牧民；
- `econSurvey` 里已经有 `terrainCounts`，口径现成，只是采购侧没用上。

**消费者 3：升级选城（= BACKLOG P1-3）**

`upgradeCandidate` 现在只看 spare 比例、时代差、"是不是最高代那座城"。
接上 `heat` 与 `slots`：**产兵格多、又不在敌人射程里**的城优先升。

### P0-4b 经济兵的归属城（软约束）

- 出生时把 `homeCity` 记到单位上（就近、粘住，别每回合重算）；
- 走位候选加一条：目标格离 home 城 > 5 时 −20，**除非** home 周边已经没有 ≥4 产出的空格；
- **优先级必须低于 `yieldPlan`（让位）**，否则跟"清城格"打架。

为什么这次和"经济产出距离场"（19-3-2，已回退）不一样：那次是**看得更远**
（8 格 max-plus 场），多出来的是长途跋涉；这次是**看得更近**（限制在自家辖区），
治的是"所有单位共享一张场、朝同一个最优点挤"。两者方向相反。

### P0-0 攒钱目标按"存活折现"重估（**单独立项，别和上面混**）

已经证伪的路：按兵力比关闸。剩下的路只有一条——**让"攒这个"的分数随
"城还能撑多久"衰减**：

```ts
// 目标评分时多乘一项
survival = clamp01(预计崩盘回合 / 攒够这个目标所需回合)
score *= 0.4 + 0.6 * survival
```

- "攒够所需回合" = `(targetCost − gold) / inc`（现成）；
- "预计崩盘回合"可以先用最粗的代理：最危那座城的 `hp / 每回合受到的伤害`
  （`cityThreatUrgency` 已经在算 `damage/hp`）；
- **必测**：Q1/Q2 不能掉（上一刀就是死在这）；三局负至少有一局要变。

如果这条也走不通，再考虑更硬的：**把 era 目标在"城血 < 50%"时整体降权**，
而不是按兵力比。这是两个不同的判据，得分开跑。

## 六、没做的事

- 没验证"人类测试员看到的牧民长途跋涉"：这几局经济兵平均 0.6 格就开始产出，
  走了 ≥4 格的只有 1/11。**那可能是"站在错的格子上"被看成了"跋涉"**，
  也可能真人局的城距更远——需要拿到具体回放再验。
- 没量"三局负里 AI 自己的 `myVal` 到底是多少"：v2 那一刀在三局里零触发，
  说明它认为自己不吃亏。下一步该把这个自评数打进探针，
  确认是"估值偏高"还是"根本没比"。
- 没动 `savingAllowance` 的额度算法（`inc / 产兵点数`）：它是不是"永远差一口气"
  的直接原因，需要把每回合的额度也打出来才能定。

| `CityPlan` + `buildCityPlans()` | `ai-v3.ts`（`buildSlotPlan` 之后） | 每回合算一次，进 `Fields.cityPlans` |
| `Fields.cityPlans` / `Fields.needCityId` | `Fields` 接口 | 常驻 |
| 采购选址 `siteBoost` | `recruitCandidate(..., siteBoost)` | **`aiCitySite` 关** |
| 开关 `aiCitySite` | `types.ts` + `setup.ts` 白名单 + `bench:ai --city-site` | 关 |

`needCityId` 的优先级：**有城在挨打（`heat ≥ 0.3`）就是那座城**（兵出在自己城里，
出生即到位、还自带 3 点驻军护甲），没人挨打就朝主攻方向出。

**踩过的坑**：`setup.ts` 的 `config` 是**逐项白名单抄**的，新开关不抄进去 =
"开了跟没开一样"。第一次跑 `--city-site` 逐局与基线完全相同就是这个原因
（`setup.ts` 里 `unitCap` 的注释早就记过同一条）。

### 实测（对手 `baselines/ai-9efb961.ts`，12 局/组）

| 改动 | Q1/Q2 | Q3/Q4 |
|---|---|---|
| 基线 `cutfix` | 10-2-0 | 11-1-0 |
| 选址 + 升级画像 + 经济回本（三合一） | 7-4-1（1↑4↓） | — |
| 选址 + 升级画像 | **10-2-0（1↑1↓）** | 6-2-4（**0↑5↓**） |

| 只剩选址，`SITE_TURN_COST` 从 4 降到 2.5 / 封顶 8 | 10-2-0（1↑1↓） | — |

结论：**净负，默认关**。但三个信号值得留档：

1. **小图上是持平偏正**：Q1|30|A（三局负之一）由负 78 变成**胜 51**，
   8 局胜局提前 4~14 回合；代价是 Q1|32|A 由胜 85 变负 102。
2. **`probe:city-role` 的"落后 ≥2 格"从 45% 只降到 41%**——因为真正的差距
   不在"选哪座城"，而在**时代**：前线城常常是 e2、后方城 e3，
   `eraWindowOk` 让前线城**造不出当代兵**。样本原样输出：
   ```
   T19 halberdier 出在 c2（离敌 7 格）· 最近的是 c1（3 格）· 多跑 4 · 产兵格 c1(e2):1格 c2(e3):2格
   ```
   这一条属于**升级选城（P1-3）**，不属于选址——选址项再怎么加，也变不出 e3 的前线城。
3. 24×24 上"胜局变 261 回合平局"，说明**兵早到不等于赢**：v3 的进攻靠编队成形，
   兵一个个提前到场反而更碎。这和 `PLAN-YIELD` 里"给战斗单位加让位分 3↑5↓"是同一类教训。
