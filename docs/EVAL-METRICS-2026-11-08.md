# GitHub 上有没有现成的评价指标？（2026-11-08 调研）

问题：我们这套「agreement 探针 + 固定 n 局胜率 + z 检验 + 兵种性价比」是自己攒的，
GitHub 上是不是已经有一套可以照抄的评价体系？

**结论：有，但不在一处，而且没有一套直接可用的。** 现有体系分四个互不相通的家：

| 家 | 代表 | 量的是什么 | 能不能直接用 |
|---|---|---|---|
| 棋类引擎圈 | SPRT / Elo / ACPL / move agreement | 「这一版引擎比上版强吗」 | **能，最有价值** |
| 卡牌平衡圈 | GIH WR / 贝叶斯收缩 / GLMM | 「这张卡强，还是玩它的人强」 | **能，我们已手工做了一半** |
| 学术优化圈 | LUDUS（PCP/SDM/EM） | 「卡池的胜率分布均不均」 | **能，算法只有十几行** |
| LLM Agent 评测圈 | DSGBench / gg-bench / BalatroBench | 「模型会不会玩这个游戏」 | 不能用，对象完全不同 |

---

## 1. 棋类引擎圈：SPRT 是唯一被全行业采纳的东西

SPRT（序贯概率比检验）是 Stockfish / Leela Zero 等所有主流引擎的标准判决流程，
不是"一套指标"，而是**一套判决协议**：给定 H0 = 新版 +0 Elo、H1 = 新版 +5 Elo、
α=β=0.05，每打完一批对局更新对数似然比 LLR，一旦越过任一边界立刻停。

关键在这三条，正好对着我们现在做错的地方：

1. **样本量不是预设的，是检验出来的。** 我们现在"默认 400 局（200 种子），
   方向明确才上 800"——这是固定样本设计，最坏情况是花了 800 局得到一个本来就
   该在 120 局停下的"中性"。
2. **配对而不是独立。** 标准做法是同一开局打两遍、交换先后手，把结果记成
   五悬（pentanomial：LL/LD/DL/DD/WD…）而不是三悬，因为同开局的配对局强相关，
   当独立样本算会低估方差。
   **这一条我们已经有了一半**：`.tmp/draft/paired.ts` 就是按种子配对做 McNemar
   （同种子 = 同地图同卡池，只有选人顺序不同）。缺的是把它变成**默认判决**——
   主口径仍然是独立比例 z（`summarize.py` 里 `se=sqrt(p(1-p)/n)`），配对分析是
   事后补的第二份报告。两次结论打架时以哪个为准，没有写死。
3. **不显著 == 不通过。** 引擎圈把"inconclusive"直接当作"没有提升"（leela-zero
   FAQ：必须 95% 置信新版对旧版有 55% 胜率才换网络）。这条和我们止损规则第 5 条
   （连续两次中性 → 换层）是同一个思想，但他们是**事前写死**，我们是事后总结。

**最贴近我们场景的一个仓库**：`Z15-N/unsw-battlecode-2026` 的 `docs/PIPELINE.md`。
那是 UNSW 的网格对战机器人比赛，做法是：
- 每个 `(map, seed)` 打两遍、交换边位，消掉地图与先后手运气；
- SPRT 门禁，H0=+0 / H1=+20 Elo，最多 1600 局，实测 88~1628 局收敛；
- 另配 `spsa.py` 同时调几十个常数（不用逐个扫参数）；
- 用「克隆对手」（模仿其他队行为的 MLP）做自对弈之外的对局，因为自对弈提供不了
  分布外的对手。

这几条几乎是给我们写的：我们的 32 核、种子并行、`--old` 基线、A/B 席位差异，全都在。

**其余可借的单点指标**（都在 `Meddhif13/Monte-Carlo-Chess-Suite`、
`skorotkiewicz/chesslm` 里有实现）：
- **best-move agreement**（top-1 / top-k 一致率）→ 就是我们的 `probe:agreement`，
  说明这条路子是对的，行业认可；
- **ACPL（平均分差损失）** / **Acc% = 100·k/(k+loss_cp)** → 我们缺。因为我们没有
  裁判引擎，算不出"这一步比最优差多少分"。可行的替代是**自我 regret**：用旧策略
  同一局面下的估值减新策略估值，但那是拿评估函数给自己打分，只能看相对变化，
  不能当绝对棋力；
- **blunders per 100 moves**（按损失分档统计失误/漏着）→ 可借壳：我们已有
  `ai-trace` 的逐决策日志，可以按"是否错过击杀/是否白送单位"分档计数。

## 2. 卡牌平衡圈：GIH WR 与 GLMM，解决"强人用好卡"

`GuySchnidrig/ManaCore` 的 `card_impact_analysis.R` 是目前最完整的一套：
- **GIH WR（Game-in-Hand Win Rate）**：只在"这张卡在你手里"的局里算胜率，
  17Lands（万智牌）的行业口径；
- **贝叶斯收缩**：小样本卡向均值拉，避免 5 局 4 胜就 80%；
- **GLMM 控制变量**：把玩家 Elo、卡组原型、对位原型、重复测量都放进混合模型，
  剩下的系数才是"卡本身的贡献"。它点名了那个陷阱：*Mox Ruby 原始胜率 75%，
  但那是卡强还是玩它的人强？*

对照我们：`docs/DRAFT-STATS-2026-11-07.md` 里的**席位校正**（按 A/B 侧基准做二项
检验）本质上就是 GLMM 的解析解版本——我们只控制了"席位"这一个混淆项，
而且是被数据里的席位差逼出来的，不是一开始就设计好的。
**更麻烦的是它没固化成脚本**：`summarize.py` 里仍然是 `z=(p−0.5)/se`，
席位校正只存在于那份文档的手算过程里。下次重跑，这套修正等于不存在。
这是比"缺指标"更值得修的东西。

GLMM 我们不需要（样本量撑不起随机效应），但**贝叶斯收缩要补**：
现在我们对 `n<10` 的卡标 `n小` 就放着，收缩后可以给一条排序，而不是让读者自己
在 `n=8` 和 `n=86` 之间做心算。

## 3. LUDUS：卡池是否"摊得平"的三个数

AAAI 论文（`LUDUS: An Optimization Framework to Balance Auto Battler Cards`），
把每张卡的胜率做成向量 w，然后三个指标：

- **PCP（per-card payoff）** = (1/n)·Σ|w_j − 0.5|² —— 平方项专门惩罚离群卡；
- **SDM** = w 的标准差；
- **EM** = w 归一化后的熵，熵越大越"人人有份"。

我们现在的卡池体检是**逐卡看 z 值**，看的是"哪张出问题"，没有"整个池子摊不摊得平"
的一个数。加上 SDM/EM 之后，任何一次数值改动都能给出一句可比较的话，而不是每次
重读一张 40 行的表。

另有一个现成口径可以直接搬：**抓取覆盖率**。我们已经量到"96 张能进池，只有 40/43
张真被选过，53~56 张零抓取"——这正是 LUDUS 里 EM 想量的东西，只是我们没把它
做成指标。

## 4. 学术 LLM 评测圈：不适用的三家

- `XiaoqingWang/DSGBench`（SC2 / 文明 / 狼人杀 / 外交，评 LLM agent 的战略规划）
- `vivek3141/gg-bench`（LLM 生成的双人回合制游戏，用 RL agent 当对手量 winrate）
- `coder/balatrobench`（固定种子跑 Balatro，比"平均到第几轮"）

这三个都是"**评模型**"，我们是"**评自己的引擎和数值**"。它们的指标（能力分、
工具调用成功率、token 成本）没有一个能落到我们的判决上。唯一可借的思路是
balatrobench 的**固定种子白名单 + 每种子固定局数**，而我们已经这么做了。

顺带记一个有意思的：`star-nexus/star` 提出 **PWER（Performance-Weighted Elo）**，
把胜负加权为「单位保存率 × 时间效率」——胜得漂亮才算赢，专门处理"惨胜"。
我们的胜率判决把这两维全丢了。平均回合 81.9 这个数已经在手上，单位保存率也在
复盘数据里；如果要区分"AI 是靠拖赢的还是靠打赢得"，这两个是现成的第二判决维度。

## 顺手实测：把三个池子级指标接到已有数据上（2026-11-08）

脚本 `scripts/draft-metrics.py`（读 `.tmp/draft/<批次>/*.jsonl`，不跑对局；
`python scripts/draft-metrics.py e1 e3 e3-turnban`）。口径：
单卡胜率只算"只有一方拿到它"的局；期望 = Σ(该侧局数 × 该侧基准胜率)；
**SDM 扣噪声底**（逐卡 `p(1−p)/n` 的均值开方，纯抽样就会垫出这个高度），
只有"超额 SDM"能跨批次比；覆盖率 = 真被选过的卡 ÷ 进池过的卡。

| 批次 | n | 覆盖率 | SDM | 噪声底 | 超额 SDM | 显著卡(席位校正后) |
|---|---|---|---|---|---|---|
| e1（时代1，序列禁用） | 100 | 42% | 16.6pp | 8.6pp | 14.3pp | 6 |
| e3（时代3，序列禁用） | 100 | 45% | 17.4pp | 9.2pp | 14.8pp | 2 |
| e3-turnban（轮流禁用） | 200 | 53% | 14.0pp | 7.6pp | 11.8pp | 7 |

表面看是"轮流禁用让池子从 17.4 摊平到 14.0"。**但这是假象**：覆盖率与 SDM
都随样本量机械变化（每局 12 次抓取，局越多覆盖越广；局越多噪声底越低）。
把 turnban 随机子采样到 100 局（300 次）：

- 覆盖率 **49%**（90% 区间 46~52%） vs 序列禁用 45%
- 超额 SDM **12.2pp**（90% 区间 8.4~15.6） vs 序列禁用 14.8pp

**两个差值都落在噪声里**。也就是说：用池子级指标，在 n=100 这个量级上**分不出
轮流禁用和序列禁用**——这和"胜率只从 67.6% 挪到 63.5%（4pp）"是同一个结论的
两种说法，互相印证，不是坏消息。

附带两条口径警告：

1. **EM 在我们的场景里是废的。** 三批数据的归一化 EM 都是 98~99%。原因是单卡
   胜率全挤在 40~60% 区间，熵几乎恒等于最大值——它只能区分"有卡胜率 90%、有卡
   30%"这种极端分布。LUDUS 那个场景卡胜率跨度大，EM 才有分辨力。**别用 EM 报数。**
2. **SDM 必须和噪声底一起报。** 14.0pp 听起来比 17.4pp 好，但只看这一对数会得出
   "池子变均匀了"的错误结论；扣掉噪声底之后（11.8 vs 14.8）才看得出这一点差异
   本来就不显著。

## 落地建议（按性价比排序，不是按优雅程度）

**第一优先：把席位校正固化进汇总脚本，并补 SDM / 抓取覆盖率。**
（席位校正 + SDM/覆盖率已落进 `scripts/draft-metrics.py`；EM 经实测无分辨力，删掉。）
这两件都是零机时——200 局数据已经在 `.tmp/draft/`，只是没被算成数。**
现状是：席位校正只存在于 `DRAFT-STATS-2026-11-07.md` 的手算段落里，
`summarize.py` 仍然是 `z=(p−0.5)/se`。同一批数据换个日子重跑，结论会不一样，
这不是方法问题，是工具问题。加三个输出：
- 按侧加权期望的二项检验（替代裸 0.5）；
- 卡池级 SDM（单卡胜率标准差）与 EM（归一化熵）；
- 抓取覆盖率（真被选过的卡 ÷ 进池过的卡）。
200 局的数据跑一遍就知道这刀下去池子摊平了没有，不用再烧一轮。

**第二优先：A/B 判决加序贯停止。**
配对已经有了（`paired.ts`，McNemar），缺的是"能不能提前停"。现在是打满 400 局
再看结果；SPRT 在方向明确时 100~150 局就收敛。**但只能用在对称比较上**：
"新版 vs 旧版 AI"适合，"先手 63.5% 偏不偏高"不适合（那不是强弱，是结构性偏差）。
另外要注意：引擎圈 SPRT 假设对局同分布，我们的对局由同一个 AI 自对弈产生，
方差比真实对手小，σ 会低估——**先拿已有的两组历史数据反推经验方差**，
再用它设边界，别直接套 Elo 的默认参数。

**第三优先：胜率之外补一个副判决（单位保存率）。**
平均回合数 `summarize.py` 已经在算了（`turns`），缺的是单位保存率。
借 STAR 的 PWER 思路，但**不做加权**，只分列报告——先看两个数是否同向，
同向才谈加权。防止再次出现"胜率动了但其实是拖出来的"这种事后才发现的解释。

**不建议做的**：
- 引 ACPL / Acc%：没有裁判引擎，拿自己的评估函数当裁判是循环论证；
- 上 GLMM：样本量（每卡几十局）撑不起随机效应，席位校正已经吃掉主要混淆；
- 照搬 DSGBench 那一套能力分：对象是 LLM，不是引擎。

## 一句话

**方法论上是有的（SPRT + GIH WR + LUDUS 三件套），但没人把它拼成一个能直接
`npm install` 的东西；我们缺的不是"一套指标"，是「把已有的修正固化成脚本」
（席位校正还在文档里手算）和「池子级的汇总数」（SDM/EM/覆盖率）。
前者决定结论可不可复现，后者决定要不要再烧一轮机时。**
