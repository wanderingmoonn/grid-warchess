# 帧预算：把 32×32 的单帧从 18.7ms 压到 5ms

> 玩家向的公告在 [`UPDATE-2026-10-28-perf-launch.md`](UPDATE-2026-10-28-perf-launch.md)，
> 这份是技术细节：每一处怎么改的、为什么、以及踩过的坑。
>
> 起因：32×32 在一台机器上不卡、在另一台上明显卡，说不清卡在哪。
> 先写了体检脚本（`npm run perf`，见 [PERF.md](PERF.md)），再照着它排的顺序改。
>
> 这一批只动渲染层，**规则、平衡、存档格式一行没变**：同一份局面在同一台机器上
> 走出来的棋完全一样，改的只是"怎么把它画出来"。

---

## 1. 改了什么

七处，按当时的收益排：

| 改动 | 位置 | 一句话 |
|---|---|---|
| 格子层增量重绘 | `ui/board.ts` | 1 024 个格子节点留着复用，只改变化那几格的 `className` |
| 棋子层按 id 复用 | `ui/board.ts` `paintUnits()` | 节点留着，只 patch 变了的字段 |
| 侧栏按内容跳过 | `ui/panel.ts` | 拼出 HTML 先和上次比，一样就不写 |
| FLIP 不再读矩形 | `ui/board.ts` | 位移自己乘格子宽算，不再问浏览器要 `getBoundingClientRect` |
| `fitBoard()` 按需执行 | `main.ts` | `ResizeObserver` 标脏，只在尺寸真变时才读写布局 |
| 顶栏按签名跳过 | `ui/panel.ts` | 十几个文字的签名一样就整段跳过 |
| `playerView()` 每帧只算一遍 | `main.ts` | 以前 render 和侧栏各算一次 |

---

## 2. 结果

32×32、43 支部队，同一台机器（多次运行取区间，绝对毫秒跨运行会漂 ±10%）：

| | 改之前 | 改之后 |
|---|---:|---:|
| 单帧最快（每帧换选中，玩家真在点的那种） | 18.7ms | **4.5~5.6ms** |
| 单帧中位 | 21.2ms | **7.9~8.7ms** |
| 单帧最快（画面完全没变） | 18.7ms | **1.5~2.3ms** |
| 每帧新建 DOM 元素 | 1 106 | **41** |
| 每帧写进 innerHTML | 66.4 KB | **3.8 KB** |
| 每帧调 `getBoundingClientRect` | 86 | **0** |
| 12×12 单帧最快 | 5.0ms | 1.7~3.0ms |
| 掉帧率（32×32） | 100% | 0% |

那 41 个元素全是侧栏——棋盘和棋子层现在是零。

---

## 3. 为什么这么做

### 3.1 格子：留着节点，只改 class

一局里格子的"身份"只定两次：位置（`x, y`）整局不变，地形开局定一次。
之后每帧真正会变的只有高亮档（可达 / 可攻击 / 威胁 / 可放置）。

以前每帧把这 1 024 个 `div` 连同城市、棋子一起丢掉重建。代价不只是拼字符串：
旧节点全被丢掉，浏览器的样式缓存作废，正在跑的动画被打断。

现在节点建一次就留着，逐格比算出来的 `className`，一样的一行 DOM 都不碰。

### 3.2 棋子：按 id 对号入座

同一件事发生在 43 个棋子上。现在每个棋子一个稳定的节点，插在地图上的
DOM 顺序仍然是"建筑 → 地面 → 空中"（`z-index` 管不了这件事，顺序才管），
但已经在对的位置一格都不动，只有真的换了顺序的节点才被挪。

顺带一个好处：**FLIP 动画不再打断自己**。以前每帧节点都是新的，
动画起点等于"从空白里冒出来"；现在节点是同一个，位移补的是真的位移动画。

### 3.3 FLIP：位移不必问浏览器

位置本来就是按 `(x, y)` 算百分比排的。一格的像素宽 = (棋盘宽 − 12) / 列数，
乘一下就有位移量。以前是"写完一大块 DOM → 读所有棋子的矩形 → 再写 transform"，
每一次读都让浏览器立刻把整套布局算一遍——**在真机上，这一读比动画本身贵得多**。

现在 `getBoundingClientRect` 在这条路径上彻底没有了。

### 3.4 侧栏：一样就不写

侧栏那 1.7ms 里，拼字符串只占 0.05ms，剩下的全在"把字符串变成 DOM"。
而大部分 `render()` 的触发和侧栏无关——棋盘上换了选中、顶栏换了回合、
AI 走了一步但金币和战报都没动。内容一模一样还重写一遍，等于每帧白扔一百多个节点，
还把滚动位置和正在输入的搜索框一起弄没。

判"一样"用的是拼出来的整串，不是另做一份摘要：摘要漏一个字段就会让面板
停在旧内容上，那种 bug 比慢难查得多。

> 有个坑：上帝模式会把侧栏整块换成兵种货架。之后回到普通局，如果新内容碰巧
> 和进沙盒前一模一样，"缓存说一样"就会让货架一直挂在屏幕上。所以直接改写侧栏
> 的地方要调一次 `invalidatePanel()`。

### 3.5 尺寸：只在真的变了才量

`fitBoard()` 要读 `offsetWidth` / `offsetHeight` / 计算样式，再写 `style`。
这一对读-写放在渲染流水线末尾，在真机上就是一次**强制同步布局**：
刚写完一千个格子的样式，浏览器为了回答"容器多宽"必须先把这一切算完。

而棋盘尺寸一年也变不了几次——窗口改大小、缩放换档、参谋部栏展开/收起，就这三件。
现在由 `ResizeObserver` 盯着这三处，真变了才把它标脏。

没有 `ResizeObserver` 的宿主（jsdom、很老的浏览器）量不到这些变化，
就老实每帧都量——那是从前的行为，慢一点，但不会算错。

## 4. 体检脚本也跟着改了

工具本身有两处必须改，否则它会骗人：

1. **主表默认改成"每帧换一个选中单位"**。增量重绘之后，"什么都不变"的帧所有缓存
   全命中，那一行的数字好看但不代表真机。现在主表用一个能重复的最小真实操作，
   另外两档（什么都不变 / 每帧全量重画）单独列在「缓存省了多少」一节里，
   三档一起看才是完整的图景。
2. **加了一列「读矩形」**。它由代码决定、不受机器影响，是"强制同步布局"最硬的证据。
   这一批把它从 86 降到了 0。

另外，正式采样前会先画一帧不进样本：那一帧要把格子节点建起来（换地图才发生一次）。
把它算进"最大帧"，抖动结论就会被它一个人带跑——玩家抱怨的"一顿一顿"是稳态里的抖动。

---

## 5. 还没做的

按现在的收益排：

1. **侧栏拆成几块各自缓存**：换一个选中会把整块 30KB 重写，顶卡和战报卡明明没变。
   预计能砍掉侧栏的 60~70%。
2. **雾视图按需重算**：`playerView()` 只依赖单位位置、视野和回合，这些没变就能复用。
3. **AI 决策让帧**：单次 8~10ms，一回合十几步会累加成肉眼可见的停顿。
4. **地形层 canvas 化**：**现在不划算了**。格子层已经不再重写，canvas 化只能省
   "样式重算与绘制"，却要动掉所有依赖 `.tile.t-water` 这类选择器的测试与样式。
   只有真机上确认瓶颈在绘制时再做。

顺带一句实话：脚本不含浏览器的布局与绘制，它测的是**下限**。
JS 侧已经进预算（32×32 p50 5~8ms），如果朋友那台机器还卡，瓶颈大概率在
绘制或合成那一半——那时候该开 DevTools 的 Paint flashing 看是不是整屏在闪，
而不是继续压脚本。
