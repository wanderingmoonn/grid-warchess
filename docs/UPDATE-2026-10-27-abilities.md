> 提交 `27bbaa5`。规则测试 304 项、界面测试 108 项全绿，行为快照与重构前**逐字节一致**。

## 一句话版

能力不再写成"内核里的一串 `if (hasAbility(def,'xxx'))`"，而是"一条定义 + 一组带时机的钩子"，
写在**能力主人自己的文件里**。加一个带新机制的兵种不用再碰 `rules.ts`；删一个扩展，
它带来的机制会跟着一起消失，不用回内核一行行找哪几段是谁的。

---

## 一、玩家会看到的变化

**一条，而且只在规则书里**：能力条目改成"先本体、后扩展"排列。

| 位置 | 之前 | 现在 |
|---|---|---|
| 规则书「进攻」章 | 先手、破甲、破城、自爆、**冲锋、吸血、狂暴**…… | 先手、破甲、破城、自爆、**长短皆可、冲锋、吸血**…… |
| 规则书「机动」章 | 穿林、潜行、收割、飞行…… | 潜行、飞行、掠空、穿林、收割…… |

原因是合并顺序变了：本体 11 条在前，奇想包 40 条按原来的先后跟在后面。
每条能力的名字、说明、"谁有"一栏都没有变。

**除此之外一个字节都没变**：伤害、取整、反击、溅射、状态层数、战报文案、AI 决策、
存档格式、联机同步全同。敢这么说不是靠肉眼看，是靠下面第五节那份快照——58 万个伤害点逐个对过。

---

## 二、为什么要动

改之前的形态是 55 处 `if (hasAbility(def, 'xxx'))`，散布在伤害、护甲、寻路、命中、
攻城、回合结算里。看着只是"代码不够漂亮"，实际有四个具体代价：

**1. 内核认识每个扩展的私货。**
`rules.ts` 里直接判断「淬毒」「筑墙」「掠空」「威吓」「重生」——这些全是某个兵种包的概念。
结果是内核和扩展互相依赖：`fantasy-packs.ts` 提供兵种，`rules.ts` 为它写实现，删任何一个都要先拆另一个。

**2. 一段公式里挤着十几件不相干的事。**
伤害计算从"扣地形掩护"到"同源护壁减半"连着十几段判断，其中能力判断就有十二段：

```
穿隙 → 林地之主 → 驻军 → 诅咒 → 咒域 → 扩展改甲 → 破甲
  → 冲锋 → 群势 → 追猎 → 狂暴 → 盾墙 → 威吓 → 长短皆可 → 游骑 → 魔法段 → 属性 → 同源护壁
```

报"某个兵不够疼"时，要在这十几行里定位那一行，而它和旁边那行没有任何结构上的隔离。

**3. 加兵种必须改内核，而且很容易改到对面。**
伤害公式是攻守共用的。给新兵种加一条守方能力，一不小心就写成了攻方条件——
这次重构第一版就踩了个现成的例子：攻守双方的护甲钩子合并成一张表之后，一个**自己带破甲**的兵，
在挨打时把自己的甲砍了一半（112,675 个伤害点当场变了）。常规用例没抓住，快照抓住了——
这也是为什么值得先花两分钟跑一份基线。

**4. 面板和结算各写一套口径。**
「狂暴」的 +50% 在伤害公式里一份、在面板的 `effectiveStats` 里又一份。
改一处漏一处时，玩家看到的是"面板写着 22，实际打出来 18"——而这种不一致最难被当成 bug 报上来。

## 三、现在的样子

四层，职责不重叠：

| 文件 | 管什么 | 规模 |
|---|---|---|
| `src/core/ability-hooks.ts` | 只定**接口与时机**：钩子签名、stage 常量、注入给扩展的 `api`。一条能力都不实现 | 424 行 |
| `src/core/abilities.ts` | 本体兵种的公共能力 | 11 条 |
| `src/core/fantasy-packs.ts` | 奇想包的能力（`FANTASY_ABILITIES`），挂在 `fantasy-core` 前置包上 | 40 条 |
| `src/core/ability-registry.ts` | 把核心表和各扩展贡献的表合并成一张查询表 | 134 行 |

`rules.ts` 里现在只剩 **3 处 `hasAbility`**，全在注入给扩展的 `api` 对象上。规则代码里
一处"按能力名判断"的分支都没有了——它只负责"在什么时机问一句"，不再知道有哪些能力。

**时机表**（`ability-hooks.ts`，数字有语义，别随便重排）：

| 组 | 时机 | 为什么必须这个顺序 |
|---|---|---|
| `DAMAGE_STAGE` | 加减(100) → 狂暴乘(200) → 盾墙减(300) → 威吓(400) → 远程折扣(500) → 游骑(600) → 同源护壁(700) | 乘法和加法不能互换：狂暴挪到盾墙后面，结果就差一点 |
| `ARMOR_STAGE` | 穿隙(100) → 林地之主(200) → **扩展改甲(500)** → 破甲(900) | 破甲要削"扩展加的那几点甲"；穿隙只免地形，不算破甲 |
| `HIT_STAGE` | 命中贴状态(100) → 属性精研(200) | 属性精研是"常驻属性"，得排在普通命中之后，不然火属性一次叠两层 |
| `STRIKE_STAGE` | 吸血(100) → 命中状态 → 击退(200) | 吸血按"真打出来的伤害"算，且要在反击之后；击退要先确认对面还活着 |
| `TURN_START` | 自愈(100) → 光环(200) → 动手(300) → 召唤(400) | 中间要清一次场：布雷能打死人，而"召唤上限"数的是活人 |
| `STAT_STAGE` | 面板数值(100) | 只给"现在就成立"的加成用 |

## 四、如果你是扩展作者

以前文档写的是两步：在 `abilities.ts` 加一条定义，在 `rules.ts` 找到时机加一个 `if`。
**这一步已经改了**，别按老路子写。

现在只有一步：把能力写进**你自己的文件**，挂到扩展的 `abilities` 字段上，再让兵种写上它的 id。

```ts
const MY_ABILITIES: AbilityDef[] = [
  {
    id: 'my-ability',
    name: '我的能力',
    summary: '生命低于一半时攻击 +3。',
    group: 'attack',
    hooks: {
      damage: [
        {
          stage: DAMAGE_STAGE.attackFlat,
          apply: (c) => {
            if (c.side !== 'attacker') return;              // ← 纪律二
            const def = c.api.utype(c.state, c.self.type);
            if (c.self.hp * 2 <= def.maxHp) c.damage += 3;
          },
        },
      ],
    },
  },
];

const MY_PACK: Expansion = {
  id: 'my-pack',
  name: '我的扩展',
  summary: '一句话说清它改变了什么。',
  hooks: {},
  abilities: MY_ABILITIES,   // ← 能力跟着扩展走，合并由 ability-registry 做
  units: [/* … */],
};
```

三条纪律，每条都是用血换的：

1. **钩子必须是纯函数**。面板的伤害预览和 AI 的试算都会调用它们，一旦有副作用，
   预览就会悄悄改变游戏状态。要随机就用 `ctx.api.hashPick`，从种子派生。
2. **攻守要分清**。护甲和伤害阶段双方的能力改的是同一坨数字，用 `ctx.side` 说明
   自己是出手的还是挨打的。漏了这一句，一个带破甲的兵在挨打时会把自己的甲砍一半。
3. **stage 不是随手填的数字**。不确定填哪个，就去抄一条语义相近的现有能力
   （`charge`、`shield-wall`、`woodland`），再跑一遍快照确认差异只有你预期的那几处。

完整说明在 `docs/EXTENSIONS.md` 第 6 节，那里还有"能力该写在哪"的判定表和"能力各归各家"这条
用例的来由。

## 五、怎么确认没改坏

结构重构最怕"某个取整、某个顺序悄悄挪了一格"，而常规用例刚好没覆盖到。所以这次先立证据，
再动手：`scripts/snapshot-behavior.ts` 把行为摊平成一份可 diff 的文件。

```bash
npm run snapshot -- before.json     # 改之前
# ...改...
npm run snapshot -- after.json      # 改之后
diff before.json after.json         # 必须是空的
```

覆盖范围：

- **伤害矩阵**：113 个参战兵种（带能力的全要，另加每个时代抽样的白板）两两对打，
  三种地形 × 两种距离 × 两种血量 × 反击 × 伤害预览，共 **580,368 个伤害点**；
- **面板数值**：2,712 个点——攻击/护甲的有效值和算式、移动力、视野、可达格、威胁格；
- **判定类**：潜行与隐匿、能不能站（掠水、掠空）、攻城伤害；
- **回合结算**：26 组，真跑两个回合，记下血量、状态、城市耐久和战报条数。

这次一共跑了三遍：改完 `rules.ts`、搬完扩展能力、最终态。三遍都是**逐字节一致**。

另外加了一条用例，把这次的结构约束钉住，防止过半年又长回去：

> **能力各归各家**：本体只留公共词汇；同一条能力不许在两个地方各声明一份
> （合并时"核心优先"，重复的那份会静默失效，改扩展里那份的人会以为生效了）。

常规闸门：`npm run test:rules`（304 项）、`npm run test:ui`（108 项）、`npm run build`、
`npm run manual`（14 册，能力仍是 51 条）。

以后新写一条能力，按这个判：

- 本体兵种要用，或两个以上扩展都要用 → 放本体，算公共词汇；
- 只有一个扩展在用 → 放那个扩展自己的文件；
- 只是留给兵种编辑器勾的词汇 → 当公共词汇处理。

唯一还"认识"具体能力的地方是 `src/core/ai.ts` 里三处战术打分（看到破城就更愿意去砸城、
看到盾墙就更愿意去顶线）。那是 AI 的判断，不是规则实现，这次没动它。
