# 邀请网友参与数据采集：风险清单与应对

> 面向"把对局数据采集从同学扩大到网友"这件事。
> 下面的判断都对着**当前这套实现**说（`warchess_reports` 表 + 结算卡上传 + 无账号体系），
> 不是通用套话。文末有 P0/P1/P2 清单，标明哪些我现在就能改。
>
> ⚠️ 本文不是法律意见。涉及合同条款、隐私政策定稿，建议找律师过一遍；
> 我能给的是"技术事实 + 常见做法"，不是"合规背书"。

---

## 0. 先认清这套系统的天花板

三件事决定了后面所有风险的上限，必须先说：

1. **没有账号，没有服务端权威。** 一局棋完全在浏览器里算完，上传的只是一份"声明"。
   服务端无法验证"这局真的这么打过"。所以**任何一条数据都只能当举报看待，不能当证据**。
2. **端点和 publishableKey 就在前端包里。** 谁打开 F12 都能拿到，直接 `curl` 往表里插行。
   这不是漏洞（设计如此），但它意味着：**一切防护都不能依赖"别人不知道入口"**。
   2026-10-28 开发时我就是这么插了十几条测试数据，一次没被拦。
3. **匿名 + 只写不读**是当前唯一的隐私设计：`anon` 只有 INSERT 策略，
   读不到任何行。这是对的，要保住——它是"网友互害"的最后一道墙。

结论：这套系统的合理定位是**"低价值、可污染、需交叉验证"的样本池**，
不是"可信数据集"。网友带来的风险不能用"信任"解决，只能用**分层 + 标记 + 剔除**解决。

## A. 数据安全（可用性层面）

### A1. 无上限写入 → 容量与配额被打爆
**现状**：`payload jsonb` 没有任何大小限制，也没有 `CHECK` 约束。
一条 POST 可以塞几十 MB 的 JSON；`turns` 可以是负数；`expansions` 可以是十万个元素。

**后果**：配额烧穿（云服务有额度）、查询变慢、备份变大，而且**删除需要管理员介入**。

**建议（P0）**：
```sql
-- 单行体积上限：正常报告 3~8KB，给到 256KB 已经很宽容
alter table public.warchess_reports
  add constraint warchess_reports_payload_size
  check (pg_column_size(payload) < 262144);
-- 基本范围
alter table public.warchess_reports
  add constraint warchess_reports_turns_range
  check (turns between 1 and 5000);
-- 扩展最多 40 个（现在全量 25 个）
alter table public.warchess_reports
  add constraint warchess_reports_exp_len
  check (cardinality(expansions) <= 40);
```

### A2. 限流是"客户端自报"，绕过成本为零
**现状**：30 条/小时，按 `client_id` 计数。但 `client_id` 是浏览器自己生成、自己带上来的。
攻击者每次请求换一个随机 id 即可无限插入——**一次 `for` 循环的事**。

**建议（P0/P1）**：
- P0：加**全局限流**（不依赖身份）：
  ```sql
  -- 每小时全站上限，防止单点爆破烧配额
  select count(*) from warchess_reports where created_at > now() - interval '1 hour';
  ```
  超过阈值直接 raise（阈值按"正常应该有多少人玩"定，比如 500/小时）。
- P1：给受邀网友发**一次性邀请码**（下节 E2）——这是唯一能真正做到"一人一份"的低成本办法。

### A3. 备份与可恢复性
**现状**：只写不读，没有 UPDATE/DELETE 策略 → 数据一旦写进去，**连你自己用 anon 也删不掉**，
只能走管理员通道。这是好事（防篡改），但也意味着误操作/污染只能靠管理员清理。

**建议（P1）**：每周导出一次 JSON 存本地；清理用"标记"而不是"删除"（见 C4）。

## B. 隐私保护

### B1. `client_id` 是**持久假名**，而界面承诺"不含任何能定位到你的东西"
**现状**：`client_id` 存在 `localStorage`，不清缓存就永久不变，并且**跟每一份报告绑定**。
它确实定位不到具体的人，但它能把"同一个浏览器的十几局"串成一条线——
这在个人信息保护法语境下**属于假名化的个人信息**（可识别性来自"可关联"），
不是"完全匿名"。界面上那句"不含任何能定位到你的东西"因此**不够准确**。

**建议（P0，改文案 + 改机制二选一）**：
- 文案：改成"不含玩家名、房间码、操作流水；会上传一个随机的浏览器代号，只用于限流和去重，不关联任何账号。"
- 机制（更彻底）：`client_id` 改成**按月轮换的盐 + 哈希**，让跨月不可关联；
  或干脆只在**上传那一刻随机生成**（限流就退化成"按小时全局限流"，见 A2）。

### B2. 元数据拼接
**现状**：`seed` + 精确到秒的 `created_at` + 棋盘尺寸 + 扩展组合 + `client_id`。
单看都无害，合起来足以刻画"某人某晚打了几局、什么规则、什么水平"。

**建议（P1）**：`created_at` 入库时**截断到分钟或小时**（分析不需要秒级精度）；
或另存一列 `created_hour`，原值只在客户端保留。

### B3. 未成年人
**现状**：无年龄门槛，网友里必然有未满 14 岁的。
《个人信息保护法》对不满十四周岁未成年人的个人信息有更严要求（需监护人同意）。

**建议（P0，靠文案 + 合理努力）**：
- 上传页写明"未满 14 岁请在监护人指导下使用本功能，或不要上传"；
- 不收集任何**能验证年龄**的信息（收生日反而更危险），只做"告知 + 明示同意"；
- 明确**不面向**未成年人做定向邀请。

### B4. 撤回同意 / 删除请求
**现状**：数据匿名 + 只写不读，**你无法从"某人"反查到他的行**，所以"删掉我的数据"
在技术上做不到（除非他保留自己的 `fingerprint`）。

**建议（P1）**：把它变成设计的一部分而不是缺陷：
- 文案里直说"提交后无法单独撤回，因为系统不知道哪条是你的"——**提前说清，比事后解释好**；
- 如果非要支持撤回：客户端保留自己上传过的 `fingerprint` 列表，提供"我要删除这些"，
  由管理员按 fingerprint 删。代价是这条通道本身会暴露"这个 fingerprint 是他提交的"。

### B5. 网关侧的 IP 日志
**现状**：数据库里没有 IP，但云服务网关/反代一定记了访问日志（平台侧）。

**建议（P1）**：向网友披露"托管方会记录访问日志，我们不在数据库里存 IP"。
这是"诚实披露"，不是"技术上保证"。

## C. 防篡改与恶意数据注入

### C1. 没有服务端权威 → 一切都是"声明"
**现状**：`winner`、`sides.roster`、`timeline` 全部由客户端算完提交。
一个懂行的人可以提交"我 3 回合灭了对面、阵容里 99 个坦克"。

**建议（P0，思路转换）**：
不要试图"拦住"（拦不住），而是**标注可信度**：
```sql
alter table public.warchess_reports
  add column if not exists verdict text not null default 'unverified';
  -- unverified / plausible / suspect / quarantined
```
分析时默认只用 `verdict in ('plausible')`，原始数据全留。

### C2. 结构校验缺失（最容易被自动化刷的点）
**现状**：`sides[].roster` 的 key 可以是任意字符串（`"__proto__"`、超长字符串、不存在的兵种 id）；
`timeline.samples` 可以是 100 万帧；`expansions` 可以是任意文本。

**后果**：不只是数据脏——如果哪天把这些字段渲染进管理页面，**就是存储型 XSS**；
导出成 CSV 再用 Excel 打开，会有公式注入（`=cmd|...`）。

**建议（P0，触发器里做白名单校验）**：
- `roster` 的 key 必须是已知兵种 id（可以在库里维护一张 `warchess_unit_ids` 小表）；
- `timeline.samples` 长度 ≤ 240（客户端就是这个上限）；
- `expansions` 每个元素匹配 `^[a-z0-9-]{1,32}$`；
- 所有文本字段剔除控制字符；导出 CSV 时给 `= + - @` 开头的内容加前缀 `'`。

### C3. 语义一致性（成本低、收益高）
**现状**：没有任何交叉校验。明显的自相矛盾行（赢家 0 城、`turns=1` 但有 200 次行动、
终局兵数 > 编制上限）现在混在数据里，会直接污染汇总。

**建议（P0）**：在**汇总脚本**里先跑一遍一致性检查（不改库也能做），
把可疑行单独统计、不参与主结论：
- `winner` 非空时，赢家 `cities >= 1`；
- `timeline.acts[x].RECRUIT` 与 `timeline.made[x]` 之和一致；
- 每方 `units <= 24`（编制上限）；
- `turns` 与 `acts.END_TURN` 数量级一致。

### C4. 污染处置剧本（P1）
发现一批可疑数据时，**不要 DELETE**：
```sql
update warchess_reports set verdict = 'quarantined'
 where campaign = 'XXXX' or created_at between '...' and '...';
```
保留原始证据，分析视图里过滤掉即可。删了就没法复盘"当初为什么判它可疑"。

### C5. 指纹去重不是防线
**现状**：`fingerprint` 唯一索引能防"手滑重传"，但攻击者换随机指纹即可绕过。
**建议**：把它当"数据整洁工具"，不当"安全机制"写进任何文档。

## D. 知识产权与授权（合作前必须落纸）

### D1. 数据来源合法性
- **能做**：采集"你的软件产生的、关于棋局的事实记录"（种子、回合数、阵容、胜负）。
- **不能做**：让网友上传**他们自己的**兵种表、自制地图、mod 文案——那可能是别人的作品，
  一旦进库再公开，侵权责任在你。当前 `packSize` 只存数量、不存自定义兵种内容，**这个克制要保住**。
- 若网友用**改了代码的客户端**上传（比如自己调了数值），数据本身不侵权，但会污染样本 →
  靠 `version` 字段过滤（已经存了 `report.v`）。

### D2. 版权归属
- 游戏本体、兵种表、规则、界面、以及**由软件生成的报告格式**：归你。
- 单条"这局打了 63 回合、A 方赢了"：属于**事实**，一般不构成作品，谁都不享有著作权。
- 但**汇编**（你挑选、编排、清洗后的整个数据集）在著作权法里可能构成"汇编作品"，
  前提是选择/编排有独创性。也就是说：**你公开数据集时，保护的是你的汇编，不是每一行。**
- 建议在文档里写死一句：*"游戏与工具链版权归作者；单局记录为事实数据，贡献者同意作者以任何目的使用。"*

### D3. 授权范围（最容易漏的一条）
"同意上传"≠"同意拿去训练模型"≠"同意公开"。至少要写清五件事：
1. **目的**：平衡性调整、AI 决策改进、（如果要）模型训练；
2. **范围**：是否可用于**商业**用途、是否可**转授权**给合作方、是否可**公开发布**；
3. **形式**：是否允许发布**聚合统计**（一般可以）、是否允许发布**原始行**（要单独同意）；
4. **期限**：永久 / N 年；**是否可撤回**（见 B4，技术上做不到，要提前说）；
5. **对价**：无偿（写明"不支付报酬、不承诺任何收益"）。

### D4. 署名
- 匿名贡献者通常**不希望**被署名（署名反而暴露"他玩了这个"）。
- 但公开数据集时，可以写"由 N 位匿名玩家贡献"——这是**集体致谢**，不是署名义务。
- 若你选 CC BY 之类的许可发布数据集，就要定义署名形式（如"数据来源：方格战棋"）。

### D5. 二次使用与再许可
- 你以后想**把数据给研究者**或**用于训练模型**：授权条款里必须已经覆盖，否则要重新征得同意（做不到）。
- 建议：一次性把范围写宽（"以任何目的、任何形式、在全球范围内、免费使用、复制、修改、汇编、发布、再许可"），
  同时在**告知页**里用大白话说清"可能用于训练模型、可能公开聚合统计"。
- 反过来：如果网友要求"只能用于研究、不得商用"，你要么拒绝，要么**打标分池**（`license` 列），
  别混在一起——混了就永远说不清哪条能用在哪。

### D6. 和网友的约定形式
不需要长篇合同。一页纸 + 一次点击足够：
- 页面上：一段 150 字以内的《数据贡献说明》+ 勾选"我已阅读并同意"；
- 入库时记 `consent_version`（比如 `2026-10-28.v1`），**证明"他同意的是哪一版"**；
- 保留一份 changelog：条款改了就升版本号，老数据标明用的是旧版。

## E. 合作机制（组织层面，成本最低收益最高）

### E1. 加"批次/邀请码"（P0，强烈建议）
你现在最缺的不是防作弊，是**知道哪批数据是谁带来的**——一旦某位网友刷了几百条，
你需要能一次性隔离他带来的全部数据。

**做法**：邀请链接带 `?campaign=abc123`，上传时把 `campaign` 写进单独一列
（不是身份，是批次）。分析视图里默认排除被隔离的批次。

### E2. 一次性邀请码（P1，真正的"一人一份"）
```
warchess_invites(code pk, campaign text, max_uses int, used int, expires_at timestamptz)
```
网友拿到 `ABCD-1234`，客户端上传时带上；触发器校验并 `used += 1`。
好处：能限总量、能按人追责（谁泄露了码）、能作废。
代价：多一张表 + 一点客户端改动；码被转发仍会失效（`max_uses` 到了就拒）。

### E3. 数据分层（P0，零成本）
| 层 | 内容 | 谁能看 |
|---|---|---|
| raw | 原样入库，含可疑行 | 只有你（管理员） |
| curated | 通过一致性检查、状态 `plausible` | 你 + 合作研究者 |
| published | 聚合统计（不是原始行） | 公开 |

**永远别把 raw 直接公开**——里面有 `client_id` 和精确时间戳。

### E4. 保留期（P1）
建议 180 天自动清理（脚本里已有注释好的语句），并在告知页写明。
理由不是省空间，是**降低"长期留存可关联数据"的风险**。

## G. 需要你拍板的三件事

1. **数据用途写到多宽？** 只用于平衡性调整，还是也包括"训练模型、公开数据集"？
   这决定告知文案和授权条款的写法——**写窄了以后想扩用，技术上补不回来**。
2. **要不要能"删掉某人的数据"？** 要的话就得引入可识别的键（破坏匿名），
   不要的话就得在文案里**明说不能撤回**。两者只能选一个。
3. **网友是"匿名贡献者"还是"合作者"？** 后者通常意味着：写明贡献范围、给致谢、
   可能约定不得转售数据。前者简单，但你对数据质量没有任何抓手。

我的建议：**用途写宽（含模型训练与聚合公开）、不做单人删除（明说）、按匿名贡献者对待
但用 campaign/邀请码做批次管理**。理由：这套系统的价值在于量，不在于可追溯；
要可追溯就得上账号，那是另一个工程。
