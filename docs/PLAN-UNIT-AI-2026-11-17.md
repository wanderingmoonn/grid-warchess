# 单兵 AI（自主分）· 改动计划

> 2026-11-17。配套文档：`DESIGN-UNIT-AI-2026-11-17.md`（改动清单、接口、红线）。
> 这份只管**顺序、每步的验收、失败信号、怎么退**。
>
> 背景：boss 的数值和演出还没整理好，所以这一轮只打地基。
> 地基的目标是——**加了这套机制之后，现有对局一个字节都不变**。

---

## 总览

| 阶段 | 做什么 | 改动量 | 风险 |
|---|---|---|---|
| 0 | 拆掉 50 步上限（独立提交） | 小 | 中（会改 AI 行为，基线要重跑） |
| 1 | 骨架：字段 + 注册表 + 插入点，**默认全 0** | 中 | 低（验收＝零变化） |
| 2 | 一个测试兵 + `must`，把三道门试出来 | 小 | 低（只在 dev 夹具里） |
| 3 | 接真法术：冷却/充能/沉默/出生当回合 | 中 | 中（容易被规则拒） |
| 4 | 探针 + 跑批 + 回放断言 | 中 | 低 |

阶段之间**必须各自独立提交**。原因很实际：阶段 0 会让 208 场基线作废，
如果和阶段 1 混在一起，跑出来分不清是"步数变了"还是"单兵 AI 生效了"。

## 阶段 0：拆掉 50 步上限

**为什么先做它**：它改的是 AI 行为，而阶段 1 的验收标准是"行为零变化"。
顺序反了，阶段 1 就永远证明不了自己没动东西。

### 步骤

1. **先量，别先改。** 用现有 20 局一批的跑法，记录：每回合实际动作数分布、
   `capHits` 次数、哪些局面撞得多（满编？多城？）。这份数据留档，
   它是"这刀切得对不对"的唯一凭据。
2. 加 `aiStepCap(s)`：`8 + 3 × 本单位数 + 6 × 本城数`。放 `ai-meta.ts`，
   和 `AI_MAX_STEPS` 并排，注释写清"这个数是按编制上限 24 推的，改了要重推"。
3. `src/main.ts:5601` 的循环改成用 `aiStepCap(s)`。
4. 加**卡死检测**：连续 3 次成功动作后局面指纹没变 → 直接交棒，并在战报写一句
   "AI 卡住，强制交棒"。指纹只要"单位数 + 血量合计 + 金币 + 城数 + 回合数"这种粗摘要，
   不用追求精确——它要抓的是"反复做同一件没用的事"。
5. 撞自然上限时记一次告警（`console.warn` + 战报一句），别静默截断。
6. `AI_MAX_STEPS` 保留，加 `@deprecated` 注释：`scripts/baselines/*` 和二十多个脚本
   还在 import 它，删了会把基线一起打断。

### 验收

```bash
npm run build          # 类型过
npm run test:rules     # 规则不受影响
npm run probe:level    # 关卡模式照旧
```

再跑 20 局对局，确认：

- 不再出现"满编局走到一半停住"（这是拆上限要解决的原始症状）；
- 没有一局卡死（卡死检测要么没触发，要么触发后正常交棒）；
- 记录下胜负和回合数，和阶段 0 之前的 20 局对比——**变化是预期内的，
  但要看变化有多大**。

### 失败信号

- 撞上限的次数比之前更多 → 说明式子给太小了，重推。
- 出现死循环 → 卡死检测写错了（可能把"合法但无进展"当成进展）。
- 胜负分布剧烈偏移 → 停下来想：是不是 50 步一直在保护某个局面的平衡。

### 怎么退

单个提交 revert 即可，`AI_MAX_STEPS` 一直在，主流程退回 50 就恢复原状。

## 阶段 0 实测记录（2026-11-17 已完成）

工具：`npm run probe:ai-steps`（新脚本 `scripts/probe-ai-steps.ts`）。
同一批种子跑两遍，一遍用 50、一遍用 `aiStepCap(s)`，并排打印每回合动作数。

### 结果

| 配置 | 局数 | 总回合 | 平均动作/回合 | p50 | p90 | p99 | 最大 | 撞上限 |
|---|---|---|---|---|---|---|---|---|
| 中世纪 16×16 时代2 | 3×2 档 | 260 | 8.5 | 8 | 12~16 | 17~21 | 23 | **0 次** |
| 信息化 20×20 时代5 | 3×2 档 | 243 | 8.2 | 7 | 16 | 21 | 22 | **0 次** |
| 中世纪短测 | 2×2 档 | 80 | 8.4 | 8 | 12 | 14 | 15 | **0 次** |

按兵数分档也一样：**21+ 个兵时平均 9.3~9.8 步、p90 18、最大 23**，仍然离 50 很远。

**两档的逐局结果完全相同**（回合数、总步数、胜负一字不差），所以这次改动
是行为上的空操作——可以放心合。

### 结论（修正了之前的推断）

- **50 现在不是瓶颈。** 上一轮按"24 兵 × 2 个动作 = 48"推的"必然撞上限"，
  实测没发生：AI 在"没有值得做的事"时就返回 null 收手（`best.v <= 0`，ai.ts:6290），
  20 个兵里常只有 8 个觉得该动。
- **拆它的理由是将来。** 单兵 AI 上线后，扩展会主动提正分动作，步数才涨得起来；
  那时再改，会把"名额变化"和"单兵 AI 效果"混在一次评估里。
- **顺带暴露了真正的病灶**：20 个兵里一半以上每回合什么都不做。
  这不是名额问题，是"走位收益太低 + 评分门槛"的问题。**这次不动它**——
  换个议题单独量，别顺手改。

### 本阶段改动

| 文件 | 改了什么 |
|---|---|
| `src/core/ai-meta.ts` | 新增 `aiStepCap(s)`；`AI_MAX_STEPS` 标 `@deprecated` 保留 |
| `src/core/ai.ts` | 转出 `aiStepCap` |
| `src/main.ts` | 循环改用 `aiStepCap(state)`（回合开始算一次）+ 撞上限 `console.warn` |
| `scripts/probe-ai-steps.ts` | 新增测量脚本（本文件上方"工具"那行） |
| `package.json` | 加 `probe:ai-steps` |

回归：`test:rules` 956 项全过、`probe:level` 全过、`tsc --noEmit` 无错。

## 阶段 0b 实测记录（2026-11-17 完成）

**目标：给"成功但没进展"的动作装一个刹车。** 名额只能保证"不会烧到天上去"，
它兜不住"这一回合剩下的人全都不动"——因为这种动作每一步都是合法的。

### 判据（为什么这么窄）

```
同一个动作 key 连续成功 且 局面指纹没变 → 计数 +1
计数到 2（即第 3 次执行）→ 判定卡死，交棒
```

- **只认同一个动作重复**。不用"连续三步都没变化"：那会误伤一类正常打法——
  三个兵依次进入某种只改 `custom` 的架势（每人做的事不一样，但局面指纹一样）。
- **指纹不含 `unit.custom`**。形态、姿态、层数都在那里；算进去的话，
  "切换形态"永远显示"有变化"，最典型的空转反而抓不到。
  指纹只认玩家看得见的东西：站位、血量、moved/acted、单位数、金币、城、留痕、胜者。
- **只喂成功的动作**。被规则拒掉的由 `rejected` 管，喂进来会把"AI 在换方案"
  误判成"AI 卡住了"。

### 改了什么

| 文件 | 改动 |
|---|---|
| `src/core/ai-meta.ts` | 加 `aiProgressFingerprint(s)`、`aiStallGuard(limit=2)` |
| `src/core/ai.ts` | 转出这两个 |
| `src/main.ts` | `runAiTurn` 每回合建一个 guard，每个成功动作后 `note`；判定卡死就 `break` + `console.warn`（**不 `return`**，这一回合仍要正常交割） |
| `scripts/probe-ai-steps.ts` | 同步使用 guard，汇总表加"卡死"列——**测量口径和实机必须一致**，否则"实测没卡死"是句空话 |
| `scripts/test-ai-optimization.ts` | 加 4 条用例：重复判定、真变化清零、换着做不算、指纹含坐标不含 custom |

### 验证

- `test:ai-optimization` **53 项全过**（含新增 4 条）。
- `probe:ai-steps` 2 局 120 回合：**卡死 0 次**，每回合步数与此前完全一致（527 / 511）
  ——说明它没有误判正常对局。
- 一个已知的临时不一致：**跑批脚本仍用 `AI_MAX_STEPS`，没有装 guard**。
  它们靠 50 步兜底，不算错；等阶段 4 统一迁移时一起加（那时要重跑基线）。

## 阶段 1：骨架（默认全 0）

**目标：加完这套东西，对局行为逐动作与改动前完全一致。** 这是本阶段唯一硬指标。

### 步骤

1. `src/core/types.ts`：`UnitTypeDef` 加 `aiAutonomy?` / `aiProfile?`。
   注释里写死"缺省＝0＝行为完全不变"，并说明为什么不把函数塞进兵种表。
2. `src/core/expansions.ts`：`Expansion` 加 `unitAi?: UnitAiProfile[]`，
   定义 `UnitAiCtx` / `UnitAiResult` / `UnitAiProfile` 三个类型。
3. 新文件 `src/core/unit-ai.ts`：照 `mark-registry.ts` 的写法建注册表。
   包含：查询、**动作白名单校验**、`unitId` 一致性断言、重复 id 报错、
   以及"兵种写了 profile 但没注册"的一次性警告。
4. `src/core/ai.ts`：在 per-unit 循环里插入（顺序见 DESIGN 第 6 节）。
   一句话版本：先跑原来的候选，再问 profile，`add` 乘自主分推进表，`must` 给 1000。
5. 探针段 1（新增 `scripts/probe-unit-ai.ts`）：**零变化断言**。
   同一批种子、同一配置，改动前后各跑一遍，逐条比对动作序列。

### 验收

```bash
npm run probe:unit-ai        # 第 1 段：零变化
npm run test:ai-optimization # AI 场景 25 项不红
npm run test:replay          # 回放还成立
```

### 失败信号

- 零变化断言红 → 九成是"没写字段时也走进了新分支"。检查 `aiAutonomy > 0 && profile` 这条早退。
- 类型循环报错 → 新文件被 `ai.ts` 和 `expansions.ts` 同时引用，出现了环。
  Node 的 ESM 环是运行时才炸（`undefined`），`tsc` 看不出来，所以要么把类型放 `types.ts`，
  要么让注册表只依赖 `expansions.ts` 一个方向。

### 怎么退

加的全是可选项，删掉新分支就回到原状。这一步**没有数据迁移**，不需要兼容代码。

## 阶段 2：一个测试兵 + `must`（只在 dev 夹具里）

**目标：把三道门试出来**——分差够不够、被拒之后会不会重复提、会不会被推演削没。
这一步不碰真 boss，用一个 `dev: true` 的测试关 + 一个测试兵种，不进玩家菜单。

### 步骤

1. 测试兵种：随便一个普通属性，`aiAutonomy: 1`，`aiProfile: 'probe-min'`。
2. 极简 profile：只有一个"必须做"——比如"第 3 回合往 (x,y) 走一步"。
   用最简单、最容易验证的动作，别一上来放法术。
3. 跑探针，回答四个问题（每个问题单独一段断言）：
   - `must` 会不会被普攻抢走 → 如果会，分给低了；
   - 被规则拒掉之后，会不会每一步都重提 → 应该只提一次，然后换别的；
   - 被推演削分削掉了吗 → 如果会，说明它需要 `ignoreRisk`；
   - 被 1.5% 随机带宽吃掉了吗 → 如果会，`must` 的分不够高。
4. 把实测结论写回 DESIGN 第 5 节那张"分数换算表"（哪些数是实测的、哪些是拍的）。

### 验收

- 测试兵在 20 局里，100% 按 profile 指定的回合做出指定动作；
- 日志里没有"每步重提同一个被拒动作"；
- 战报里看不到异常告警。

### 失败信号

- 时灵时不灵 → 是随机带宽或推演在作怪，别急着改引擎，先把 `must` 分拉到 1000 再看。
- 它抢走了本该补刀的动作 → `must` 条件写得太宽（"第 3 回合"不等于"第 3 回合无论什么情况"）。

## 阶段 3：接真法术

**目标：让 boss 真的会放法术，且守住四条闸。**

修真的施法走 `HERO_SKILL` 动作，`doHeroSkill`（`rules.ts:7700`）**不要求兵种是英雄**，
冷却、充能、`skillTurn`（一回合一次）、`bornTurn`（出场当回合不能放）、`canCastSkill`（沉默）
全都是现成的。这一阶段不用改规则层，只需要 profile 正确地把动作提出来。

### 步骤

1. profile 生成 `HERO_SKILL` 候选：选技能 → 选目标 → 给分。目标选择要自己写
   （全局 AI 不会替你选，它连这个效果是什么都不知道）。
2. 四条闸逐个验：冷却没好、充能打空、被沉默、刚出场那一回合。
   **每一条都要有断言**，因为这个阶段最容易出的错是"提了个必被拒的动作"。
3. 迷雾验证：断言 handler 拿到的 `state` 里没有玩家看不见的敌人
   （用"雾里藏一个兵，profile 不许选它"来测）。

### 失败信号

- 一回合被拒五六次 → profile 没自查（距离/射程/冷却）。规则层的拒是有成本的：
  每次被拒都白耗一步，一回合被拒多次，表现就是"boss 站着不动"。
- boss 隔墙打到了雾里的兵 → 有人在 handler 里读了真局，立刻回退。

## 阶段 4：探针、跑批、回放

### 要做

1. `probe:unit-ai` 补齐六段：零变化 / 一个兵能自己动 / 三道门 / 四条闸 / 迷雾 / 卡死保险。
2. 跑批对比：开与不开单兵 AI，各 20 局，看**回合数、胜负、崩溃率**。
3. 回放：带 boss 的一局导出回放，重放后动作序列一致。
4. 在 `docs/` 留一份"实测记录"：哪些结论有数据、样本多大、哪些只是方向。

### 诚实说明（写进报告，别省）

- 跑批衡量的是"对某个固定旧 AI 的胜率"，**不衡量"好不好玩"**。
  它只能证明"这个 boss 不会自己把自己玩死"。
- 20 局只能看方向，不能下结论。要下结论至少 100 局以上，且要固定种子。

## 明确不做（这一轮）

- boss 的数值、技能清单、阶段流程。
- 演出：预告格、播报文案、镜头、音效。
- 仆从波次和关卡配置（那属于「黑暗动乱」包的内容）。
- 席位级 AI（造兵/升级/换血/复活）的任何改动。
- 寻路、队形、投送（过河那类问题）。

## 风险和回退

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 拆 50 步后 AI 行为大变，平衡被打破 | 中 | 高 | 阶段 0 先量后改，独立提交，随时 revert |
| 零变化验收做不到 | 低 | 中 | 说明新分支没早退；先修分支条件，别改验收标准 |
| profile 被写成"作弊 AI"（读真局） | 中 | 高 | 类型上就不给它真局；代码 review 只查这一条 |
| 每个包都想给自己的兵开自主 | 一定会发生 | 中 | 文档层面定死：只给关卡 boss 填值；普通兵填了要问"为什么不改全局 AI" |
| 50 步拿掉之后没人做跑批脚本迁移 | 中 | 中 | 在计划里单列一步，别指望"顺便"完成 |

## 一句话记住

**机制是通用的一次性成本，行为是每个包自己的长期成本。**
接口越窄，以后越不需要回来改核心；反过来，只要有人开始要求"改全局估值"，
就说明这个口子开歪了。
