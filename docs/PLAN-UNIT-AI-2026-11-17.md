## 阶段 0：拆掉 50 步上限

**为什么先做它**：它改的是 AI 行为，而阶段 1 的验收标准是"行为零变化"。
顺序反了，阶段 1 就永远证明不了自己没动东西。

### 步骤

1. **先量，别先改。** 用现有 20 局一批的跑法，记录：每回合实际动作数分布、
   `capHits` 次数、哪些局面撞得多（满编？多城？）。这份数据留档，
   它是"这刀切得对不对"的唯一凭据。
2. 加 `aiStepCap(s)`：`8 + 3 × 本单位数 + 6 × 本城数`。放 `ai-meta.ts`，
   和 `AI_MAX_STEPS` 并排，注释写清"这个数是按编制上限 24 推的，改了要重推"。
3. `src/main.ts:5601` 的循环改成用 `aiStepCap(s)`。
4. 加**卡死检测**：连续 3 次成功动作后局面指纹没变 → 直接交棒，并在战报写一句
   "AI 卡住，强制交棒"。指纹只要"单位数 + 血量合计 + 金币 + 城数 + 回合数"这种粗摘要，
   不用追求精确——它要抓的是"反复做同一件没用的事"。
5. 撞自然上限时记一次告警（`console.warn` + 战报一句），别静默截断。
6. `AI_MAX_STEPS` 保留，加 `@deprecated` 注释：`scripts/baselines/*` 和二十多个脚本
   还在 import 它，删了会把基线一起打断。

### 验收

```bash
npm run build          # 类型过
npm run test:rules     # 规则不受影响
npm run probe:level    # 关卡模式照旧
```

再跑 20 局对局，确认：

- 不再出现"满编局走到一半停住"（这是拆上限要解决的原始症状）；
- 没有一局卡死（卡死检测要么没触发，要么触发后正常交棒）；
- 记录下胜负和回合数，和阶段 0 之前的 20 局对比——**变化是预期内的，
  但要看变化有多大**。

### 失败信号

- 撞上限的次数比之前更多 → 说明式子给太小了，重推。
- 出现死循环 → 卡死检测写错了（可能把"合法但无进展"当成进展）。
- 胜负分布剧烈偏移 → 停下来想：是不是 50 步一直在保护某个局面的平衡。

### 怎么退

单个提交 revert 即可，`AI_MAX_STEPS` 一直在，主流程退回 50 就恢复原状。

## 阶段 0 实测记录（2026-11-17 已完成）

工具：`npm run probe:ai-steps`（新脚本 `scripts/probe-ai-steps.ts`）。
同一批种子跑两遍，一遍用 50、一遍用 `aiStepCap(s)`，并排打印每回合动作数。

### 结果

| 配置 | 局数 | 总回合 | 平均动作/回合 | p50 | p90 | p99 | 最大 | 撞上限 |
|---|---|---|---|---|---|---|---|---|
| 中世纪 16×16 时代2 | 3×2 档 | 260 | 8.5 | 8 | 12~16 | 17~21 | 23 | **0 次** |
| 信息化 20×20 时代5 | 3×2 档 | 243 | 8.2 | 7 | 16 | 21 | 22 | **0 次** |
| 中世纪短测 | 2×2 档 | 80 | 8.4 | 8 | 12 | 14 | 15 | **0 次** |

按兵数分档也一样：**21+ 个兵时平均 9.3~9.8 步、p90 18、最大 23**，仍然离 50 很远。

**两档的逐局结果完全相同**（回合数、总步数、胜负一字不差），所以这次改动
是行为上的空操作——可以放心合。

### 结论（修正了之前的推断）

- **50 现在不是瓶颈。** 上一轮按"24 兵 × 2 个动作 = 48"推的"必然撞上限"，
  实测没发生：AI 在"没有值得做的事"时就返回 null 收手（`best.v <= 0`，ai.ts:6290），
  20 个兵里常只有 8 个觉得该动。
- **拆它的理由是将来。** 单兵 AI 上线后，扩展会主动提正分动作，步数才涨得起来；
  那时再改，会把"名额变化"和"单兵 AI 效果"混在一次评估里。
- **顺带暴露了真正的病灶**：20 个兵里一半以上每回合什么都不做。
  这不是名额问题，是"走位收益太低 + 评分门槛"的问题。**这次不动它**——
  换个议题单独量，别顺手改。

## 阶段 0b 实测记录（2026-11-17 完成）

**目标：给"成功但没进展"的动作装一个刹车。** 名额只能保证"不会烧到天上去"，
它兜不住"这一回合剩下的人全都不动"——因为这种动作每一步都是合法的。

### 判据（为什么这么窄）

```
同一个动作 key 连续成功 且 局面指纹没变 → 计数 +1
计数到 2（即第 3 次执行）→ 判定卡死，交棒
```

- **只认同一个动作重复**。不用"连续三步都没变化"：那会误伤一类正常打法——
  三个兵依次进入某种只改 `custom` 的架势（每人做的事不一样，但局面指纹一样）。
- **指纹不含 `unit.custom`**。形态、姿态、层数都在那里；算进去的话，
  "切换形态"永远显示"有变化"，最典型的空转反而抓不到。
  指纹只认玩家看得见的东西：站位、血量、moved/acted、单位数、金币、城、留痕、胜者。
- **只喂成功的动作**。被规则拒掉的由 `rejected` 管，喂进来会把"AI 在换方案"
  误判成"AI 卡住了"。

### 改了什么

| 文件 | 改动 |
|---|---|
| `src/core/ai-meta.ts` | 加 `aiProgressFingerprint(s)`、`aiStallGuard(limit=2)` |
| `src/core/ai.ts` | 转出这两个 |
| `src/main.ts` | `runAiTurn` 每回合建一个 guard，每个成功动作后 `note`；判定卡死就 `break` + `console.warn`（**不 `return`**，这一回合仍要正常交割） |
| `scripts/probe-ai-steps.ts` | 同步使用 guard，汇总表加"卡死"列——**测量口径和实机必须一致**，否则"实测没卡死"是句空话 |
| `scripts/test-ai-optimization.ts` | 加 4 条用例：重复判定、真变化清零、换着做不算、指纹含坐标不含 custom |

### 验证

- `test:ai-optimization` **53 项全过**（含新增 4 条）。
- `probe:ai-steps` 2 局 120 回合：**卡死 0 次**，每回合步数与此前完全一致（527 / 511）
  ——说明它没有误判正常对局。
- 一个已知的临时不一致：**跑批脚本仍用 `AI_MAX_STEPS`，没有装 guard**。
  它们靠 50 步兜底，不算错；等阶段 4 统一迁移时一起加（那时要重跑基线）。

### 关键实现选择（和原设计的两处微调）

1. **`must` 给 1000 且 `ignoreRisk: true`**。原设计只说"给固定高分"。落地时把
   "跳过推演削分"也挂上了——否则作者写的"第三回合变身"会被"对面下一回合能打多疼"
   否决掉，流程时灵时不灵。代价是：如果 `must` 是攻击型招式，它会不顾伤亡地打出去。
   这正是剧本要的。
2. **`score` 在进入候选表时才乘自主分**（`c.score * autonomy`），扩展给的是
   "这个 profile 认为值多少"。同一个 profile 挂在自主分 0.5 的兵身上自动打折，
   不用每个扩展自己乘。

### 探针结果（全过）

```

[1] 零变化：
    · 自主分 0          → handler 一次都没被调用，序列一致 ✓
    · 自主分 1、返回空   → handler 被调用了，序列仍一致 ✓（这条证明路是通的，不是死代码）
    · 自主分 1、未注册   → 静默降级 + 警告一次，序列一致 ✓
    · 自主分 1、提非法动作（END_TURN）→ 被丢弃 + 告警，序列一致 ✓
[2] 查不到 profile 时返回 null，不抛错 ✓
[3] 白名单：走/施法可用；结束回合、招募、替别的兵做主 被拦 ✓
[4] 本局 52 个兵种，写 aiProfile 的 0 个 ✓；悬空 aiProfile 能被查出来 ✓
```

## 阶段 2：一个测试兵 + `must`（只在 dev 夹具里）

**目标：把三道门试出来**——分差够不够、被拒之后会不会重复提、会不会被推演削没。
这一步不碰真 boss，用一个 `dev: true` 的测试关 + 一个测试兵种，不进玩家菜单。

### 步骤

1. 测试兵种：随便一个普通属性，`aiAutonomy: 1`，`aiProfile: 'probe-min'`。
2. 极简 profile：只有一个"必须做"——比如"第 3 回合往 (x,y) 走一步"。
   用最简单、最容易验证的动作，别一上来放法术。
3. 跑探针，回答四个问题（每个问题单独一段断言）：
   - `must` 会不会被普攻抢走 → 如果会，分给低了；
   - 被规则拒掉之后，会不会每一步都重提 → 应该只提一次，然后换别的；
   - 被推演削分削掉了吗 → 如果会，说明它需要 `ignoreRisk`；
   - 被 1.5% 随机带宽吃掉了吗 → 如果会，`must` 的分不够高。
4. 把实测结论写回 DESIGN 第 5 节那张"分数换算表"（哪些数是实测的、哪些是拍的）。

### 验收

- 测试兵在 20 局里，100% 按 profile 指定的回合做出指定动作；
- 日志里没有"每步重提同一个被拒动作"；
- 战报里看不到异常告警。

### 失败信号

- 时灵时不灵 → 是随机带宽或推演在作怪，别急着改引擎，先把 `must` 分拉到 1000 再看。
- 它抢走了本该补刀的动作 → `must` 条件写得太宽（"第 3 回合"不等于"第 3 回合无论什么情况"）。

### 实际怎么做的（2026-11-18 完成，和计划有偏差）

**没做 dev 关卡。** 原计划是"一张 `dev: true` 的测试关 + 一个测试兵种"，后来改成
**在探针里手工搭一个小局面**（12×12 全平地、B 方一个探针 boss、A 方一个贴脸民兵、无城）。
理由：boss 的内容还没定，做一张 dev 关等于先把关卡结构定死；而手工小局面能把
"普攻在竞争""走不到的目的地""换个种子"这三个变量分别单独控制住，真对局里它们会缠在一起。
兵种也是**探针内注入**的（`s.unitTypes['probe-boss']`），不进出厂兵种表。

### 三道门的答案（`probe:unit-ai` 第 5 段，7 条断言全过）

| 问题 | 实测答案 |
|---|---|
| `must` 会被贴脸普攻抢走吗 | **不会。** 1000 压得住，换 8 个种子无一失手 |
| 被拒之后会不会每步重提 | **谈不上——它根本到不了被拒那一步。** 候选在挑选前就被 `applyAction(view,…)` 筛掉了，走不到的目的地压根不会变成动作。这是好消息，但值得钉住：谁把这个筛子优化掉，扩展写错坐标就会变成每回合空转 |
| 会被 1.5% 随机带宽吃掉吗 | 不会（1000 对带宽 15，差了一个量级）；但**低分的 `add` 会被吃掉**——这正是要求"想抢就让分高于普攻"的原因 |
| 自主分真的在打折吗 | 会。同一个 `add` 200 分：自主分 1 时抢得过普攻，自主分 0.01（=2 分）时输掉 |

### 顺手量出的基准值

**24 攻打 100 血 2 甲，贴脸一记普攻 ≈ 89 分。** 原表里"打一下 10~40"偏低——
评分里还算了"会不会打死"和"目标价值"。已写回 DESIGN 第 5 节。

### 踩到的坑（自己的，不是引擎的）

探针里用二分找这个 89 分时写了 `Math.round((lo+hi)/2)`：当 `lo=2, hi=3` 时
`mid=3`，"赢了"的分支 `hi=mid` 减不下去 → **死循环，进程被系统杀掉（exit 137）**。
改成 `Math.floor`。教训：二分只要有一个分支把 `hi` 设成 `mid`，就必须向下取整。

### 验收对照

| 计划里的验收 | 实际 |
|---|---|
| 20 局里 100% 按指定回合做出指定动作 | 没跑 20 局：小局面里 8 个种子各一次，全中。**样本说明**：这是"机制正确"的证据，不是"实机稳定"的证据——后者要等真 boss 和真关卡 |
| 日志里没有每步重提 | 结构上不可能（见上表第 2 行），另外钉了一条 rejected 契约 |
| 战报里没有异常告警 | 探针里只有预期内的两条（未注册 profile、非法动作），各一次 |

## 阶段 3：接真法术

**目标：让 boss 真的会放法术，且守住四条闸。**

修真的施法走 `HERO_SKILL` 动作，`doHeroSkill`（`rules.ts:7700`）**不要求兵种是英雄**，
冷却、充能、`skillTurn`（一回合一次）、`bornTurn`（出场当回合不能放）、`canCastSkill`（沉默）
全都是现成的。这一阶段不用改规则层，只需要 profile 正确地把动作提出来。

### 步骤

1. profile 生成 `HERO_SKILL` 候选：选技能 → 选目标 → 给分。目标选择要自己写
   （全局 AI 不会替你选，它连这个效果是什么都不知道）。
2. 四条闸逐个验：冷却没好、充能打空、被沉默、刚出场那一回合。
   **每一条都要有断言**，因为这个阶段最容易出的错是"提了个必被拒的动作"。
3. 迷雾验证：断言 handler 拿到的 `state` 里没有玩家看不见的敌人
   （用"雾里藏一个兵，profile 不许选它"来测）。

### 失败信号

- 一回合被拒五六次 → profile 没自查（距离/射程/冷却）。规则层的拒是有成本的：
  每次被拒都白耗一步，一回合被拒多次，表现就是"boss 站着不动"。
- boss 隔墙打到了雾里的兵 → 有人在 handler 里读了真局，立刻回退。

### 实际怎么做的（2026-11-18 完成，用邪龙王当靶子）

**靶子选了奇想包的邪龙王**：真英雄、真技能（陨卵）、真产物链（卵 → 魔龙）。
用真东西验，比拿假技能凑数可信。

工具：`scripts/probe-dragon-king.ts`（一次性实验，不进 `npm test`）。

**场地**：16×16 空地，两家各留一座城摆在对角（**不能清空城**，没有城第一帧就判出局），
B 方一条邪龙王在南边，A 方三个 600 血「木桩」在北边。
木桩是自己造的兵种：真兵（民兵 28 血、骑士 60 血）会被一发陨卵（约 30 魔法伤害）打成灰，
五个回合就结束，魔龙还没孵出来——观察窗口全没了。

| 指标（20 回合，一个种子） | 原样 | 挂行为 |
|---|---|---|
| 王离最近敌人的平均距离 | 8.2 格 | **9.6 格** |
| 平均"余量"（>0 = 对方打不到它） | 7.2 | **8.6** |
| 一路压到几格 | **3 格**，第 16 回合开始普攻 | 全程 **8~12 格**，一次都没打 |
| 下蛋次数 | 4 | 4 |
| 魔龙峰值 | 3 | 3 |
| 魔龙离王的平均距离 | 5.3 | **4.2** |

三件想做的事都做到了：

1. **在射程外游弋**：原样是"一路拱到 3 格然后开打"，挂行为停在 8~12 格，20 回合一次没出手。
2. **等魔龙够了才出击**：阈值 2 条，第 12 回合凑齐之后它才开始往前压。
3. **魔龙护主**：离王的平均距离从 5.3 收到 4.2。

**诚实说明（别把这些当结论）**

- 一个种子、20 回合，只能看**方向**，不能说明强度变了多少。
- 木桩是假对手：不会远程、不会躲、不会集火。真实难度未知。
- 位置会**来回挪 2 格**（8,11 ↔ 6,11）：游弋带 7~9 有 3 格宽、移动力 2，
  下一版要加迟滞（出了带子 2 格以上才动）。
- 阈值 `NEED_DRAGONS = 2` 是拍的，没有依据。
- "余量"用曼哈顿距离 + 兵种射程近似，没算空中层和高度差。

**踩到的两个坑**

1. 清空 `s.cities` → 该席位第一帧就判出局，整局立刻结束、一行数据都采不到。
   这是第二次踩（第一次在关卡脚本里），**记住：试局面也要给每家留一座城**。
2. 第一次用真对局 + 真实军队跑，两档逐字相同。查下来**不是机制没生效**
   （提案确实被采纳了），是规格写错："贴着射程外 1~2 格"和全局 AI 的"推进"
   落在同一个位置。换成空场 + 拉远游弋带才看出差别。

### 顺带做的：核心污染清理（第一批）

奇想包有大量内容住在核心文件里。先清**最安全的一类**：只用到 `SkillCtx` 和 `api` 的
技能实现，从 `rules.ts` 搬到 `fantasy-packs.ts`，走同一个 `registerSkillEffect` 表。

| 已搬走（6 个） | 原来在 |
|---|---|
| 投斧 `throw-axe`、再生 `regenerate`、俯冲 `dive`、切属性 `cycle`、降临 `descend`、隐匿 `vanish` | `rules.ts` 的 `SKILL_EFFECTS[...]` |

行为**零变化**：`test:rules` 956 项、AI 53+7、`probe:level`、`probe:unit-ai`、`test:replay` 全过。

**剩下的不动，因为动了要改核心的接口**（清单）：

| 位置 | 是什么 | 为什么先不动 |
|---|---|---|
| `rules.ts` 剩 6 个技能效果 | 招魂 / 圣旗 / 飞升 / 陨卵 / 裂殖 / 聚合 | 要用 `hurtUnit` / `sweepDead` / `armySize` / `freeSpotWithin`，得先给技能上下文补口子 |
| `ai.ts` `heroSkillCandidate` | 12 个 `case '效果名'`，约 200 行 | **口子已开、`dragon-egg` 已搬**（见阶段 3b）；剩 11 个照抄形状即可，新增技能一律走新口子 |
| `unit-value.ts` | 19 处扩展能力定价（`aura-armor: 0.1`…） | 核心在给扩展能力估值。要开 `registerAbilityValue`，会动 AI 的估值基线 |
| `level.ts` 邪龙关 | 8 处 fantasy 兵种 id | 这是**内容**不是规则，可以留 |

搬运的判据写在 `fantasy-packs.ts` 第三节的注释里，下次照着做就行。

## 阶段 3b：技能自带的 AI 提示（2026-11-18）

**问题**：`ai.ts` 的 `heroSkillCandidate` 里有一串 `case '效果名'`——意思是"引擎认识
每一个具体英雄技能"。每加一个技能就要回核心改一处；而扩展的技能（修真的法术）
AI 根本不认识，配上去等于没配。

**做法**：新口子 `registerSkillAi(效果id, 提示函数)`，和 `registerSkillEffect` 并排。
技能在哪个包，就由那个包声明"什么条件下值得放、值多少分"。核心先查这张表，
查不到再走旧 `case`——**搬一个少一个，不用一次改完 11 个**。

提示返回三种：`null`（不放）、数字（值几分，落点交给规则层）、`{score,x,y}`（值几分并指定落点）。

**和 `unitAi` 的分工**（写进 `skill-hooks.ts` 的注释了）：

| | unitAi | 技能提示 |
|---|---|---|
| 管多大 | 一整个兵这一回合 | 单个技能放不放 |
| 能做 | 走位、选目标、提新动作、必须做 | 只给分数（+可选落点） |
| 谁用 | 兵种写了 `aiAutonomy > 0` | 所有会技能的兵，不用开自主分 |
| 定位 | 剧本 | 常识 |

普通英雄该走"常识"这条路：给它们开自主分等于让每个兵各打各的，协同就散了。

### 本次搬了什么，怎么证明没变

只搬 `dragon-egg` 一个，分数与判定逐字照抄（30 分 / 射程内有人可砸）。

零变化证据（改动前后各跑一遍、逐字比）：

- `probe:dragon-king` 的完整输出 **diff 为空**；
- 两个种子的全 AI 对局动作指纹相同（`1769d015`/588 步、`c048213`/385 步）。

### 顺手修的一个老 bug

规则在 2026-11-10 就允许陨卵落在**空地**上了（卵本身就是两回合后的一条龙，
不只是砸那一下），但 AI 的判断一直没跟上：**射程内没敌人时它一次都不放**，
于是"隔空往阵线里插钉子"这个用法对电脑等于不存在。

现在改成：射程内没敌人 → 找**最近的空地**放一枚（15 分），落点用
`api.canStandAt(…, 'dragon-egg')` 选——和规则层挑落点是同一个判断，所以一定点得下去。
另外跳过"自己脚下"那一格：王是飞行的，规则允许地面单位叠在它身上，
但"最近的空地"不该是"我自己站的那格"。

**这一条是对局里看不出来的**：`probe:dragon-king` 那张场里敌人总在 11 格内，
新分支根本走不到（改前改后下蛋次数都是 4）。真正能看见它的是新探针
`npm run probe:skill-ai`——手搭一个"敌人在 21 格外"的局面，直接问提示，
再**真的放一次**，看盘上有没有多一枚卵。

### 新探针 `probe:skill-ai`（已接进 `npm test`）

| 段 | 验什么 |
|---|---|
| 1 | `dragon-egg` 已有提示（不再是核心里的 case） |
| 2 | 射程内有敌人 → 返回分数、不指定落点 |
| 3 | 射程内没敌人 → 返回落点；落点最近、不在自己脚下、能站下卵、**真的放得下去** |
| 4 | 边界：距离 9 仍算"有人可砸"，距离 21 走空地分支 |
| 5 | 坏掉的 api 会抛错——兜底靠核心的 try/catch，不靠提示自己容错 |

### 剩下的 11 个 case 怎么搬

`throw-axe` / `regenerate` / `dive` / `cycle` / `descend` / `vanish` / `raise-dead` /
`holy-banner` / `ascend` / `mitosis` / `fuse`，每个都是"把 `case` 里的几行挪成
一个 `registerSkillAi`"，`SkillAiCtx` 已经给了 `foes` / `hpRatio` / `allies` / `api`
（那串 case 用到的都在里面）。搬的时候**分数必须照抄**，否则 AI 行为会漂。

搬完之后 `heroSkillCandidate` 里只剩 `switch` 的空壳，那时再整体删掉。

## 阶段 4：探针、跑批、回放

### 要做

1. `probe:unit-ai` 补齐六段：零变化 / 一个兵能自己动 / 三道门 / 四条闸 / 迷雾 / 卡死保险。
2. 跑批对比：开与不开单兵 AI，各 20 局，看**回合数、胜负、崩溃率**。
3. 回放：带 boss 的一局导出回放，重放后动作序列一致。
4. 在 `docs/` 留一份"实测记录"：哪些结论有数据、样本多大、哪些只是方向。

### 诚实说明（写进报告，别省）

- 跑批衡量的是"对某个固定旧 AI 的胜率"，**不衡量"好不好玩"**。
  它只能证明"这个 boss 不会自己把自己玩死"。
- 20 局只能看方向，不能下结论。要下结论至少 100 局以上，且要固定种子。

## 明确不做（这一轮）

## 风险和回退

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 拆 50 步后 AI 行为大变，平衡被打破 | 中 | 高 | 阶段 0 先量后改，独立提交，随时 revert |
| 零变化验收做不到 | 低 | 中 | 说明新分支没早退；先修分支条件，别改验收标准 |
| profile 被写成"作弊 AI"（读真局） | 中 | 高 | 类型上就不给它真局；代码 review 只查这一条 |
| 每个包都想给自己的兵开自主 | 一定会发生 | 中 | 文档层面定死：只给关卡 boss 填值；普通兵填了要问"为什么不改全局 AI" |
| 50 步拿掉之后没人做跑批脚本迁移 | 中 | 中 | 在计划里单列一步，别指望"顺便"完成 |

## 一句话记住

**机制是通用的一次性成本，行为是每个包自己的长期成本。**
接口越窄，以后越不需要回来改核心；反过来，只要有人开始要求"改全局估值"，
就说明这个口子开歪了。
