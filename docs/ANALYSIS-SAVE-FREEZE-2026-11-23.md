# 「攒钱冻结」是哪来的：v1 → v3 考古（2026-11-23）

> 回答的问题：v3 改自 v1，v1 有自己的攒钱逻辑、v3 也有一套新的——
> 为什么会出现"为了攒钱而等死"？
>
> **一句话答案：攒钱这套机制是 v1 的，v3 一行核心没改；v3 只把它周围的
> 两个信号（"兵够了"和"该收缩"）换掉了，而换上去的那个信号恰好是"越弱越触发"。**
> 三个具体缺口在 `V3-BACKLOG` 里记为 P0-0。

## 一、先证明"是 v1 的"

`src/core/ai.ts`（v1 内核，仍在库里）和 `src/core/ai-v3.ts` 的攒钱段是**逐行对应**的：

| 部件 | ai.ts（v1） | ai-v3.ts（v3） |
|---|---|---|
| `SAVE_HORIZON = 6` | 4746 | 同 |
| `INTENT_TURNS = 8` | 4818 | 同 |
| `savingAllowance()` | 4870 | 同（连注释里"60 局 +8.6 点"的标定都一致） |
| `reviveIntent()` | 4934 | 同 |
| goals 表（rebuild/hero/era/unit/goal） | 5100+ | 同 |
| `armyGate = boom>0.45 ? 4 : 6` | 5154 | 同 |
| `abandonMode` 门槛例外 | 5192 | 同 |
| `revive` 分支 | 5427 | 同 |
| `savingFor !== null → 冻结采购` | 5982 | 同 |

所以"攒钱冻结"**不是 v3 新引入的 bug**，是 v1 时代就在的机制，被完整继承过来。

## 二、这套机制本来要解决什么（别急着删）

规则层有三笔"必须一次付清"的大钱，而采购是"手里有多少花多少"的逐候选 argmax：

- **重建废墟**：城被打空不会易主，得派兵走进去掏 `maxHp × 2.5` 的重建费；
- **升时代**：`upgradeCostOf`（Q1 上 360、Q3 上 540）；
- **英雄**：造价 + `unlockCost`。

v1 的注释把动机写得很直白：

> "实测 80 局里三成打到回合上限，一半以上是'城都砸烂了，两边谁都掏不起重建费'。
> 所以这一条不是'更聪明的经济'，是把平局变成胜局的那一步。"

**冻结是必要的**。问题不在"有冻结"，在"什么时候停止冻结"没有出口。

## 三、机制：四个部件

1. **目标排序**（`buildPlan`）：五类目标放进同一张表，用"每金战力"量级打分，取第一名 →
   `savingFor` / `targetCost` / `targetUnitId`。
2. **闸门**：只有 `!urgent && (abandonMode || army >= armyGate)` 才允许**进入**这一步。
   - `urgent = 兵 < 3 或 敌人距某城 ≤ 3 格`；
   - `armyGate = 6`，**`boom > 0.45` 时降到 4**。
3. **额度**（`savingAllowance`）：离目标只剩 `tight` 个回合的收入（era 用 8、其余 4）→
   额度 0；否则 `floor(inc / 产兵点数)`，再按"轮"交替给 0。采购里
   `price + unlockFee > allowance` → `deny('攒钱冻结')`。
   白名单只有三条：目标本身、`fastEco`（回本 ≤ 8 回合的经济兵）、0 个工匠时的工匠。
4. **记忆**：`savingFor` 写进 `aiFocus[me].save`（`goal / cost / since / seen`）；
   `INTENT_TURNS=8` 内粘住上次目标（`INTENT_MARGIN=1.3`）；整段被跳过时
   `reviveIntent` 把它接回来。

## 四、为什么会"等死"：三个缺口

### (a) 唯一的刹车只认"贴脸"——而且这是**故意**的

v1 里原本还有第二道出口 `weaker && atGate → stance='turtle'`。它被删掉时，
注释是这么写的（`ai.ts` 里还留着）：

> "以前是'只要身价落后就固守'，可 AI 一旦进入攒钱期身价必然落后，于是它自己把自己
> 锁进固守、再也不出击（第一版就是这个死循环：越攒越不敢打，越不敢打越攒不出胜势）。"

也就是说：**作者知道"攒钱 → 身价必然落后"，为了让攒钱能跑起来，主动把"落后"
从防守信号里摘掉了。** 代价是它同时也从"停攒"的信号里消失了。

于是"5 个兵 vs 11 个兵、城在掉血、敌人还在 5 格外列阵"这种局面，`urgent` 是 `false`，
`savingFor` 照旧成立。

v3 把 `turtle` 搬进计划层 `DEFEND_PLAN`（判据原样：`enemyAtGate && weaker && army>=3`），
**同一个盲点被完整继承**，而且它只改 `pullHome` 权重，一个字都不碰 `savingFor`。

### (b) `reach()` 用"立目标那一刻的收入"做线性外推，之后不再校验

```ts
const reach = (cost, horizon) => gold + inc * horizon >= cost;   // horizon = 6
```

Q1|30|A：立目标时金 121、要 360 → 反推当时 `inc ≈ 40/回合`（121+240 ≥ 360 才允许立）。
之后实际净积累只有 **22/回合**（8 个回合从 121 爬到 294，探针原样读数"立了 8 回合、还差 66"）。
**收入掉了一半，但"还差几回合"没人重算。** 代码里没有"收入下滑 → 放弃攒钱"这条出口。

### (c) 目标会抖，抖动把 `since` 清零，"过期"永远不生效

探针逐回合读数（`--each`，Q1|30|A）：

```
T35 攒=era@360(立0)      买=—
T37 攒=rebuild@203(立0)  买=lumberjack×2
T41 攒=era@360(立0)      买=—
T43 攒=unit@130(立0)     买=crossbow,ge
T45 攒=era@540(立0)      买=—
T47 攒=—                 买=5 个
```

六个回合里目标换了五次，每次都是 `(立0)`——`since` 被重置回当前回合。
原因是：闸门关闭的那一回合会 `setFocus(save: null)` 把 `prev` 清掉，
下一次再攒时 `same` 恒为 `false` → `since = 现在` → `INTENT_TURNS` 的"8 回合过期"
和"粘住上次目标"两条同时失效。

**没有出口的结果**：`savingFor` 在"era / rebuild / unit / 无"之间来回跳，
每跳一次就把攒了几个回合的钱花掉一部分（闸门一开就买），
于是账上钱在 121 ↔ 294 之间震，**14 个回合一次都没攒到 360**。

## 五、v3 相比 v1 到底改了什么（只有两处，但方向要命）

| 位置 | v1 | v3 |
|---|---|---|
| `quality`（精兵姿态的触发） | `savingFor !== null \|\| gold >= inc*1.2 \|\| **army >= CONFIG.maxUnits - 6**` | 第三项换成 **`mood.weight.boom > 0.5`**（编制上限已删） |
| `stance` | `weaker && army>=3 && atGate → 'turtle'` | 搬进 `DEFEND_PLAN`，判据相同，只改 `pullHome` |

第一行是关键。`quality = true` → `stance='elite'` → 单价惩罚从 `0.035` 降到 `0.012`
（"钱要攒着买贵的"）。

- v1 的语义：**"兵够多了（≥18），开始买贵的"** —— 一个"富了"的信号；
- v3 的语义：**"boom 权重高，开始买贵的"** —— 而 boom 恰恰在**正面打不过、
  有城守不住**时最高，是一个"弱了"的信号。

同一行代码，语义从"富了"翻成"弱了"。叠上 `armyGate` 也吃 boom：

```
兵越少 → boom 越高 → ① armyGate 6→4（更容易进入攒钱）
                   → ② quality=true（更省着花、只买贵的）
                   → 兵更少 → boom 更高 …
```

**这是一个正反馈环，v3 的改动把它闭合成环了。** 实测 Q3|31|A：

```
T45 兵10 boom=0.37   （闸门 6，还能正常造兵）
T55 兵 6 boom=0.50   （boom 过 0.45 → 闸门 4）
T67 兵 3 boom=0.73   （3 个兵也在攒钱）
```

## 六、所以"等死"不是某个 bug，是缺三个出口

| 缺的东西 | 现在的样子 | 加在哪 |
|---|---|---|
| **放弃出口**：攒了 N 回合没到 → 松手 | 只有 `INTENT_TURNS=8`，但它被抖动清零 | `goal.since` 不再被 `setFocus(save:null)` 清掉，或按"累计攒了几回合"记 |
| **重估出口**：收入掉了 → 重算"还差几回合" | `reach()` 只用立目标那一刻的 `inc` | `savingFor` 每回合复核一次 `(cost-gold)/inc`，超过阈值就降权/放弃 |
| **生死出口**：城快丢时不攒 | 只有 `urgent`（敌人 ≤3 格） | 城血/受伤害速率进 goals 打分（见 `ANALYSIS-CITY-PROFILE` P0-0） |

**已经证伪的替代方案**（别再走）：按兵力比直接关闸 →
Q1/Q2 `10-2-0 → 9-3-0 → 8-4-0`，两局胜变负，而三局负**回合数逐局一字不差**
（那个闸在病灶上零触发：AI 用造价自评，贵兵对便宜兵并不认为自己落后）。
