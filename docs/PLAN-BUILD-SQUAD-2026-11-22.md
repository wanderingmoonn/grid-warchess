# 建造编队：按编队流程组织（2026-11-22）

> ⚠️ 2026-11-23：本文的「待办 / 下一步 / 还没做」章节已并入 `docs/V3-BACKLOG.md`
> （v3 待办的唯一清单）。本文只作历史记录与设计依据，**不要再往这里加新条目**。


> 用户的设计：不要"工人保底"那种补丁，而是**模仿组织进攻编队的流程**——
> 有过河需求 → 计划层组织建造编队 → 优先收拢附近散工 → 没有就下单请求生产。
> 防抖靠"有没有正在进行的建造编队"，不做"每回合必然造一个"。

## 三步计划

| 步 | 内容 | 状态 |
|---|---|---|
| 1 | **补"编队缺口 → 生产端"通道**（进攻/建造共用） | ✅ 本次完成 |
| 2 | 建造编队：收拢附近散工（builder 进散兵池）、距离判据、"没工人就下单" | 未做 |
| 3 | 状态机：`forming → marching → building → holding → 解散`（现在只有 marching） | 未做 |

## 第 1 步：缺口通道

**原来断在哪**：`Fields.squadNeed` 从 2026-11-21 就声明了"编队缺口 >0 时采购给战斗单位
加分"，`squadShortfallOf` 也在算，但**采购里没有任何消费者**——值算出来没人读。

**现在**：

- `squadTick` 返回 `{ reports, squadNeed, builderNeed }`，写进 `focus.plan.keep`；
- `squadNeed` = 所有 `attack` 编队的 `want − 现有`；
- `builderNeed` = 有计划要修桥、建造编队却不够 2 人时，缺几个；
- 采购消费：
  - 战斗单位 `+min(24, squadNeed × 4)`；
  - 工人**只在 `aiEconCap` 开时**：`builders === 0` → +80（必须先有一个人才能修桥），
    第二个 → `min(40, builderNeed × 20)`（略高，抢不过就等）。

## 为什么工人加成要绑在 `aiEconCap` 上

实测三档：

| 加成 | 结果 |
|---|---|
| 每人 +40 | 建造编队仍只有 1 人（工人 ~108 vs 兵 ~115） |
| 每人 +60 | 编队到 2 人，但 Q2 一局胜→负（挤掉兵） |
| 第一个 +80 / 第二个 +20 | 只在 econ-cap 下启用；默认 Q1/Q2 回到 10-2-0 |

默认配置下工人本来就造得出来（Q3 有 10 段桥），全局加成只会在 12×12 上挤掉一个兵。
**唯一会让工人被挤到 0 的是 econ-cap**（经济缺口 +80 vs 工人 24），所以只有那个场景需要。

## 第 1 步实测（24×24/era4/seed30，econ-cap 开）

| | 之前 | 现在 |
|---|---|---|

仍是平——通道解决的是"没人修桥"，不是"修了桥就能赢"。

## 第 2、3 步要做什么（未做）

**第 2 步（收拢与下单）**：

- `squadTick` 的 `free` 现在只算 combat；要把 builder 放进"未编队池"，
  建造编队组建时**优先收拢附近散工**；
- 距离判据：`dist(工人, 渡口) < dist(工人, 最近自家城)` 才值得收（用户否掉了
  "工人是否已在动"这一条——零散工人本来就没任务）；
- 附近没有、或都太远 → 报 `builderNeed`（第 1 步已经能把它变成采购请求）。

**第 3 步（状态机）**：

- 给 `AiSquad.state` 加 `building` / `holding`，现在只有 `forming | marching`；
- 消费方要同步：`planSummary`、UI、`squads.jsonl`，否则面板会把施工显示成"走"。

## 已知取舍

- 建造编队现在**只有 1 人**（第二个不硬挤）：`build走1人`。
  如果第 2 步把"收拢"做出来，第二个应该来自零散工人，而不是新造。
- 进攻编队的 `squadNeed` 通道**无法单独验证**（采购本来就有钱就造兵），
  用户 2026-11-22 明确：只验证建造编队。
