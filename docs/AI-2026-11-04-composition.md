# "让产兵跟着战术走"：两版都测了，都没赢

2026-11-04 · 每臂 800 局配对 A/B · **一版显著更差，一版中性** · 两版都已回退

---

## 〇、一句话结论

"产兵和战术对不上"这个判断**方向错了**。按战术平移编队配比，800 局配对 A/B 是
**43.9%（z = −3.43）——显著更弱**；改成"只给速攻加一档攻城器"，是 **50.3%（z = 0.18）——
中性**，而且探针证明机制确实在触发（4 局里造了 27 台攻城器）。

所以：**编队模板 30 / 25 / 30 / 15 是承载胜负的结构，不是待优化的摆设**。
胜率的瓶颈不在"买什么兵"，在"什么时候往哪打"。

---

## 一、测量方法（先说清楚，否则数字没法读）

| 项 | 做法 |
|---|---|
| 对照 | `scripts/baselines/ai-8fc819d.ts`——动手前那一刻的 `src/core/ai.ts` 原样副本，只改导入路径 |
| 配对 | 一颗种子打两局（新先手 / 新后手各一次），先手优势与地图不对称互相抵消 |
| 样本 | 每臂 **800 局 = 400 颗种子 × 2**；计分 = 胜 + 平×0.5 |
| 检验 | 二项 z（平局按半分计，方差取 played/4 保守估） |
| 墙钟 | 28 片并发 ≈ 6~8 分钟/臂（36 核机器） |

顺手补了一处工具缺口：`ai-duel-batch.ts` 以前**不转发 `--policy`**，于是"AI 打人类套路"
只能串行跑（5 秒一局、200 局十七分钟）。现在转发，同一件事从"要不要测"变成"顺手测一下"。

---

## 二、第一臂：按战术平移配比（显著更差）

改法：`roleTargets(drive)` 按 drive 位移目标份额，其余四档不变——

| 战术 | 位移 |
|---|---|
| 速攻 | 前排 +6、近战 +6、支援 **−10** |
| 骚扰 | 远程 +10、前排 −6、支援 −6 |
| 弃城 | 近战 +12、远程 −8 |

**结果（时代 2，800 局）**：新 348 胜 / 旧 445 胜 / 平 7 → **43.9%（z = −3.43）**，显著更弱 6 个点。

为什么输，事后解释得很清楚：**那 15% 支援兵（牧师 / 巫医）是硬通货**。速攻砍掉支援，
军队就是在裸战；骚扰把前排份额换成火力，压不住阵线。这组数字是拿战绩喂出来的，
不是拍脑袋写的——我不该整块搬动它。

## 三、第二臂：速攻期给攻城器留一格（中性）

改法：只加一档，不动四档——`roleTargets` 里 `siege += 0.10 × drive.rush`，并把 siege 纳入模板。

理由本来很硬：破城是这套规则里**唯一**通向胜利的动作，而攻城器以前只在
"已经有单位贴到对面城下 4 格"时才 +16 分——速攻的窗口恰恰在那之前。

**结果（时代 3，800 局）**：新 400 胜 / 旧 395 胜 / 平 5 → **50.3%（z = 0.18）**。

中性 ≠ 没生效。探针（`npm run probe:composition -- --games 4 --era 3`）数出来：

```
4 局 · 造兵 288 个 · 攻城器 27 台（mortar×13、artillery×8、tank×6），出现在 4/4 局里
```

机制在跑，胜率没动。那就是"多买攻城器不是胜负手"——不是因为 AI 没买，是因为
**它买得起的时候，局面已经由别的东西决定了**。

## 四、这一轮踩的两个坑（都可复现，写下来免得再踩）

1. **时代 2 根本没有攻城单位**。唯一的臼炮是 3 代、坦克/火炮是 5 代。
   第一轮 era2 的 800 局跑的是一个不可能触发的机制——跑完只会得到 ~50%，
   然后被误读成"这个机制没用"。**动手之前先查"它在这个时代能不能出现"**。
2. **探针漏了 `END_TURN`**。`aiNextAction(s, budget)` 在一回合预算用尽时返回 null，
   调用方必须补一个结束回合——少了它，每局只走两步，"造兵 1"被当成正常结果。
   结构要照抄 `ai-duel.ts` 的 `playOne`，不要另写一套。

## 五、那把"人类打法脚本"的尺子也废了

```
200 局（时代 2）：脚本 36 胜 / AI 141 胜 / 平 23 → 脚本胜率 23.8%（z = −7.42）
```

2026-11-02 它还跟 AI 打平（45%），现在只剩 23.8%。**拿它当尺子会被天花板吃掉**——
AI 已经把它按在地上打，之后的改进在这个尺子上几乎不动。所以：

- 强度：只能用**冻结对照 + 配对种子**（本文用的就是这条）；
- 诊断：得用真实人机对局（见第六节）。

## 六、真实对局数据能做什么、不能做什么

翻了上报结构（`src/core/report.ts`、`sql/warchess_reports.sql`），先列硬事实：

- `warchess_reports.payload` 里有：seed、棋盘地形分布、时代、人数、扩展、AI 配置与坐席、
  行动数、胜负、双方终局编制 / 城数 / 金币 / 血量，以及可选的 `timeline`
  （每席**造了什么兵、死了什么兵、打出多少伤害、挨了多少**）；
- **没有动作序列**。所以"让新 AI 重打一遍人类那局"做不到——人类那一步是针对
  *旧 AI 上一步* 选的，AI 一变，局面分叉，后面记录的动作直接非法。
- 结论：真实数据**算不出胜率**，但能回答"AI 输的局里它造了什么、死的是什么"。

工具已就位：`scripts/audit-human-games.ts`（吃 JSON 数组 / Supabase 行 / NDJSON），
按"AI 赢 / AI 输"分组输出每局造兵、阵亡、伤害交换比、终局编制。

**卡在读权限**：`warchess_reports` 只给 anon 发了 INSERT，读策略在 SQL 里是注释掉的
（设计如此：谁都能交一份，没人能顺着表把别人的拉走）。要分析得用管理员连接导：

```sql
select payload from public.warchess_reports
where (payload->>'version')::int >= 2
order by created_at desc;
```

## 七、下一步该动哪里（不是继续调权重）

两条独立证据指向同一个结论：

1. 2026-11-02 的五条结构性改动：46.0%（n=200）；
2. `ladder` 量过"高级 → 中级（多一整套战术层）"= **+0 点**；
3. 本轮的配比平移：43.9%，加档：50.3%。

**决策层已经饱和**：再往采购打分里塞几个权重，动不了胜负。真正没做的是
"三回合以上的计划"——抢时代、控节奏、选战场。那是搜索，不是启发式。

要动就得接受三件事：状态克隆的开销、确定性（不能碰 `Math.random`）、
以及"必须先量再信"的节奏（每臂 800 局 8 分钟）。
