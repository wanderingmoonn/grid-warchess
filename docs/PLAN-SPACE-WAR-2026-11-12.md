# 太空战争 · 实施计划

2026-11-12 · 草案 v1（待确认后开工）

---

## 一、定位

「太空时代」现在是一个自洽的小包：造井 → 加注 → 发射 → 落月 → 展开基地 → 采样 3 回合取胜。
「太空战争」**不改写它**，只在它上面长出星图层：

> 地球和月球不再是"两张碰巧存在的图"，而是星图上的两个节点，中间连着航道。

这样才谈得上空间站（挂在节点/航道上的东西）、航道选择（走哪条路）、以及"登月不再是终点"。

---

## 二、四个已定决定

| # | 决定 | 影响 |
|---|---|---|
| 1 | **空间站 = 一张小棋盘**（`kind: 'station'`） | 站内驻军/建造/战斗全部复用现成规则；代价是每站一张图 |
| 2 | **航道只计时，不能打** | 在途单位不进战斗；反制仍在地面（拆井、杀等舱的人） |
| 3 | **胜利 = 月面基地累计采样** | 摘掉"3 回合即胜"，改成累计满 N；**会反转 11-11 的"挨打清零"**（见第五节） |
| 4 | **空间站来自"核心舱"**，不同型号初始化出不同大小的棋盘 | 发射井的货舱从"送兵"扩展成"送什么都可以"；站的大小由货物决定，不由代码写死 |

第 4 条是关键补充：它让"空间站"变成一条**数据驱动**的链路，而不是又一段写死的流程。

## 三、领域模型

### 3.1 星图：节点 ≠ 棋盘

```ts
type StarNodeId = string;                      // 'earth' | 'moon' | 'orbit-1' ...

interface StarNode {
  id: StarNodeId;
  kind: 'planet' | 'moon' | 'orbit';           // orbit = 没有棋盘的轨道槽位
  board?: BoardId;                             // 有棋盘的节点才填（地球='earth'、月球='moon'、空间站=生成时给的 id）
  name: string;
}

interface StarLane {
  id: string;
  a: StarNodeId;
  b: StarNodeId;
  turns: number;                               // 走完要几个回合
}
// 没有"封锁"、没有平行航道：一条边 = 相连（见 P1 的决定）

interface Starmap {
  nodes: StarNode[];
  lanes: StarLane[];
  stations: Array<{ board: BoardId; at: StarNodeId; owner: PlayerId; core: string }>;
}
```

**为什么要分"节点"和"棋盘"**：轨道槽位是位置但没有格子（核心舱没到之前它什么都不是）；空间站有格子但它"停"在某个槽位上。把这两件事混成一张表，就再也表达不了"站从 A 槽移到 B 槽、站内坐标不动"。

### 3.2 在途

```ts
interface Transit {
  id: string;
  owner: PlayerId;
  lane: string;
  from: StarNodeId;
  to: StarNodeId;
  left: number;                                // 还剩几个回合
  cargo: Unit[];                               // 在途单位（**已移出 s.units**）
}
```

三条约定：

- 在途单位**不在 `s.units` 里**：不会被回合重置、不会被迷雾裁、不会在两张图上同时出现。复用现成的货舱语义。
- 到达时按**目的图**算落点（现在写死在 `moonLandingTile`，要抽成通用的 `landingSpotOn(s, board)`）。
- 发射与到达都发**公开**战报，`left` 对双方可见（和加注进度同一条口径）。

### 3.3 核心舱 → 空间站

```ts
CORES: Record<string, { name: string; size: number; cost: number; slots?: string[] }>
```

链路：

```
工程队造发射井 → 装核心舱 → 选航道 → 加注 → 点火
  → 进入 transit（在途 N 回合）
  → 到达轨道槽位 → 展开成 station board（尺寸 = core.size）→ 注册进 starmap.stations
```

站生成后 `Board` 里就是普通的格子：站内建造、驻军、开火全部走现有规则，一行都不用新写。

## 四、阶段

### P0 · 地基（✅ 2026-11-12 完成）

| # | 做什么 | 验收 |
|---|---|---|
| 1 | `starmap` / `transit` 进 `GameState`（专用可选字段，和 `pendingEgg` 一个风格） | 存档、回放、联机快照天然带上，不需要兼容层 |
| 2 | 通用投送：`enterLane` / `tickTransit` / `arrive` | 地球 → 月球 1 回合到达 |
| 3 | 发射井改走航道：代码里不再出现 `MOON_BOARD` | 把目的地换成一张手搓的 `test-b`，照样能送到 |
| 4 | 通用落点 `landingSpotOn(s, board)` 取代 `moonLandingTile` | 任意图都能算落点（中心最近空地） |
| 5 | `boardViews` 染色按图（`main.ts` 的 `state.w` 与 `onlyVisibleCells` 的 `idx`） | 月球上染的色不出现在地球格子上 |
| 6 | `LOAD` / `UNLOAD` 按图 | 月面/站内也能装卸 |

**落地时的一处行为变化**：以前"点火即到达"（加注 3 回合 → 立刻落地），现在点火后还要飞
`MOON_LANE_TURNS = 1` 个回合，总时长 3 → 4。这一回合就是航道上"能被看见、能被等"的那一段，
是后面多航道与拦截的基础，不是副作用。

**明确不做**：多航道选择、星图 UI、空间站、胜利条件。P0 结束时玩家的操作和现在完全一样。

**落地位置**

| 文件 | 内容 |
|---|---|
| `core/types.ts` | `Starmap` / `Transit` 类型 + `state.starmap` / `state.transit` |
| `core/space/starmap.ts` | 节点与航道的查询；`starmapOf` 会给老存档自补一张星图 |
| `core/space/transit.ts` | `enterLane` / `tickTransit` / `arrive` / `landingSpotOn` |
| `core/board.ts::tileOn` | 按图取一格。放这里是为了避开 `rules` ↔ 扩展 的循环依赖 |
| `core/space/silo.ts` | `launchIntoLane`：只知道"我在哪个节点、这儿有哪些航道" |
| 顶栏 | `<方> 火箭 <n>`，公开；和加注进度同一口径 |

一个坑记下来：`nodeById`（节点 id）和 `nodeOfBoard`（棋盘 id）差一层，发射时传错会得到
"航道那一头还没有能落脚的地方"——两个名字太像，以后加接口时注意。

### P1 · 星图面板（✅ 2026-11-12 完成）

**航道不做封锁、不做平行**（2026-11-12 更正）：太空里可以向任何方向飞，
航道只是"两个节点之间有路"的抽象——一条边就够了，既没有"走哪条"，
也没有"封哪条"。所以 P1 的内容不是多航道，而是**把星图显示出来**。

| # | 做什么 | 验收 |
|---|---|---|
| 1 | 数据层删掉 `StarLane.blocked`，`lanesFrom` 不再过滤 | 航道只有"相连 + 航程"两个属性 |
| 2 | 地图列表从**左下角搬到左上角** | 不再和缩放条、底栏挤在一个角 |
| 3 | 星图并进这块面板：节点、相连（`地球 ⇄ 月球 · 1 回合`）、在途（`红方 → 月球 · 1`） | 一眼看到"我在哪、连着谁、路上有什么" |
| 4 | 只有一张图时**整块隐藏**（内联 `display:none` + DOM 清空） | 单图局玩家看不到任何星图信息，不信息过载 |
| 5 | 取数抽成 `ui/star-panel.ts::starRows`（纯函数） | 节点名/在途倒计时能被测试直接验 |

**为什么要用内联 `display:none`**：上一版只加了 `.board-list.single` 这个类，
玩家反馈"还是看得见"——类样式会被 `display:flex` 或别处的覆盖层吃掉，
内联样式没有这个问题（CSS 那条留作兜底）。教训：**藏东西要藏两遍**。

**不做**：在途战斗（决定 2）、单条航道内的路线选择（不存在）。

### P1.5 · 星图视图（✅ 2026-11-12 完成）

把星图画成"一张特殊的棋盘"：节点占格、连线是航线，点星球看信息、点航线看航程。

**关键决定：星图不是 `boards` 里的一张图。**

| 如果塞进 boards | 后果 |
|---|---|
| `boardIds()` 多一项 | 地图面板把星图列进去，星图里又列星图（自指） |
| 被当成战场 | 视野、待命统计、AI 寻路都会扫它一遍（零单位零地形） |
| `boardStateOf` 投影出空图 | 任何按图取格的代码都会拿到空 tile |
| 发射井找错节点 | `lanesFrom(nodeOf(silo))` 会认为"我站在星图上" |

所以它是一个**只借表现、不借数据管线**的 UI 视图：用 CSS grid 画格子、
用 SVG 画航线、用 `data-act` 接点击。规则层完全不知道它存在。

| # | 做什么 | 落点 |
|---|---|---|
| 1 | 布局纯函数：地球居中、其余节点沿外圈均分 | `ui/star-layout.ts`（坐标算出来，不进存档） |
| 2 | 覆盖层 + 节点格 + 连线 + 待命/敌人/在途/站数角标 | `ui/star-map.ts` |
| 3 | 点节点/航线 → 侧栏卡；星球与停泊的站各有「前往」 | `main.ts::starPanelInfo` + `ui/panel.ts` |
| 4 | 入口在左上角面板里；Esc / 关闭退出；切图时自动收起 | `main.ts` |
| 5 | 复盘里也能看（`star-*` 不改这一局） | 同上 |

**没做**：在途动画、航线的封锁（不存在）、星图上的单位/战斗（永远不会有——它是元视图）。

踩到的两个点：
- **连线点不中**：2px 的线没有命中面积，所以每条线配一根透明粗线（`stroke-width: 0.34`）专门接点击。
- **`hidden` 会被类选择器压住**：`.star-map { display:flex }` 会让 `[hidden]` 失效，
  所以写成 `.star-map:not([hidden]) { display:flex }`。和左上角面板那次是同一个教训。

### P2 · 空间站（2026-11-12 细化，待开工）

#### 先补的地基：投送要能去"轨道"

P0 的 `enterLane` 要求**目的地有棋盘**。核心舱要去的偏偏是轨道——棋盘正是它到了才生成的。
所以 P2 第一件事是把投送拆成两种目的地：

| 目的地 | 行为 |
|---|---|
| `surface` | 落到某张图上按落点放人（现状） |
| `orbit` | 到达**星球节点的轨道** → 生成 station 棋盘 → 中心放下核心舱 |

#### 核心舱 → 空间站

| | |
|---|---|
| 发射 | **不加注**，选型号 + 扣资源 → 直接进航道 |
| 位置 | 挂在星球节点（`starmap.stations[].at = 'earth'`），一个节点可停多座 |
| 站位 | 生成一张 `kind: 'station'` 的 board，中心 1 格是核心舱，其余全是 `void` |
| 尺寸 | 由核心舱型号决定：5×5 / 7×7 / 9×9 |

#### 两个新地形

| 地形 | 通行 | 用途 |
|---|---|---|
| `void` | 不可通行、不可建造、无掩护 | 还没铺出来的虚空 |
| `deck` | 1 步、无掩护 | 已铺好的甲板，站内唯一能站人的地方 |

为什么地板必须是新地形而不是复用 `plain`：`buildOn: ['plain']` 的建筑（比如发射井）
会在站内被判定为"可以盖"——一个建在空间站上的火箭发射井，听着就像 bug。
新地形让这两件事在数据上就不可能混淆。

加两个地形要补 5~6 张表（`terrainCost` / `terrainName` / `TERRAIN_INFO` / 高度 / 视野），
编译器会逐一点名，不是隐蔽的坑。

#### 扩建：选点，一格一格铺

**做成核心舱的一门技能**（建筑挂技能已有先例：月球基地的「月壤采样」）：

```
SkillDef{ id:'station-expand', targeting:'point', multiCast:true }
  SKILL_TARGET_CELLS = 站内所有"与已有甲板/核心舱相邻的 void"
  effect: 扣资源 → 那一格 terrain = 'deck'
```

- 一次一格，可以连着铺（`multiCast`），**不需要运输、不需要工程队**
- 价格 = 每格额定 × (1 − 折扣)
- 可点格只给"相邻于已有结构"的虚空：空间站必须一圈一圈长，不能凭空在角落铺一块

#### 太空建设折扣：一条渐近曲线

`rate(n) = 0.5 − 0.8^n`（n = 火箭井的**等效数量**，不同类型给不同权重，求和）

| 井数 | 折扣 | 实际成本 |
|---|---|---|
| 0 | −50% | 额定 × 1.50 |
| 1 | −30% | × 1.30 |
| 2 | −14% | × 1.14 |
| 3 | −1.2% | × 1.01 |
| 4 | +9% | × 0.91 |
| 6 | +24% | × 0.76 |
| 10 | +39% | × 0.61 |
| 20 | +48.8% | × 0.51 |

- **每多一座井的收益递减**（第一座 +20 个点，第二座 +16，第三座 +12.8…）
- **不封顶，软上限 +50%**：永远不会到 50%，所以"再盖一座井"永远有一点点回报，
  只是越来越小——这正好是想要的激励形状
- 未来不同井型给不同权重（重型井 1.5 座），**代入同一个 n**，公式不用改

#### 生产舱（P2a 的验证舱段）

- 站内建筑，每回合给一点资源（数值待调）
- 建造同样走核心舱的技能（选点，落在空的 `deck` 上），同样享受折扣
- 它存在的意义：证明"在站上花资源造东西"这条链是通的，
  顺便给空间站一个"为什么要建"的答案

#### 两个会冒出来的副作用，先定掉

1. **面板列表会变长**：每座空间站都是一张 board，会进 `boardIds()`。一局三座站，
   左上角面板就从 2 项变成 5 项。
   → **面板列表只列 `kind !== 'station'` 的图**；站通过星图或侧栏的「前往」进。
   星图本来就是为这个做的，别让两个入口互相重复。

2. **站内不要迷雾**：空间站是自己的，虚空只是"还没铺"，不该像未探明地形那样黑着。
   → `boardKindOf === 'station'` 时把可见格视为全图（渲染与面板都不裁）。

##### 包拆分（2026-11-12 修正）

一开始把空间站直接写进了「太空时代」，结果基础包里混进了星图、空间站、折扣——
一个只想要"简单登月"的玩家也得吃下整套轨道玩法。现在拆成两个包：

| 包 | 内容 | 依赖 |
|---|---|---|
| **太空时代**（`space-age`） | 月球图、火箭发射井、月面基地、月壤采样、**星图数据与航道投送** | — |
| **太空战争**（`space-war`） | 核心舱、空间站棋盘、扩建与舱段、太空建设折扣、星图视图入口 | `requires: ['space-age']` |

分界线为什么画在"星图数据留在基础包"：发射到月球本身就要走航道，
那是**发射的一部分**；而星图**视图**、空间站、折扣是额外的玩法层。
所以基础包有 `starmap`/`transit`，但没有星图入口、没有核心舱。

`requires` 由 `enabledExpansionIds` 跑到不动点过滤：只勾战争包时整包不进场
（兵种表里也不会有核心舱），这条有测试钉着。

**面板入口**按扩展 id 判断（`hasSpaceWar()`），不是按"有没有星图"——
基础包也有星图数据，按数据判断会把入口漏给基础包。

### P2b · 推进器与太阳能（✅ 2026-11-12，当日修正一次）

| | 数值 | 说明 |
|---|---|---|
| 核心舱自带电 | 10 | 新站至少能带一座生产舱，不至于开局就断电 |
| 太阳能舱 | +12 电，240 金 | 自己不用电，电再紧也能造（否则死锁） |
| 推进器舱 | −15 电，420 金 | 必须装在核心舱**下半区**；至少一台才能启航 |
| 生产舱 | −4 电，320 金 | P2a 时不耗电，现在纳入同一本账 |

**能量是每座站各自的账**，不是一方共用（两座站隔着几万公里，不可能互相供电）。
面板复用装配坞那套 `.power-line` 横条，只换颜色。**过载 = 整站停摆**：
推进器不提速（航速退回 1）、生产舱不产金。

#### 推进器 = 让站变成飞船（2026-11-12 修正）

第一版把推进器做成了"给火箭提速"，方向错了。**火箭弹道是固定的**：
一次性投送，谁发、有没有推进器都是 1 回合到。

推进器真正的用途是**空间站自己开走**：装了推进器，这座站就是飞船，可以沿航道
去别的星球轨道。转移的实现就是改一个字段——`starmap.stations[i].at`，
站内棋盘、甲板、单位坐标一格不动。

| 推进器 | 航速 | 地月航道（距离 6） |
|---|---|---|
| 0 台 | 1 | 不能启航 |
| 1 台 | 2 | 3 回合 |
| 2 台 | 3 | 2 回合 |
| 5 台 | 6 | 1 回合 |

交互不是技能（技能是"选棋盘格"），而是核心舱的**单位动作**：
每个相邻节点一个「启航 → 目的地」按钮，标注航程与航速。
飞行期间 `travel = { lane, from, to, left }`，站还在出发地（星图上带 ⇢ 标记），
到港才改 `at`。

**为什么两套时间**：`StarLane.turns` 是火箭航程（固定），`StarLane.distance` 是
太空距离（给站算 `距离 ÷ 航速`）。共用一个字段就只能二选一：要么火箭慢到能
体现推进器（发射流程被拖长），要么推进器永远看不出效果。

#### 顺带修的界面

- **左上角面板压在指挥官条上**：`top` 从写死的 54px 改成 `var(--chrome)`，
  值由 `fitBoard()` 写（它就是算棋盘可用高度时用的那个数）。上帝模式 / AI 观战
  会多出一条指挥官条，以前列表正好压在上面。
- **上帝模式里星图卡被兵种货架顶掉**：货架占满侧栏，点星球只能看到一堆兵种，
  找不到自己的空间站。现在星图打开时侧栏让给星图卡（指挥官条保留），
  关掉星图再重画货架。

### P2d · 航天员与恶劣外空环境（✅ 2026-11-12 完成）

#### 一、火箭先选目的地，再开始加注（A）

`launchIntoLane` 以前直接取 `lanesFrom(node)[0]`——只有月球一条路时这不是问题。
现在多了"投送到自己的空间站"，而**加注回合数跟目的地走**：

| 目的地 | 加注 | 航道 | 合计 |
|---|---|---|---|
| 月球表面 | 3 回合 | 1 回合 | 4 回合 |
| 自己的空间站（同节点） | **1 回合** | 不走航道 | **1 回合** |
| 自己的空间站（异节点） | 1 回合 | 1 回合 | 2 回合 |

- 发射井的 `custom.dest = { node, board?, fuel }`；**改目的地会清空燃料**
  （否则可以先按站加注 1 回合再改月球，白赚两回合）
- `SILO_FUEL_TURNS` 仍是"去月球"的常量；去站用 `SILO_FUEL_TO_STATION = 1`
- 老存档没有 `dest`：`currentDest()` 按"第一条航道 + 月球燃料"兜底，行为不变
- `Transit.board`：投送到某座站时，`arrive` 的落点从"节点的棋盘"改成"这张棋盘"
- **同节点投送不走航道**（地球和地球之间没有航道），点火即到；
  和航道到达共用 `landCargoOn()`，落地规则只有一份

#### 二、恶劣外空环境（B）

```ts
export interface HazardSpec {
  id: string; name: string;
  armorDiv?: number;   // 护甲 ÷N（无保底）
  moveMul?: number;    // 移动 ×N
  moveMin?: number;    // 乘完的保底
}
export interface Board { ... hazard?: HazardSpec }
```

挂 `Board` 而不是地形表：它和"站在哪一格"无关。月球与空间站棋盘创建时都带上
`SPACE_HAZARD`（护甲 ÷5、移动 ×0.5 保底 1）。

**三处接入（都在 `rules.ts`）**：

| 位置 | 做什么 |
|---|---|
| `movePower()` | 扩展钩子之后、石化之前 `max(moveMin, floor(move × mul))` |
| `effectiveStats()` 护甲 | 所有加成之后 `floor(armor / div)` |
| `computeDamage()` 的 `ctx.armor` | 同上，破甲**之前** |

为什么要"环境先、状态后"：环境是"这张图让所有人变慢"，石化是"这个单位自己变慢"。
反过来会让同一支兵在两张图上算出不同结果，玩家没法用"我在月球上就是慢一半"解释。

**无保底**是有意的：12 甲的月球基地只剩 2，4 甲的舱段直接归零。

`core/hazard.ts` 提供 `hazardOn` / `hazardFor` / `registerHazardExempt`（**列表**，
不是单槽——两个包各注册一条，单槽会互相覆盖）。

#### 三、维生仓（C）

- 兵种 `station-life-support`：耗电 8、额定价 360、护甲 3
- **覆盖半径 3**（曼哈顿距离）：半径而不是全站，否则它就是一笔必交的税
- 豁免**读时算**，不写回 `board.hazard`：写回去的话，维生仓被打掉 / 站被拆 /

## 五、采样口径（已定）

11-11 落的是「**基地挨打 → 采样进度清零**」，理由是民兵 13 攻打 12 甲 = 1 点/回合，不清零的话反制在数学上不成立。

P3 的"累计采样"会把它换成「**挨打 → 这一回合不 +1（暂停），进度保留**」，基地被拆才归零。
**这条已经确认**，两件事各归各位：

| | 挨打（骚扰） | 被拆（摧毁） |
|---|---|---|
| 后果 | 那一个回合不 +1，进度保留 | 进度归零，重新登月 |

这样"贴脸打"是拖慢而不是永久锁死（累计版本里永久锁死等于永远采不完），
"打死基地"仍然是最彻底的反制。

## 六、风险

1. **每座站一张图，`playerView` 每帧 `structuredClone` 整个 state**。站尺寸要小（5×5 ~ 7×7），站多了要注意帧率；必要时给站图做惰性克隆。
2. ~~**地图列表会变长**~~ → P1 已处理：面板搬到左上角、并进星图；图多时菜单自带滚动。
3. **所有变更必须走 action**（核心舱展开、站点转移、航道封锁）。UI 层直接改字段会让回放和联机不同步——这正是"直接改字段"最容易踩的坑：**字段可以改，但要在 action 的 handler 里改。**
4. **AI 仍然不懂多图**（`ai.ts` 零引用）。太空线在单机里对 AI 单向开放，这个已知短板写在规则书里，不假装不存在。
5. **残留的地球假设**：`heat` 只有一维（继续跳过）、迷雾染色的 `onlyVisibleCells`（P0 修）。
