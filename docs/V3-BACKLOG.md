## 二、P0：当前真正卡胜负的

### P0-0 攒钱冻结：钱攒不到目标，兵也只零星买

**证据**：`npm run probe:collapse`（新探针，读 `aiRecruitTrace` + `aiFocus.save`）。

```
Q3|31|A  T24→T76 一直挂着 era@c1/c2 要 540，账上 195→381→194→382 来回震，一次都没攒到
Q1|30|A  era@c2 要 360，121→218→294（"立了 8 回合"，还差 66），攒够前被打死
Q1|31|B  T16：6 兵/420 值 vs 3 兵/150 值，账上 466 金一个兵不买
```

**机制**：`buildPlan` 的 `army >= armyGate`（6，boom>0.45 时降到 4）是绝对人头；
`savingAllowance` 每回合仍放行 `inc / 产兵点数` 的额度；`reach(cost, 6)` 只问
"6 回合内收入够不够"，不问"6 回合后城还在不在"。

**已证伪的修法**：按兵力比关闸（`outmatched = foeVal ≥ myVal×1.2/1.25`，
含"复活上次目标"那条路）→ Q1/Q2 **10-2-0 → 9-3-0 → 8-4-0**，两局胜变负，
而**三局负回合数逐局一字不差**（说明那个闸在它们里面零触发：AI 自己并不认为落后）。
已回退。

**剩下的路**：给攒钱目标的评分乘"存活折现"（`ANALYSIS-CITY-PROFILE` 第四节 P0-0）。
判据要换（按城血/受伤害速率，不按兵力比），单独立一批跑。

### P0-4 没有城画像（2026-11-23 新）

  `royalComboBonus` 的"国王 4 格内"）；`camp` 有 +6，城市没有 → 同兵种在各城分数
  **逐位相同** → 落进 `tied` 按 `aiNoise` 抽 = **在城之间均匀随机**。

### P0-1 开局被速推 —— 三局负全在 78~84 回合

```
Q1|30|新A  负 78 回合     Q1|31|新B  负 79 回合     Q3|31|新A  负 84 回合
```

**已量（2026-11-23）**：崩盘形状不是"后期打不动"，是**中期兵力领先 → 攒钱 → 被追平 →
继续攒钱 → 城被打空**（见 P0-0）。原来的猜测"威胁没参与 `horizon`/`econUntil`"**不成立**：
`econUntil` 一直很保守（horizon=4），钱不是投进经济了，是**躺在账上**。

**现象**：不是拖到后期打不动，而是中期被一波打死。同一形状在
`AUDIT-SOLVERS` 里记过一次（"48 回合崩：敌人大军压境还在发展"）。

**机制上的猜测（未验证）**：威胁没有参与 `horizon` / `econUntil`。
现在是"先按固定窗口发展经济 → 威胁到了再转兵"，转的时候已经晚了。

**下一步**：已量完（2026-11-23），见上面 P0-0——真因是攒钱冻结，不是 `horizon`。
P0-1 在 P0-0 之后重新量一次，别提前归因。

**注意**：`EXPERIMENT-4WAY` 试过"威胁 → 压经济"，**both = cap 逐局完全相同**，
原因是"econ-cap 前 10 回合就把经济铺开了，压住的是后续投资，不是已经铺出去的单位"。
所以这次要么在**开局**就算威胁，要么做**回收**（卖/拆经济换兵），不能重复那条路。

### P0-2 没有进攻配额（PLAN 39/40 节）

- **要做的**：战略层给总配额（按目标守军 / 我方兵力），组建编队时消耗配额。
- **依赖**：与 `postureBudget` 的关系要先理清。

### P0-3 钱变不成兵（产兵格是瓶颈）

- **证据**：`aiEconCap` 能让经济单位铺到 40 个、终局剩 7.5 万金，**胜负不变**。
- **`aiEconPlan`（残值 R=4）**：9-3-0 vs 基线 10-2-0，差在 Q2；可试 R=3 或边际递减。
- **要做的**：查 `productionCapacity` 曲线、产兵建筑数量、产兵格被占比例；

## 三、P1：结构缺口

### P1-1 进攻编队没有伤亡回收（零风险，建议先做）

- **现状**：`note:'attrition'`（`lost ≥ 2`）只用于**上报**，编队照样留着；
  成员死光了只要 `count > 0` 就继续挂着。
- **证据**：`Q4|31|A` 的 `atk-3-55`：兵 7→5、**停 63 回合**一直没解散；
  `atk-4-83` 停 48、`atk-8-149` 停 55，编队数从 1 涨到 8，全卡在离目标 5~12 格。
- **要做的（按保守到激进）**：
  1. 成员全死（`count === 0`）→ 立刻丢弃（纯正确性问题，零风险）；
  2. `count < 3` 且 `lost ≥ 2` → 丢弃重组；
  3. `stalled ≥ 20` → 丢弃并回冷却。
- **风险**：编队成型要 10 回合，淘汰太快会更弱。第 2、3 条各自跑批。

### P1-2 编队没有"撤退"指令（PLAN 39）

- 只有"全灭 / 伤亡过重"被动解散，被反推时不会主动脱离。
- 与"建造编队待机 3 回合解散"是同一类需求，可共用一个 `retreat` 出口。

### P1-3 升级选城（已落地，默认关 `aiHub`）

**病根**：升级判据是"时代最高的那座城"（`buildPlan` 的 `mainCity` + `upgradeCandidate`
的 `city.era >= myEra ? +18 : -10`），是个自我加强的循环——谁先升级谁永远是最高代，
于是升级永远投给**已经领先的那座**（通常是后方城），前线的城停低一代。
而 `eraWindowOk` 让低代城造不出当代兵，**"兵从后方来"的真因就是它**（不是采购选址）。

**已实现**：`hubCityOf`（离 `needCityId` 最近、slots ≥ 1、heat < 0.75、粘住上次的 era 目标），
三个接入点（攒时代的钱攒给谁 / 集中升一座 / `savingFor==='era'` 的闸门）。
开关 `aiHub`（`bench:ai --hub`、`export-bench-replay --hub`）。关着时逐局与基线一致。

**三版实测都净负**（详见 `ANALYSIS-UPGRADE-HUB-2026-11-23.md`）：

| 变体 | Q1/Q2 | Q3/Q4 |
|---|---|---|
| 枢纽城（v1） | 9-3-0（1↑2↓，Q1 单组 5-1） | **5-2-5（0↑6↓）** |
| 只加分不换枢纽（v2） | — | 7-1-4（0↑4↓） |
| 只扣分（v3） | — | 8-1-3（0↑3↓） |

**关键副产品**：大图上同一批对局滑进 261 回合平局，**终局 29~41 个兵也打不完**
（Q4|30|A 41 兵 / Q3|30|A 29 兵）。→ 瓶颈已经从"产不出兵"移到"收尾"，
所以下一步该做 **P0-2 进攻配额** / **P2-3 `commit` 门槛**，不是继续调升级。

### P1-4 建造编队第 2/3 步

- **第 2 步（收拢与下单）**：`squadTick` 的 `free` 只算 combat，要把 builder 放进未编队池；

## 四、P2：地图与战术

### P0-5 抢废墟不看有没有敌人（2026-11-23 新）

**链路**（`scoreMoveInner` + `buildPlan`）：
① 对**地图上每一座废墟**给"每近一格 +35"的坡度（普通推进只有 9）；
② 踩进废墟那一步 **+220**（比击杀 120+造价×0.12 还高，仅次于破城 260）；
③ 附近有"一步能踩到"的废墟就挂 `savingFor='rebuild'`，冻结采购攒 248~300 金；
④ `doMove` 结算：扣 `maxHp×2.5`、易手、城血只给 `captureHpRatio`。
**四步里没有一步检查"附近有没有敌人"**。

**实测**（`npm run diag:replay`）：Q4\|32\|A 同一座城接管 **22 次、5924 金**，
其中 7 次踩进去时 4 格内有 8~10 个敌兵；Q3\|32\|A 17 次、4490 金。

**已修（2026-11-23，`aiRuinSafe` 默认关）**：三处都要求"抢下来守得住"，
判据是 `enemyThreatAt(废墟格).n === 0`（敌人的移动力 + 射程，和"城下有人"同一把尺子，
不新拍数字）：① 朝向废墟的坡度 ② 踩进去的接管分 ③ 攒重建费。
另外接管分和坡度按 `1/(1+接管次数)` 折，次数用 `capturedTurn` 数
（**不能用归属变没变**——废墟被打空不改归属，同一方能反复接管自己那座城）。

**实测**：Q4\|32\|A 从 22 次 / 5924 金 → **4 次 / 1096 金**，261 平 → **87 回合胜**（= 基线）。

| 组 | Q1/Q2 | Q3/Q4 |
|---|---|---|
| 基线 | 10-2-0 | 11-1-0 |
| 只开废墟闸 | 10-2-0（**0↑0↓**） | 11-1-0（**0↑0↓**） |
| 三件套 | 11-1-0 | 4-3-5 |
| 三件套 + 废墟闸 | 11-1-0 | 4-1-7 |

**注意**：它对**基线是 no-op**——基线本来就不抢废墟，这个病要等三件套把兵推到城下才出现。
叠在三件套上是 **2↑0↓**（两局"负"→"平"），但没把任何"平"变成"胜"。
详见 `ANALYSIS-RUIN-SAFE-2026-11-23.md`。

### P0-6 `canReachEnemyByLand` 判据太粗（2026-11-23 查清）

**判据**：从城格做等步数 BFS（`passable` 为准，**浅流/沼泽算陆地**），超过 `min(w,h)` 判"过不去"。
下游有三处吃它，三处一起生病：

1. **宽浅流被当渡口**：20 格宽的浅流按"1 格 1 步"记，很容易越过 24 → 判不通 → 在浅流上修桥；
2. **池塘造船**：`seaDemandNow` 里 `!canReach → 1`（全额海军需求），不管这片水通向哪；
3. **决战判决误判**：`marchTurns` 由 `min(旱路, 涉水价)` 得出，没桥 40 回合、有桥 3 回合，
   判决在每个动作之间跳（实测同一回合 157→12→156）。

**试过了，净负（2026-11-23）**：开关 `aiReachCost` 默认关。两种实现（水按 14 计入 / 水仍是墙）
结果一样：Q1/Q2 **0↑0↓**、Q3/Q4 **0↑3↓**（三局胜→平）。
原因：那道 `min(w,h)` 步上限本身在编码一个真实偏好——"绕 24 步以上不如修桥"；
换成"直线的 3 倍"等于允许绕 60 步，AI 就真的去绕、去种田，兵涨到 126 个也打不完
（Q4\|30\|A 终局 126 兵 / 4848 金 / 桥 10 座 / 陆路已通 / 261 平）。

**浅流那条**仍然要治，但**不能用标准队列验**——四条队列里没有宽浅流的地图，
改判据只会改动无关的图。做法：先造一张"中间 8~10 格宽浅流"的图，只在那张图上比三种判据。
详见 `ANALYSIS-REACH-COST-2026-11-23.md`。

### P0-7 海军需求不看"这片水是不是死水"

`seaDemandNow` 只看 `waterShare` 和 `canReach`，**从不检查这片水通不通向敌城**。
封死的池塘（我的城挨着、水只有几格）只要占全图 ≥8%、陆路又判不通，就会全额造船
（运输船每艘 +40）。要做的：从挨着我方城的水做一次水域洪泛，摸不到敌城附近的水 → 0。

### P0-8 跑批的"平局"里有一部分是对手不会收废墟

`src/core/ai.ts`（v1 内核，跑批对手 `baselines/ai-9efb961.ts`）**没有收废墟的逻辑**。
所以"对方占优但拿不到最后一座废墟"会一直拖到回合上限判平。
**这不是我们的问题，但会污染胜率**：看平局必须先确认"是不是还剩废墟没被占"。
`diag:replay` 的"陆路最小步数 / 废墟"两列就是干这个的。

### P0-6-旧 渡口选点不看水面宽度（已被 P0-6 吸收，保留证据）

**实测**：Q4\|30\|A 地图上有 **19 座桥**，而 `canReach`（陆路连通）**T1~T211 一直是 false**，
T241 才变 true。原因是选点只比"我方岸边 + 到对岸的穿水洪泛距离"，**不看这片水有多宽**；
桥的延伸受 `bridgeChainOk` 限制（超出建造距离 2 格 ≈ 合计 5 格），
于是它在一张 14 格宽湖的岸边反复起桥头、铺 4 格就停。
**另**：桥是单位，人离开桥就塌 —— 一条 5 格宽的河要吃 5 个单位。

**要做的**：`crossingPointOf` 加"连续水面 ≤ N（≈5）格"；找不到窄水面就别修（绕路/船/先不打）；
桥段数上限；`bridgeJam` 从"渡口 3 格内 ≥10 人多"改成"人多**且位置没变**"。

### P2-1 渡口选点没有连续性（"8 座桥散在河湾"的根因）

- `crossingPointOf` 每次挑"离对岸最近的岸"，不要求沿**已铺的桥面**往下接
  （`buildSpots` 有 `bridgeChainOk`，选点上没有）。
- 实测 Q3/seed30：桥 8 座、**关键 0 座**、坐标 T120→T260 一字未变，全是碎片。
- 换渡口（`noLink ≥ 30` / `cut ≥ 2`）只缓解，不治本。
- **成本高**：要改选址逻辑，单独一批跑。

### P2-2 水军封锁（用户 2026-11-23 反馈）

- AI 没有"敌方控制水域"的概念：岸线被船罩住，陆军/经济只能挪一格躲，躲不出射程就卡住。
- **三层**：① 水域威胁图（复用 `tactical.exposure`）；② 陆军走位加"离敌方船射程 X 格"惩罚；
  ③ 反舰决策（造自己的船 / 岸基远程赶船）——第三层是全新的。
- 先做 ①②。

### P2-3 `commit` 门槛写死 8 个兵

对面 20 兵时，8 兵全军压城就是排队送。要跟对面兵力比。

### P2-4 绕路只在"换城"层

没有"同一座城换一条进攻路线"（比如从另一侧过河再打同一座城）。

### P2-5 走位不绕防御建筑火力圈

建筑现在是**集火目标**，但走位评分里没有"绕开它的火力圈"这一项。

## 五、P3：计划层与体验

### P3-1 `trade` / `turtle` 还在 `stance` 里（PLAN 27）

它们**不能只用权重表达**，要先补三个出口（一次加一个，各自可验）：

1. `PlanWeights.pullHome`（0~1）：离家惩罚强度，`turtle` 用；
2. `PlanFocus` 从 `{x,y}` 扩成 `{x?, y?, cityId?}`，`trade` 用它指定主攻方向；
3. `plan.switches: { commit?, guard? }`：布尔，最容易搅乱行为，最后加。

顺序：`pullHome` → 搬 `turtle` → `focus.cityId` → 搬 `trade`。

### P3-2 `readyTurns` 没有消费者

扫描算出了"第几回合该开战"，但没有执行机制（编队 deadline、按 deadline 攒兵）。

### P3-3 回放面板不显示建造编队

`aiFocus[me].squads` 里有数据，`planSummary` 只统计 attack/defend。
39.3 的"v3 在想什么"小窗口整体没做——**等战略层落地再做**，否则是个空壳。

### P3-4 采购是"每金战力"不是"每产兵位战力"

后者只在 `power-solver.pickUnit`（钱瓶颈/名额瓶颈切换），没进采购。
只有在"钱花不完、名额是瓶颈"时才有差别——和 P0-3 同源。
