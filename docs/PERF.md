# 性能体检

> 起因：32×32 在一台机器上不卡、在另一台上明显卡。体感没法定位，也证明不了改完有没有变好。
> 这个脚本把一次完整重绘拆成几段逐段计时，输出可比的数字。
>
> 2026-10-28：按这份文档排的顺序改完了前四项，32×32 的单帧从 18.7ms 降到 4.5~5.5ms。
> 改法和取舍见下面的「已经改过的」。

```bash
npm run perf                                  # 12/16/20/24/32 五档
npm run perf -- --sizes=20,32 --frames=100    # 只测两档，帧数给足
npm run perf -- --compare                     # 32×32 上比不同配置
npm run perf -- --json=docs/perf-baseline.json   # 存一份基线
npm run perf -- --baseline=docs/perf-baseline.json  # 改完之后跟基线比
npm run perf -- --md=docs/PERF-REPORT.md      # 出一份 Markdown
```

## 一帧是什么

一帧 = `main.ts` 里 `render()` 走的那条流水，按顺序拆成四段计时：

| 阶段 | 函数 | 什么时候跑 |
|---|---|---|
| 雾视图 | `playerView()` | 每帧 |
| 威胁圈 | `threatTiles()` | 选中单位且还没行动时，每帧 |
| 棋盘 | `renderBoard()` | 每帧 |
| 侧栏 | `renderPanel()` | 每帧 |

「一帧」在真实对局里发生得很频繁：**每一个动作之后都调一次 `render()`**，AI 快进时一回合能走十几步。所以 5ms 的帧不是"每秒 200 帧"，而是"每走一步多花 5ms"。

**主表每帧切换一个选中单位**（`churn = select`）。这是刻意的：增量重绘之后，"什么都不变"的帧所有缓存全命中，那一行的数字好看但不代表真机——玩家每点一下、AI 每走一步，面板和高亮都会真的换。用"每帧换选中"当主表，改前改后才在同一把尺子上。

## 怎么读那张表

| 列 | 意思 | 怎么用 |
|---|---|---|
| **最快** | 这一档跑得最快的一帧 | **比改动前后用它**。机器上有别的活只会让帧变慢，不会让它变快 |
| p50 | 中位数 | 看典型体感 |
| p95 / 最大 | 慢帧 | 掉帧的主要来源 |
| **掉帧率** | 超过 16.7ms 的帧占比 | 直接对应"卡不卡" |
| p50 帧率 | `1000 / p50` | JS 侧上限，不是真实帧率 |
| DOM 节点 | 这一档页面里有多少元素 | 和浏览器布局成本成正比 |
| **新建元素** | 每帧被丢弃重建的 DOM 数量 | 由代码决定，**不受机器影响**——优化前后看这个最硬 |
| HTML/帧 | 每帧写进 `innerHTML` 的字节数 | 同上 |
| **读矩形** | 每帧调了几次 `getBoundingClientRect` | 每次都可能让浏览器立刻做一遍布局，真机上是纯亏 |
| 堆增量 | 跑完 N 帧后常驻涨多少（已 GC） | 短命节点多 → GC 频繁 → 一顿一顿 |

四个容易误读的地方：

1. **绝对毫秒数不可跨机器比**。同一份代码连跑两次，p50 会漂 ±10%（CPU 频率、后台进程），32×32 这种大档能漂到 ±30%，`--compare` 里甚至会差 50%。要比就比同一台机器、同一时段的两次运行。
2. **脚本测不到浏览器的布局和绘制**。jsdom 没有这两步，所以这里的帧时间是**下限**：它都过不了 16.7ms 的档，真机必然掉。反过来不成立——这里过了，真机未必过。
3. **`--baseline` 里低于 ±8% 的差异不算数**，脚本会直接标成"噪声内"。
4. **「缓存省了多少」那一节才是完整的图景**。主表只报"每帧换选中"，另外两档（什么都不变 / 每帧全量重画）在那一节里。

## 2026-10-28 的两次测量

### 改之前（增量重绘之前）

`docs/perf-baseline.json` 存的是改之后的数据，改之前的那份数字留在下面做对照：

| 规模 | 最快 | 掉帧率 | 新建元素 | HTML/帧 |
|---|---:|---:|---:|---:|
| 12×12 | 4.9ms | 2~5% | 235 | 16.6 KB |
| 16×16 | 6.2ms | 6~8% | 340 | 21.7 KB |
| 20×20 | 8.0ms | 6~16% | 482 | 29.9 KB |
| 24×24 | 10.6ms | 12~68% | 658 | 40.8 KB |
| 32×32 | **18.7ms** | **100%** | **1 106** | **66.4 KB** |

### 改之后

32×32（43 支部队），多次运行取区间：

| 画面情形 | 最快 | 新建元素 | HTML/帧 | 读矩形 |
|---|---:|---:|---:|---:|
| 同一画面重复画 | 1.5~2.3ms | 0 | 0 B | 0 |
| **每帧换选中（主表用的就是这档）** | **4.5~5.5ms** | 41 | 3.8 KB | 0 |
| 每帧全量重画（等价于改之前） | 16~21ms | 1 102~1 109 | 53~55 KB | 0 |

新建元素从 1 106 降到 41，那 41 个全是侧栏（侧栏还是一整块重写）。棋盘和棋子层现在是零。

## 已经改过的（按当时的收益排）

| 改动 | 位置 | 效果 |
|---|---|---|
| **格子层改增量重绘** | `ui/board.ts` | 1 024 个格子节点留着复用，只改变化那几格的 `className`。1 024 个元素/帧 → 0 |
| **棋子层改按 id 复用** | `ui/board.ts` `paintUnits()` | 节点留着，只 patch 变了的字段。43 个元素/帧 → 0（A/B 实测 32×32 快 8~10%） |
| **侧栏按内容跳过** | `ui/panel.ts` | 拼出 HTML 先和上次比，一样就不写。1.7ms → 0.03ms（内容没变的帧） |
| **FLIP 不再读矩形** | `ui/board.ts` | 位移自己乘格子宽算，`getBoundingClientRect` 2N 次 → 0 次 |
| **`fitBoard()` 按需执行** | `main.ts` | 用 `ResizeObserver` 标脏，只在窗口/缩放/工具栏变高时才读写布局 |
| **顶栏按签名跳过** | `ui/panel.ts` | 十几个文字的签名一样就整段跳过，顺带省掉 `syncTopbarScroll()` 的那次布局 |
| **`playerView()` 每帧只算一遍** | `main.ts` | 以前 render 和侧栏各算一次，白烧 ~0.7ms |

## 瓶颈在哪（改完之后）

- **JS 侧已经进预算**：32×32 p50 5~8ms，最快 4.5~5.5ms，掉帧率 0%。
- **不再是"格数问题"**：格数从 144 涨到 1 024（×7.1），单帧只涨 ×1.4。线性拟合的"每格成本"已经掉到 2µs 量级，固定开销占七成——**盯着格子优化是白费力气了**。
- **剩下的大头是"每帧固定的那部分"**：棋子层 patch、侧栏整块重写、雾视图。它们只跟"有多少单位、面板里写了多少字"走。
- **侧栏是最大的一块**（1.4~1.9ms/帧）。按内容跳过已经做了，这个数代表"内容真变了"的帧；而它仍然是一整块 30KB 重写——换一个选中，顶卡和战报卡这些没变的也跟着重建。
- **抖动还是存在**：最快 4.5ms、最慢 14ms，差 2.5~3 倍。来源是 GC 和强制布局，不是算力。真机上这就是那种"隔几秒一顿"。

## 还能改什么（按现在的收益排）

1. **侧栏拆成几块各自缓存**：顶卡（金币/城市/回合）、详情卡（选中单位）、战报卡各存一份 HTML。换选中只重建详情卡。预计能砍掉侧栏的 60~70%。
2. **雾视图按需重算**：`playerView()` 只依赖单位位置、视野和回合。这些没变就可以复用上一次的结果。
3. **AI 决策让帧**：单次 8~10ms，一回合十几步会累加成肉眼可见的停顿。短期在决策前后 `await` 一个 0 延时，长期挪 Worker。
4. **静态地形层 canvas 化**：把 1 024 个 `.tile` 的地形背景画到一张 canvas 上，DOM 里只留高亮层和棋子。**这条现在不划算了**：格子层已经不再重写，canvas 化只能省"样式重算与绘制"，却要动掉所有依赖 `.tile.t-water` 这类选择器的测试与样式。只有真机上确认瓶颈在绘制时再做。

## 改完怎么验

```bash
npm run perf -- --json=docs/perf-baseline.json    # 改之前
# 改代码
npm run perf -- --baseline=docs/perf-baseline.json
```

看两样：

- **新建元素 / HTML 字节 / 读矩形**——这三个由代码决定，不受机器影响。从 1 106 降到 41 就是降了，没有争议。
- **最快帧**——看趋势，别抠小数点。连跑三次都对得上再下结论。

想在真机上确认，浏览器三步：

1. DevTools → Performance → 录制 3 秒 → 看 Main 线程最长的那块是不是 `renderBoard` / `renderPanel`；
2. 同一次录制里看有没有紫色的 Layout 条反复出现（强制同步布局）；
3. Rendering 面板开 `Paint flashing`，点一下棋盘看是不是整屏在闪——是的话说明还有全量重绘。

## 局限

- 不含浏览器布局与绘制，也不含 GPU 合成。显卡差、屏幕分辨率高的机器，真实开销比这里高。
- **jsdom 的 `innerHTML` 比真浏览器慢得多**（它自己解析、自己建节点，没有浏览器的快速路径）。所以"避免 innerHTML"这类改动的收益，在这里被放大了；反过来说，"节点复用"在真机上的收益主要在样式重算和绘制，本脚本量不到。
- 只测 UI 重绘这条路径。首屏启动、存档读写、AI 整回合推演另算（AI 单步在表里，整回合没有）。
- 兵力是按面积自动摆的（32×32 摆 43 支），不是真实对局推演出来的局面。
- `--compare` 里的"基准"直接取主表那一行，不重新跑。重跑一次就会差 30~50%，那是机器状态不是配置差异。
