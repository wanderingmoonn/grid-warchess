# 性能体检

> 起因：32×32 在一台机器上不卡、在另一台上明显卡。体感没法定位，也证明不了改完有没有变好。
> 这个脚本把一次完整重绘拆成几段逐段计时，输出可比的数字。

```bash
npm run perf                                  # 12/16/20/24/32 五档
npm run perf -- --sizes=20,32 --frames=100    # 只测两档，帧数给足
npm run perf -- --compare                     # 32×32 上比不同配置
npm run perf -- --json=docs/perf-baseline.json   # 存一份基线
npm run perf -- --baseline=docs/perf-baseline.json  # 改完之后跟基线比
npm run perf -- --md=docs/PERF-REPORT.md      # 出一份 Markdown
```

## 一帧是什么

一帧 = `main.ts` 里 `render()` 走的那条流水，按顺序拆成四段计时：

| 阶段 | 函数 | 什么时候跑 |
|---|---|---|
| 雾视图 | `playerView()` | 每帧 |
| 威胁圈 | `threatTiles()` | 选中单位且还没行动时，每帧 |
| 棋盘 | `renderBoard()` | 每帧 |
| 侧栏 | `renderPanel()` | 每帧 |

「一帧」在真实对局里发生得很频繁：**每一个动作之后都调一次 `render()`**，AI 快进时一回合能走十几步。所以 20ms 的帧不是"每秒 50 帧"，而是"每走一步卡一下"。

## 怎么读那张表

| 列 | 意思 | 怎么用 |
|---|---|---|
| **最快** | 这一档跑得最快的一帧 | **比改动前后用它**。机器上有别的活只会让帧变慢，不会让它变快 |
| p50 | 中位数 | 看典型体感 |
| p95 / 最大 | 慢帧 | 掉帧的主要来源 |
| **掉帧率** | 超过 16.7ms 的帧占比 | 直接对应"卡不卡" |
| p50 帧率 | `1000 / p50` | JS 侧上限，不是真实帧率 |
| DOM 节点 | 这一档页面里有多少元素 | 和浏览器布局成本成正比 |
| **新建元素** | 每帧被丢弃重建的 DOM 数量 | 由代码决定，**不受机器影响**——优化前后看这个最硬 |
| HTML/帧 | 每帧写进 `innerHTML` 的字节数 | 同上 |
| 堆增量 | 跑完 N 帧后常驻涨多少（已 GC） | 短命节点多 → GC 频繁 → 一顿一顿 |

三个容易误读的地方：

1. **绝对毫秒数不可跨机器比**。同一份代码连跑两次，p50 会漂 ±10%（CPU 频率、后台进程），32×32 这种大档能漂到 ±30%。要比就比同一台机器、同一时段的两次运行。
2. **脚本测不到浏览器的布局和绘制**。jsdom 没有这两步，所以这里的帧时间是**下限**：它都过不了 16.7ms 的档，真机必然掉。
3. **`--baseline` 里低于 ±8% 的差异不算数**，脚本会直接标成"噪声内"。

## 2026-10-28 的基线

`docs/perf-baseline.json` 是这一版的数据。32×32（43 支部队）：

```
最快 18.8ms · p50 21.0~32.2ms · 掉帧率 100%
每帧新建 1 106 个元素、写 66.4 KB HTML
```

分档：

| 规模 | 最快 | 掉帧率 | 新建元素 | HTML/帧 |
|---|---:|---:|---:|---:|
| 12×12 | 4.9ms | 2~5% | 235 | 16.6 KB |
| 16×16 | 6.2ms | 6~8% | 340 | 21.7 KB |
| 20×20 | 8.0ms | 6~16% | 482 | 29.9 KB |
| 24×24 | 10.6ms | 12~68% | 658 | 40.8 KB |
| 32×32 | 18.8ms | **100%** | **1 106** | **66.4 KB** |

## 瓶颈在哪

按格数做线性拟合，单帧 = **固定开销 ≈ 4.8ms + 每格 ≈ 26µs**（R² = 0.99）。32×32 里 85% 是格子本身。

| 结论 | 证据 |
|---|---|
| **棋盘重绘吃掉 89%** | 32×32 上 `renderBoard` 28.7ms，侧栏 1.9ms、雾 1.4ms、威胁圈 0.2ms |
| **每帧全量重建** | `board.ts:153` 一句 `tilesEl.innerHTML = tileParts.join('')`，1 024 个格子连同城市、棋子一起丢弃重建 |
| **格子数就是主要变量** | 兵力从 43 加到 85 只贵 2%；格数从 144 到 1 024 让单帧涨 3.2 倍 |
| **扩展和雾不是主因** | 开三项基础扩展 −0%、开雾 +18%（含噪声）、兵力翻倍 +2%，都在同一量级 |
| **AI 决策不是主因** | 32×32 单次 9.3ms（最快 7.5ms），一回合十几步会累加，但比每帧 20ms 轻得多 |
| **抖动比均值更刺眼** | 同一份活最快 20ms、最慢 44ms，差 2.2 倍——GC 和强制布局造成的"一顿一顿" |

### 具体位置

- `src/ui/board.ts:124-153`：每格拼一段字符串，`s.cities.find()` 在循环里逐格调用；最后整块 `innerHTML` 覆盖。
- `src/ui/board.ts:240-276`：FLIP 动画先量一遍所有棋子的 `getBoundingClientRect`，**重写 `innerHTML` 之后**再量一遍。真机上这是"写 → 读 → 写"，每次读都会强制同步布局。
- `src/main.ts:663`：`render()` 是同步调用，不是 rAF 节流；一次动作触发一次完整重绘。
- `src/main.ts:786`：`fitBoard()` 每帧读 `offsetWidth/offsetHeight` 再写 `style.width/height`，同样是强制同步布局。
- CSS：每个 `.tile` 最多 3 个绘制对象（自身 + `::before` 地形纹理 + `::after` 高亮层），32×32 最多 3 072 个。

## 建议的改法（按收益排）

1. **格子层改增量重绘**。缓存 1 024 个节点，只在"地形 / 归属 / 高亮档位"变化的格子上改 `className`。高亮（可达 / 可攻击 / 威胁 / 可放置）每帧都变，但那只是换 class，比重建节点便宜一个数量级。
2. **静态地形层 canvas 化**。地形只在对局开始时定一次，整层可以画成一张 canvas；DOM 里只留高亮层和棋子。这一条能把 1 024 个 div 直接砍掉。
3. **侧栏按签名跳过**。1.2~1.9ms/帧的整块重绘里，大部分帧输入根本没变（金币、回合、选中项、战报长度）。
4. **FLIP 不读矩形**。位置本来就是按百分比算的，`(x,y)` 直接能推出像素位移，不需要 `getBoundingClientRect`。动画交给 `transform` + 一次 rAF。
5. **`render()` 用 rAF 合并**。同一帧里连着触发三次重绘时，只画最后一次。
6. **AI 决策让帧**。单次 9ms 在本机不明显，但低端机上是十几毫秒的连续卡顿；短期在决策前后 `await` 一个 0 延时，长期挪 Worker。

## 改完怎么验

```bash
npm run perf -- --json=docs/perf-baseline.json    # 改之前
# 改代码
npm run perf -- --baseline=docs/perf-baseline.json
```

看两样：

- **新建元素 / HTML 字节**——这两个由代码决定，不受机器影响。从 1 106 降到 200 就是降了，没有争议。
- **最快帧**——看趋势，别抠小数点。连跑三次都对得上再下结论。

想在真机上确认，浏览器三步：

1. DevTools → Performance → 录制 3 秒 → 看 Main 线程最长的那块是不是 `renderBoard`；
2. 同一次录制里看有没有紫色的 Layout 条反复出现（强制同步布局）；
3. Rendering 面板开 `Paint flashing`，点一下棋盘看是不是整屏在闪——是的话就是全量重绘。

## 局限

- 不含浏览器布局与绘制，也不含 GPU 合成。显卡差、屏幕分辨率高的机器，真实开销比这里高。
- 只测 UI 重绘这条路径。首屏启动、存档读写、AI 整回合推演另算（AI 单步在表里，整回合没有）。
- 兵力是按面积自动摆的（32×32 摆 43 支），不是真实对局推演出来的局面。
- `--compare` 里的"基准"直接取主表那一行，不重新跑。重跑一次就会差 30~50%，那是机器状态不是配置差异。
