# v4 题库（exams/）

> 这里面装的是 v4 的"考卷"。规矩看 `docs/GUIDE-V4-EXAM-2026-11-23.md`，
> 为什么要考卷看 `docs/PLAN-V4-2026-11-23.md` 第五节。
> **一道题不经手五个文件就不算存在**（第五个是评审）。

---

## 一、一道题 = 五个文件

| 文件 | 给谁 | 里面有什么 | 能不能外发 |
|---|---|---|---|
| `snap.json` | 游戏 | 那一格的完整局面（首页「导入对局」粘贴） | ✅ 发给测试员 |
| `card.md` | 测试员 | 局面摘要（有多少什么）+ 问题 + 请他回的三件事 | ✅ 发给测试员 |
| `answer.md` | 出题人 | 标准答案、红线 | ❌ 含答案 |
| `author.md` | 出题人 | 带坐标的完整面板 + 被雾挡住的敌人 + **v3 这一回合实际做了什么** | ❌ 含隐藏信息 |
| `criteria.json` | 判分器 | 机器可读的判据（`scripts/exam-grade.ts` 只认这一份） | ❌ 含答案 |
| `review.md` | 所有人 | 测试员原话 + 我们认定这题能不能用 | ✅ |

没有 `criteria.json` 的题，判分器会直接拒绝——**判据没写就等于没人会去执行它**。
判据写了的题还必须过"可行性"（见第四节第三条），过不了就标 `"status": "unusable"`，
判分器会拒绝出结论，除非加 `--force`。

`card.md` 和 `author.md` 都从同一个局面生成，所以"给人看的"和"给机器判的"永远是同一盘棋。
`card.md` 里**只有测试员在游戏里看得见的东西**——被雾挡住的敌人一个字都不许出现，
否则这题就成了"人开了全图，AI 没有"。

## 四、四条必须记住的发现（会影响后面怎么出题）

### ① 24×24 的真实局面很快就不适合当单机制题

`Q3|49|A` 到第 31 手就已经 28 个单位、第 61 手 38 个、第 151 手 64 个。
手册第八节把"局面太复杂（十个兵、三个战场）"列为坏题——因为答错了也归因不明。
**单机制题请优先从 12×12 挖**（`Q1` 那一档，19~23 个单位已经是上限）。
大图只留给整局过程指标，以及下面第二条说的手工小局。

### ② 从失败局直接切出来的局面，多半是"综合判断"题

原因很实在：v3 的失败不是"少做了一个明确动作"，而是"整体判断错了"。
所以真实局面的答案一定有分歧（守还是弃、打还是等），判据也就写不硬。

**真实回放的价值是"证据"，不是"题目本体"。** 题目本体要靠手工摆小局面——
把某一个病单独隔离出来，像 v3 的探针那样（`probe:bridge-block` 就是手工摆的"桥头被自己人堵住"）。
那条路在 v3 里是有效的：探针把病钉死了，虽然当时没能治好。

### ③ 局面真实 ≠ 局面合理（`Y-001` 教我们的）

测试员的原话是"他不论如何都不会打出这种局面"。回放里每一格都真发生过，
但只有一部分是**人也会走到的**。过不了这一道，题目问的就是"人从没遇到过的问题"。

→ 出题前先问一句：**这局面人会不会走到这里？** 答不出"会"就别用。

### ④ 判据必须先证明可行（`Y-002` 教我们的）

`Y-002` 的三条判据，空壳 / v1 / v3 **全红同一条**。这不是"三个答题者都差"，
而是"这道要求本来没人做到过"。所以：

> **一条判据在被某个执行者跑绿之前，只是没人验证过的一段文字。**

跑绿的那个执行者最好是**人的答案**（它同时证明"人能赢"和"判据没写错"）。
做不到就先标 `"status": "unusable"`，判分器会拒绝出结论。

所以第一批 15 题的构成改成：

| 类型 | 数量 | 来源 | 判据 |
|---|---|---|---|
| 真实局面（综合判断） | 3~5 道 | 这三局 + 后面导的失败局 | 松一点，先验流程 |
| 手工小局（单机制） | 10+ 道 | 照病灶自己摆 | **硬**，也最容易先红后绿 |

## 五、工具与还差什么

三件工具都在了：

| 工具 | 干什么 |
|---|---|
| `scripts/make-exam.ts` | 从回放里切一格（真实局面） |
| `scripts/make-scene.ts` | 手摆一格（单机制题；`scenes/*.json`） |
| `scripts/exam-grade.ts` | 判分：`--me-ai v3/v1/none` 或 `--answers`，跑 N 手看判据红绿 |

三者共用 `scripts/lib/exam-kit.ts` 写文件，所以题卡长相永远一致。

**还差的一件：人工答案的可执行化。** 测试员给的是战略（"看住关口""抓紧升 3"），
不是动作序列，判分器没法直接跑。两条路：出题人代打并录动作，或者给游戏加一个
"导出从导入起的动作"。在这条打通之前，"人的答案必须绿"这条**验不了**——
所以现在判据的可行性只能靠 v1/v3 证明（`S-001` 就是这么立住的：v3 跑绿）。

顺带两件小事：
1. 判分器的"三桩对照"还要手打三条命令，以后加 `--check` 一次跑完并自动标"三桩全红"；
2. `scenes/` 里的局面会随兵种表/规则改动失效，规则一变要重跑一遍（和题库体检同一件事）。

## 六、命令

```bash
# 从跑批队列复现某一局（种子不在 30/31/32 时要加 --allow-any-seed）
node --experimental-strip-types scripts/export-bench-replay.ts \
  --queue Q3 --seed 49 --new-side A --allow-any-seed \
  --out results/replays/v4src-Q3-49-A.json

# 看一局的时间线（每 30 手一行：城/兵/经济/金）
node --experimental-strip-types scripts/analyze-replay.ts results/replays/v4src-Q3-49-A.json --every 30

# 从某局切一格出来出题（--dry 只看不出文件）
node --experimental-strip-types scripts/make-exam.ts \
  --replay results/replays/v4src-Q1-30-A.json \
  --turn 12 --me A --id Y-001 [--ask "自定义问句"] [--dry]

# 判分：让某个答题者从那一格往下走 N 手，看判据红绿
node --experimental-strip-types scripts/exam-grade.ts --exam exams/Y-002 --me-ai v3   # v3 现状
node --experimental-strip-types scripts/exam-grade.ts --exam exams/Y-002 --me-ai none # 空壳
node --experimental-strip-types scripts/exam-grade.ts --exam exams/Y-002 --me-ai v1   # v1
node --experimental-strip-types scripts/exam-grade.ts --exam exams/Y-002 --answers my.json
#   ↑ 人手答案：{ "turns": [[{...动作...}], [{...}]] }，我方按回合分组，对手仍由 --foe-ai 决定
```

`--turn` 是**半回合**（引擎每次结束回合把 `turn` 加一，A 打完是 B）。
脚本会切到"该方还没动手"的第一格，实际落在第几手会打在面板标题上。

判分器的三条铁律：**空壳必须红**（否则题会白送）、**人写的答案必须绿**（否则判据写错）、
**判据要能被人跑绿**（否则是在要求一件没人做到过的事）。

## 七、种子卫生（别忘）

- `30 / 31 / 32`：被 v3 调参用过太多次，**只配当出题原料**，不能当验收集。
- `40~49`：v3 的诚实验收样本，同上——出题可以，验收不行。
- `60~69`：**留给 v4 自己的体检，出题时不许用，写完锁起来。**

题库是 v4 的开发集（拿它调，天经地义）；验收集必须是没进过题库的种子。
v3 就是在"练习卷即考卷"上刷出了 88% 的假成绩。
